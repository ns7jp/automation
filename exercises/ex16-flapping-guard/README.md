## 1. どんな場面で必要になるか

ex15 で作った監視スクリプトを cron で5分ごとに動かし、異常を見つけたらSlackへ通知するようにしたとします。翌朝、担当者のスマートフォンには通知が**112件**たまっていました。原因を調べると、深夜に一瞬だけ回線が揺れて1回だけ ping が失敗しただけ。しかもその後は正常なのに、別のサーバーの障害通知が5分おきに鳴り続けていました。

こうなると人は通知を見なくなります。**通知が多すぎる監視は、監視をしていないのと同じ**です。実務ではこれを防ぐために2つの決まりごとを入れます。1つは「1回の失敗では騒がない (連続N回失敗して初めて異常とみなす)」、もう1つは「一度通知したら、状態が変わるまで同じ通知は出さない」です。さらに、直ったときに「復旧しました」と知らせることも同じくらい大切です。復旧通知が無いと、担当者は現地に着くまで直ったことに気づけません。

短時間で異常と正常を行ったり来たりして通知が暴れる現象を**フラッピング (flapping)** と呼びます。この演習では、そのフラッピングを抑える「連続失敗回数」と「通知済みフラグ」という2つの状態を、ファイルに保存しながら管理するスクリプトを書きます。案件No.4 の `state.csv` がまさにこの仕組みです。

## 2. この演習で学ぶこと

| 学ぶこと | ひとことで言うと |
|---|---|
| 状態ファイル | スクリプトは毎回終了する。前回の記憶はファイルに残すしかない |
| `read` によるファイルの分解 | `read -r a b < ファイル` で1行を空白区切りの変数に分ける |
| 環境変数の既定値 | `${FAIL_THRESHOLD:-3}` で「指定が無ければ3」を実現する |
| しきい値判定 | 連続失敗が何回続いたら異常とみなすかを数値で比較する |
| エッジトリガの考え方 | 通知は「状態が変わった瞬間」だけ出す。同じ状態の間は出さない |
| 復旧通知 | 直ったことを知らせるところまでが監視の仕事 |

### 3分でわかる予備知識

**なぜ状態ファイルが必要か**

シェルスクリプトは実行が終わると、変数の中身をすべて忘れます。cron から5分おきに呼ばれるスクリプトにとって、5分前の自分は別人です。「前回まで何回連続で失敗していたか」を覚えておくには、**ファイルに書いて残す**しかありません。

```text
1回目の実行 → 状態ファイルに「1 no」と書いて終了
2回目の実行 → 状態ファイルから「1 no」を読む → 2回目だと分かる
```

**状態ファイルを読む**

```bash
count=0
notified="no"
if [[ -f "$STATE_FILE" ]]; then
    read -r count notified < "$STATE_FILE"
fi
```

`read -r count notified < ファイル` は、ファイルの1行目を空白で区切って `count` と `notified` に入れます。ファイルがまだ無い初回のために、**読む前に既定値を入れておく**のがポイントです。

**状態ファイルを書く**

```bash
echo "${count} ${notified}" > "$STATE_FILE"
```

`>` は上書きです。状態は「最新の1行だけあればよい」ので、追記 (`>>`) ではなく上書きにします。

**環境変数で既定値を切り替える**

```bash
FAIL_THRESHOLD="${FAIL_THRESHOLD:-3}"
```

`${変数:-既定値}` は「変数が未定義または空なら既定値を使う」という書き方です。こう書いておくと、スクリプトを変更せずに実行時だけ設定を変えられます。

```bash
FAIL_THRESHOLD=2 bash alert_state.sh web01 ng    # この実行だけしきい値2
```

**ディレクトリを用意する**

```bash
mkdir -p "$STATE_DIR"
```

`-p` を付けると、既にあってもエラーにならず、途中のディレクトリもまとめて作られます。無人で動くスクリプトでは `mkdir -p` が定番です。

**エッジトリガとレベルトリガ**

| 考え方 | 意味 | 通知の出かた |
|---|---|---|
| レベルトリガ | 異常な「状態」である限り出す | 5分おきに鳴り続ける |
| エッジトリガ | 状態が変わった「瞬間」だけ出す | 異常になった時と、直った時の2回だけ |

監視の通知はエッジトリガにします。そのために「もう通知したか」を覚えておくフラグ (`yes` / `no`) が必要になります。

## 3. 課題

`work/alert_state.sh` を編集し、次の仕様を満たすスクリプトを完成させてください。

このスクリプトは「1台ぶんの監視結果 (`ok` または `ng`) を受け取り、通知すべきかどうかを判断して1行表示する」係です。実際の通知の送信は行わず、**通知するかどうかの判断**だけに集中します。

### 使い方と設定

```text
alert_state.sh <ホスト名> <ok|ng>
```

| 環境変数 | 既定値 | 意味 |
|---|---|---|
| `STATE_DIR` | `./state` | 状態ファイルを置くディレクトリ。無ければ作る |
| `FAIL_THRESHOLD` | `3` | 何回連続で失敗したら異常とみなすか |

状態ファイルは `<STATE_DIR>/<ホスト名>.state` です。中身は**1行**で、半角スペース区切りで次の2つを書きます。

```text
<連続失敗回数> <通知済みフラグ>
```

例: 3回連続で失敗し、通知済みの状態

```text
3 yes
```

通知済みフラグは `yes` または `no` です。状態ファイルがまだ無いときは「連続失敗回数0 / 通知済みフラグ no」として扱います。

### 仕様

| No. | 条件 | 期待する動作 |
|---|---|---|
| 1 | 引数がちょうど2個でない | 使い方を**標準エラー出力**に表示し、終了ステータス `1` で終わる |
| 2 | 2つ目の引数が `ok` / `ng` 以外 | 使い方を**標準エラー出力**に表示し、終了ステータス `1` で終わる |
| 3 | `ng` を受けた | 連続失敗回数を1増やす |
| 4 | `ng` で、回数がしきい値**未満** | `様子見: <ホスト名> 連続<回数>回目の失敗 (しきい値: <N>回)` を表示する |
| 5 | `ng` で、回数がしきい値**以上**、かつ未通知 | `通知: <ホスト名> が異常です (連続<回数>回失敗)` を表示し、通知済みフラグを `yes` にする |
| 6 | `ng` で、回数がしきい値**以上**、かつ通知済み | `抑止: <ホスト名> は通知済みです (連続<回数>回失敗)` を表示する |
| 7 | `ok` を受けた、かつ通知済み | `通知: <ホスト名> が復旧しました (連続<回数>回失敗のあと復旧)` を表示する |
| 8 | `ok` を受けた、かつ未通知 | `正常: <ホスト名>` **とだけ**表示する |
| 9 | `ok` を受けた (どちらの場合も) | 連続失敗回数を `0`、通知済みフラグを `no` にリセットする |
| 10 | 処理が正常に終わった | 状態ファイルを更新し、終了ステータス `0` で終わる |

補足:

- 仕様7の `<回数>` は、**リセットする前の**連続失敗回数です (4回失敗したあとに復旧したなら `連続4回失敗のあと復旧`)。
- 表示は毎回**1行だけ**です。仕様8で「復旧しました」を出してはいけません。
- 状態ファイルは毎回上書きします (追記しません)。

### 実行例 / 出力フォーマット

しきい値が既定の3のまま、`web01` の監視結果を順に流し込んだ場合です。

```text
$ bash alert_state.sh web01 ng
様子見: web01 連続1回目の失敗 (しきい値: 3回)
$ cat state/web01.state
1 no

$ bash alert_state.sh web01 ng
様子見: web01 連続2回目の失敗 (しきい値: 3回)

$ bash alert_state.sh web01 ng
通知: web01 が異常です (連続3回失敗)
$ cat state/web01.state
3 yes

$ bash alert_state.sh web01 ng
抑止: web01 は通知済みです (連続4回失敗)

$ bash alert_state.sh web01 ok
通知: web01 が復旧しました (連続4回失敗のあと復旧)
$ cat state/web01.state
0 no

$ bash alert_state.sh web01 ok
正常: web01
```

しきい値を2に変えた場合です。

```text
$ FAIL_THRESHOLD=2 bash alert_state.sh web09 ng
様子見: web09 連続1回目の失敗 (しきい値: 2回)
$ FAIL_THRESHOLD=2 bash alert_state.sh web09 ng
通知: web09 が異常です (連続2回失敗)
```

書式で必ず守る点:

- ラベル (`様子見` `通知` `抑止` `正常`) のあとは**半角コロン+半角スペース**
- かっこは**半角の `( )`** で、その前に**半角スペース1つ**
- 状態ファイルの区切りは**半角スペース1つ**で、`3 yes` のように2項目だけ

### 使い方メッセージ

引数が正しくないときに標準エラー出力へ表示します。「使い方」という単語を必ず含めてください。

```text
使い方: alert_state.sh <ホスト名> <ok|ng>
```

## 5. ヒント

自力で20分考えてから開いてください。

<details>
<summary>ヒント1: 状態遷移を表に描いてから書く</summary>

コードを書く前に、「今の状態」と「受け取った結果」の組み合わせを表にすると、`if` の分岐がそのまま決まります。

| 受け取った結果 | 連続失敗回数 | 通知済み | 出す言葉 | 更新後の状態 |
|---|---|---|---|---|
| ng | しきい値未満 | どちらでも | 様子見 | 回数+1 / フラグはそのまま |
| ng | しきい値以上 | no | 通知 (異常) | 回数+1 / フラグ yes |
| ng | しきい値以上 | yes | 抑止 | 回数+1 / フラグ yes |
| ok | - | yes | 通知 (復旧) | 回数0 / フラグ no |
| ok | - | no | 正常 | 回数0 / フラグ no |

「回数を1増やしてから判定する」順番にすると、表のとおりに書けます。

</details>

<details>
<summary>ヒント2: 状態の読み書きと分岐の書き方</summary>

```bash
# 読む(ファイルが無い初回のために既定値を先に入れておく)
FAIL_COUNT=0
NOTIFIED="no"
if [[ -f "$STATE_FILE" ]]; then
    read -r FAIL_COUNT NOTIFIED < "$STATE_FILE"
fi

# ng のときの分岐
FAIL_COUNT=$((FAIL_COUNT + 1))
if [[ "$FAIL_COUNT" -lt "$FAIL_THRESHOLD" ]]; then
    echo "様子見: ..."
elif [[ "$NOTIFIED" != "yes" ]]; then
    echo "通知: ..."
    NOTIFIED="yes"
else
    echo "抑止: ..."
fi

# 書く(最後に必ず1回だけ)
echo "${FAIL_COUNT} ${NOTIFIED}" > "$STATE_FILE"
```

`-lt` は「より小さい (less than)」です。数値の比較には `-lt` `-ge` (以上) を使います。

</details>

<details>
<summary>ヒント3: 全体の骨組み</summary>

```bash
#!/bin/bash
set -u

usage() {
    echo "使い方: $(basename "$0") <ホスト名> <ok|ng>"
}

if [[ "$#" -ne 2 ]]; then
    usage >&2
    exit 1
fi

HOST="$1"
RESULT="$2"

case "$RESULT" in
    ok|ng) ;;                 # 正しい値なので何もしない
    *) usage >&2; exit 1 ;;
esac

STATE_DIR="${STATE_DIR:-./state}"
FAIL_THRESHOLD="${FAIL_THRESHOLD:-3}"
STATE_FILE="${STATE_DIR}/${HOST}.state"
mkdir -p "$STATE_DIR"

# ここで状態を読み、ng / ok で分岐し、最後に状態を書き出す

exit 0
```

`case` の `ok|ng) ;;` は「ok か ng なら何もしない」という書き方です。正常な値を先に通し、それ以外をまとめて弾くと読みやすくなります。

</details>

## 6. よくあるつまずき

| 症状 | 原因と対処 |
|---|---|
| `unbound variable` と出る | `set -u` の状態で `$STATE_DIR` を直接使っている。`STATE_DIR="${STATE_DIR:-./state}"` のように既定値を与える |
| 何回 `ng` を出しても「連続1回目」のまま | 状態ファイルを読んでいない、または書き出しを忘れている。最後に必ず1回 `echo "..." > "$STATE_FILE"` を実行する |
| `No such file or directory` と出る | `mkdir -p "$STATE_DIR"` を書く前に状態ファイルへ書き込んでいる。ディレクトリ作成を先に行う |
| 3回目以降ずっと「通知」が出続ける | 通知済みフラグを `yes` に更新していない。`NOTIFIED="yes"` を忘れていないか確認する |
| 復旧しても「正常」しか出ない | 回数とフラグのリセットを、メッセージを表示する**前**に行っている。表示してからリセットする |
| 状態ファイルが2行になっている | `>` ではなく `>>` (追記) で書いている。状態は上書きで保存する |

`./check.sh 16` が失敗したときは、`KEEP_WORKDIR=1 ./check.sh 16` と実行すると採点用の作業ディレクトリが残ります。中の `state/` を覗くと、状態ファイルの中身を確認できます。

## 7. 発展課題(採点対象外)

1. しきい値に到達したあと、一定回数ごと (例: 12回ごと) に「まだ異常が続いています」と再通知する仕組みを足す
2. 状態ファイルに最終更新日時も保存し、`障害継続時間` を復旧通知に含める
3. `--reset <ホスト名>` オプションを足し、メンテナンス前に状態を初期化できるようにする
