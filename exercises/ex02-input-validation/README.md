## 1. どんな場面で必要になるか

株式会社サンプル商事の情報システム部では、毎月の入社者ぶんのアカウントを、人事部から届いたCSVファイルをもとに一括作成しています。ところが現場では「ファイル名を打ち間違えた」「共有フォルダから他人が作ったファイルをコピーしてきたので読み取り権限が無い」「Excelで開いて保存し直したら中身が空になっていた」といった事故が普通に起こります。

このとき、**入力の確認をせずに処理を始めてしまうスクリプトは最悪です。** 途中まで作られた中途半端なアカウントが残ったり、原因の分からないエラーが延々と流れたりして、後片付けに何時間もかかります。

そのため実務のスクリプトは、必ず先頭で「これから使う入力が本当に使えるものか」を確認し、駄目ならすぐに止まります。この「処理を始める前に止まる仕組み」を安全装置(ガード)と呼びます。

案件No.1の `create_users.sh` も、CSVを1行も読む前に「ファイルがあるか」「読めるか」を確認しています。この演習では、その安全装置の部分だけを取り出して自分で書きます。

## 2. この演習で学ぶこと

| 学ぶこと | ひとことで言うと |
|---|---|
| `if` / `elif` / `else` | 条件によって処理を分ける文法。条件が複数あるときは順番が意味を持つ |
| ファイル判定演算子 | `-f`(通常ファイルか) `-r`(読めるか) `-s`(中身が空でないか)の3点セット |
| 否定 `!` | 「〜でないとき」を書く記号。`[[ ! -f "$FILE" ]]` で「ファイルが無いとき」 |
| 終了ステータスの使い分け | 失敗の理由ごとに違う数字を返すと、呼び出し側が原因を判別できる |
| `wc -l` のリダイレクト形 | `wc -l < file` と書くと、行数の数字だけが得られる |

### 3分でわかる予備知識

**ファイルの状態を調べる書き方**

Bashには「ファイルがどうなっているか」を調べる専用の記号があります。`[[ ]]` の中で使います。

```bash
FILE="users.csv"

[[ -e "$FILE" ]]   # 存在する(ファイルでもディレクトリでも真)
[[ -f "$FILE" ]]   # 「通常ファイル」として存在する(ディレクトリは偽)
[[ -r "$FILE" ]]   # 読み取り権限がある
[[ -w "$FILE" ]]   # 書き込み権限がある
[[ -s "$FILE" ]]   # 存在し、かつサイズが0より大きい(空ではない)
[[ -d "$FILE" ]]   # ディレクトリである
```

この演習では `-f` `-r` `-s` の3つを使います。`-e` ではなく `-f` を使うのは、ディレクトリを指定されたときも「ファイルではない」として弾きたいからです。

**「〜でないとき」の書き方**

判定の前に `!` を置くと意味が反転します。エラー処理は「駄目なときに書く」ので、この形が圧倒的によく出てきます。

```bash
if [[ ! -f "$FILE" ]]; then
    echo "エラー: ファイルが見つかりません: ${FILE}" >&2
    exit 2
fi
```

`!` と `-f` の間の半角スペースは必須です。詰めて書くとエラーになります。

**終了ステータスを理由ごとに変える**

ex01では「成功=0 / 失敗=1」だけを使いました。実務では、失敗の理由ごとに違う数字を返すことがあります。

```bash
exit 1   # 使い方が間違っている
exit 2   # ファイルが無い
exit 3   # 権限が無い
exit 4   # 中身が空
```

こうしておくと、このスクリプトを呼び出した側(cronのジョブや別のスクリプト)が `$?` の値を見て「2ならファイル配置のミスだから人事部に連絡」「3なら権限の問題だからサーバー担当に連絡」と、**中身を読まずに次の行動を判断できます。**

なお、慣習として 0 は必ず成功を意味します。また 126 以上の数字はシェルが特別な意味で使うため、自分で決める終了ステータスは 1〜125 の範囲にします。

**行数を数える `wc -l`**

`wc -l` はファイルの行数を数えるコマンドですが、2通りの書き方で結果の見た目が変わります。

```bash
wc -l users.csv      # → 4 users.csv   ← ファイル名まで出てしまう
wc -l < users.csv    # → 4             ← 数字だけ
```

`<` は「このファイルの中身を、コマンドの標準入力に流し込む」という記号(リダイレクト)です。この書き方だと `wc` は自分が何のファイルを読んでいるか知らないので、ファイル名を出しようがありません。**メッセージに数字だけを埋め込みたいときは、必ず `$(wc -l < "$FILE")` の形を使います。**

## 3. 課題

`work/check_input.sh` を編集し、「入力ファイルが処理できる状態かどうか」を確認するスクリプトを完成させてください。

### 仕様

| No. | 条件 | 期待する動作 |
|---|---|---|
| 1 | 引数がちょうど1個ではない(0個・2個以上) | 「使い方」を含むメッセージを**標準エラー出力**に表示し、終了ステータス `1` |
| 2 | 指定されたファイルが存在しない | 標準エラー出力に `エラー: ファイルが見つかりません: <パス>` を表示し、終了ステータス `2` |
| 3 | 存在するが読み取り権限が無い | 標準エラー出力に `エラー: 読み取り権限がありません: <パス>` を表示し、終了ステータス `3` |
| 4 | 存在し読めるが、中身が空(サイズ0) | 標準エラー出力に `エラー: ファイルが空です: <パス>` を表示し、終了ステータス `4` |
| 5 | すべて問題なし | 標準出力に `OK: <パス> は処理できます (<行数>行)` を表示し、終了ステータス `0` |
| 6 | 判定の順番 | 「存在するか」→「読めるか」→「空でないか」の順に確認する |

`<パス>` は、引数で受け取った文字列をそのまま使ってください(絶対パスに変換しない)。

### 実行例 / 出力フォーマット

```text
$ bash check_input.sh
エラー: 入力ファイルを1つ指定してください。
使い方: check_input.sh <入力ファイル>
  指定したファイルが、これから処理できる状態かどうかを確認します。
$ echo $?
1

$ bash check_input.sh missing.csv
エラー: ファイルが見つかりません: missing.csv
$ echo $?
2

$ bash check_input.sh secret.csv
エラー: 読み取り権限がありません: secret.csv
$ echo $?
3

$ bash check_input.sh empty.csv
エラー: ファイルが空です: empty.csv
$ echo $?
4

$ bash check_input.sh users.csv
OK: users.csv は処理できます (4行)
$ echo $?
0
```

書式で必ず守る点は次のとおりです。

- エラーメッセージは `エラー: ` (半角コロン+半角スペース)で始め、そのあとに理由、`: `、パスの順で続ける
- 成功メッセージは `OK: ` で始め、`<パス> は処理できます (<行数>行)` と続ける
  (`は処理できます` の前後は半角スペース1つ、括弧は**半角**、行数と `行` の間に空白は入れない)
- エラーメッセージは**標準エラー出力**(`>&2`)、成功メッセージは**標準出力**に出す

> 補足: 採点をroot権限で実行している場合、rootはファイルの権限を無視して読めてしまうため、仕様3のテストは自動的にスキップされます。スキップされても、仕様3のコードは必ず書いてください(一般ユーザーで採点すると判定されます)。

## 5. ヒント

自力で15分考えてから開いてください。

<details>
<summary>ヒント1: 判定の順番はなぜ大事か</summary>

「存在しないファイル」に対して読み取り権限を調べても意味がありません。空かどうかも同じです。つまり**手前の条件が成り立って初めて、次の条件を調べる意味が生まれます。**

```text
引数の個数は正しいか?  → 違えば exit 1
    ↓ OK
ファイルは存在するか?  → 無ければ exit 2
    ↓ OK
読み取り権限はあるか?  → 無ければ exit 3
    ↓ OK
中身は空ではないか?    → 空なら exit 4
    ↓ OK
行数を数えて OK メッセージ → exit 0
```

この形は「関門を1つずつ通過させる」書き方で、**ガード節**と呼ばれます。駄目な場合をその場で `exit` して先に進ませないので、最後まで到達したときには「すべて問題ない」ことが保証されます。ネストの深い `if` の入れ子より読みやすくなります。

</details>

<details>
<summary>ヒント2: 使う文法の具体例</summary>

ファイル判定と、そのときのメッセージの書き方です。

```bash
INPUT_FILE="$1"

if [[ ! -f "$INPUT_FILE" ]]; then
    echo "エラー: ファイルが見つかりません: ${INPUT_FILE}" >&2
    exit 2
fi
```

- `${INPUT_FILE}` の波括弧は無くても動きますが、`${INPUT_FILE}行` のように文字が続く場合に区切りが明確になるため、付ける習慣を付けると安全です
- `>&2` を付けないとエラーが標準出力に出てしまい、`> result.txt` でファイルに保存したときにエラーが画面から消えてしまいます

行数は次のように取得します。

```bash
LINE_COUNT="$(wc -l < "$INPUT_FILE")"
echo "OK: ${INPUT_FILE} は処理できます (${LINE_COUNT}行)"
```

</details>

<details>
<summary>ヒント3: 全体の骨組み</summary>

```bash
#!/bin/bash
set -u

usage() {
    echo "使い方: $(basename "$0") <入力ファイル>"
    echo "  指定したファイルが、これから処理できる状態かどうかを確認します。"
}

# 1. 引数の個数チェック
if [[ "$#" -ne 1 ]]; then
    echo "エラー: 入力ファイルを1つ指定してください。" >&2
    usage >&2
    exit 1
fi

INPUT_FILE="$1"

# 2. 存在チェック( exit 2 )
# 3. 読み取り権限チェック( exit 3 )   ← ヒント: [[ ! -r ... ]]
# 4. 空チェック( exit 4 )             ← ヒント: [[ ! -s ... ]]

# 5. ここまで来たら問題なし
LINE_COUNT="$(wc -l < "$INPUT_FILE")"
echo "OK: ${INPUT_FILE} は処理できます (${LINE_COUNT}行)"
exit 0
```

</details>

## 6. よくあるつまずき

| 症状 | 原因と対処 |
|---|---|
| `[[: not found` や `unexpected operator` と出る | `sh check_input.sh` で実行している。`[[ ]]` はbashの機能なので `bash check_input.sh` で実行する |
| `[[ !-f "$FILE" ]]` でエラーになる | `!` と `-f` の間に半角スペースが必要。`[[ ! -f "$FILE" ]]` と書く |
| 行数が `4 users.csv` のように表示される | `wc -l "$FILE"` と書いている。`wc -l < "$FILE"` に直すと数字だけになる |
| 空ファイルなのに「OK」と出る | `-s` は「サイズが0より大きい」という意味。「空のとき」は `[[ ! -s "$FILE" ]]` と否定形で書く |
| 存在しないファイルなのに終了ステータスが1 | `exit 1` と `exit 2` を書き間違えている。仕様表の番号ともう一度突き合わせる |
| エラーメッセージが `./check.sh 02` の期待と1文字違う | コロンの後の半角スペース、括弧が半角かどうかを確認する。**メッセージは仕様表からコピーするのが確実** |

## 7. 発展課題(採点対象外)

1. ディレクトリを指定されたときに「エラー: ディレクトリが指定されました: <パス>」と表示し、終了ステータス `5` で終わるようにする(`-d` を使う)
2. `-q`(quiet)オプションを付けたときは、成功メッセージを表示せず終了ステータスだけを返すようにする
3. 拡張子が `.csv` でない場合に警告(処理は続行)を標準エラー出力に出す。`case "$INPUT_FILE" in *.csv) ... esac` を使う
