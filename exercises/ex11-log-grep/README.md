## 1. どんな場面で必要になるか

アプリケーションのログは、1日で数万行になることも珍しくありません。人間が毎朝全部読むのは不可能なので、実務では「異常を表す行だけを機械に拾わせる」という方法をとります。

拾い方の中心になるのが `grep` と正規表現(文字列のパターンを表す書き方)です。ところが、素直に `ERROR` を拾うだけだと困ったことが起きます。監視ツール自身が定期的に出す「想定内のERROR」まで毎回引っかかり、担当者が「またいつものやつか」と本物の異常を見逃すようになるのです。これを **アラート疲れ** と呼びます。

そこで実務のスクリプトは、**検知パターン**(拾う条件)と **除外パターン**(捨てる条件)を必ずセットで持ちます。この演習では、その2つを持つログスキャナを自分の手で書きます。案件No.3の `log-watch-alert.sh` も、`ALERT_PATTERN` を `grep -E` に渡して1行ずつ判定するという、まったく同じ考え方で作られています。

## 2. この演習で学ぶこと

| 学ぶこと | ひとことで言うと |
|---|---|
| `grep -E` | 拡張正規表現で検索するモード。`ERROR\|FATAL` のような OR 条件を素直に書ける |
| `grep -v` | 条件に一致した行を「捨てる」オプション。除外パターンで使う |
| パイプ `\|` | 前のコマンドの出力を次のコマンドの入力に渡す仕組み。検知 → 除外を数珠つなぎにする |
| 件数の数え方 | `wc -l` は空文字を1行と数えてしまう。`0件` を正しく出すための定番の対処 |
| 監視系の終了ステータス | 異常を見つけたら `1`、平常なら `0`。呼び出し側が成否を判断するための約束 |
| `getopts` | `-f` `-p` `-e` のようなオプションを解析する仕組み(ex05 の復習) |

### 3分でわかる予備知識

**正規表現とは**

「文字列のパターン」を表す書き方です。`grep -E` を付けると **拡張正規表現(ERE)** というルールで解釈されます。

```bash
grep -E 'ERROR|FATAL' app.log     # ERROR または FATAL を含む行
grep -E '^2026-09-06' app.log     # 行の先頭が 2026-09-06 である行(^ は行頭)
grep -E 'failed$' app.log         # 行の末尾が failed である行($ は行末)
```

`|` は「または」の意味です。`-E` を付けないと `|` がただの文字として扱われてしまうため、この演習では必ず `-E` を付けます。またパターンはシングルクォートで囲みます。囲まないと `|` をシェルがパイプだと勘違いします。

**除外は `-v`**

```bash
grep -Ev 'health-check' app.log   # health-check を含む行「以外」を出す
```

検知と除外は、パイプでつなぐと素直に書けます。

```bash
grep -E 'ERROR|FATAL' app.log | grep -Ev 'health-check'
```

**件数を数えるときの落とし穴**

一致した行を変数に入れてから `wc -l` で数えると、**1件も無いのに「1」になる**ことがあります。

```bash
MATCHED=""                       # 1件も見つからなかった状態
echo "$MATCHED" | wc -l          # → 1  ("空っぽの1行" と数えられてしまう)
```

`echo` が最後に改行を1つ出すため、中身が空でも「1行ある」と見えてしまうのが原因です。対処は簡単で、**数える前に「変数が空かどうか」を確かめる**ことです。

```bash
COUNT=0
if [[ -n "$MATCHED" ]]; then          # -n は「空ではない」
    COUNT="$(printf '%s\n' "$MATCHED" | wc -l)"
fi
```

この演習では、1行ずつ表示しながら `COUNT=$((COUNT + 1))` で数える方法を使ってもかまいません。どちらでも仕様を満たせます。

**監視スクリプトは「異常があったら非0」で終わる**

普通のコマンドは「成功したら0」ですが、監視系のスクリプトは慣習として **異常を検知したら0以外**(この演習では `1`)を返します。理由は、cron や systemd、CI といった **呼び出し側が終了ステータスしか見ていない** からです。

```bash
./scan_log.sh -f app.log || echo "異常あり。担当者に通知する"
```

「スクリプト自体は正常に動いた」ことと「監視対象が正常だった」ことは別物である、と考えると理解しやすくなります。

## 3. 課題

`work/scan_log.sh` を編集し、次の仕様を満たすスクリプトを完成させてください。

### 仕様

| No. | 条件 | 期待する動作 |
|---|---|---|
| 1 | `-f <ログファイル>` を指定しない | `エラー: -f で調べるログファイルを指定してください` を**標準エラー出力**に出し、終了ステータス `1` |
| 2 | `-f` に存在しないファイルを指定 | `エラー: ログファイルが見つかりません: <指定されたパス>` を**標準エラー出力**に出し、終了ステータス `1` |
| 3 | `-h` を指定 | 使い方を**標準出力**に出し、終了ステータス `0` |
| 4 | `-p <検知パターン>` を省略 | 検知パターンの既定値は `ERROR\|FATAL\|CRITICAL` |
| 5 | `-e <除外パターン>` を省略 | 除外はしない(検知した行をすべて出す) |
| 6 | 検知パターンに一致する行がある | 1行ずつ `検知: <行の内容>` の形で**標準出力**に出す |
| 7 | `-e` を指定した | 検知した行から、除外パターンに一致する行を取り除く |
| 8 | 検知処理が終わった | 最後に `検知件数: <件数>件` を**標準出力**に出す |
| 9 | 検知件数が1件以上 | 終了ステータス `1` で終わる |
| 10 | 検知件数が0件 | `検知件数: 0件` を出し、終了ステータス `0` で終わる |

### 実行例 / 出力フォーマット

次のログファイル `app.log` があるとします。

```text
2026-09-06 10:00:01 INFO service started
2026-09-06 10:00:02 DEBUG cache warm up
2026-09-06 10:00:03 ERROR db connection failed
2026-09-06 10:00:04 WARN disk usage 85%
2026-09-06 10:00:05 FATAL out of memory
2026-09-06 10:00:06 INFO retry scheduled
2026-09-06 10:00:07 ERROR health-check dummy probe (テスト用の想定内エラー)
2026-09-06 10:00:08 CRITICAL disk failure detected
```

**既定の検知パターンで実行したとき**

```text
$ ./scan_log.sh -f app.log
検知: 2026-09-06 10:00:03 ERROR db connection failed
検知: 2026-09-06 10:00:05 FATAL out of memory
検知: 2026-09-06 10:00:07 ERROR health-check dummy probe (テスト用の想定内エラー)
検知: 2026-09-06 10:00:08 CRITICAL disk failure detected
検知件数: 4件
$ echo $?
1
```

**除外パターンを指定したとき**

```text
$ ./scan_log.sh -f app.log -e 'health-check'
検知: 2026-09-06 10:00:03 ERROR db connection failed
検知: 2026-09-06 10:00:05 FATAL out of memory
検知: 2026-09-06 10:00:08 CRITICAL disk failure detected
検知件数: 3件
```

**検知パターンを絞ったとき**

```text
$ ./scan_log.sh -f app.log -p 'FATAL'
検知: 2026-09-06 10:00:05 FATAL out of memory
検知件数: 1件
```

**1件も見つからなかったとき**

```text
$ ./scan_log.sh -f app.log -p 'PANIC'
検知件数: 0件
$ echo $?
0
```

書式の決まりは次のとおりです。テストはこの文字列をそのまま見ています。

- 検知した行の書式は `検知: ` (半角コロン+半角スペース) のあとに **ログの行をそのまま** 続ける
- 件数の書式は `検知件数: ` + 数字 + `件`。0件のときも必ず出す (`検知件数: 0件`)
- エラーメッセージは仕様表の文言をそのまま使う。パスは受け取った文字列のまま表示する
- 使い方のメッセージには「使い方」という単語を必ず含める。例:
  `使い方: scan_log.sh -f <ログファイル> [-p <検知パターン>] [-e <除外パターン>] [-h]`

## 5. ヒント

自力で15分考えてから開いてください。段階的に答えに近づくよう3段階に分けています。

<details>
<summary>ヒント1: 処理の流れを整理する</summary>

やることを日本語で並べると、次の5段階になります。

1. `getopts` で `-f` `-p` `-e` `-h` を読み取る(既定値は変数の初期値として先に入れておく)
2. `-f` が空、またはファイルが無ければ、標準エラー出力にエラーを出して `exit 1`
3. `grep -E` で検知パターンに一致する行を取り出す
4. 除外パターンが指定されていれば、そこから `grep -Ev` で取り除く
5. 残った行を1行ずつ `検知: ...` で出しながら数え、最後に件数を出して `exit`

**3と4の結果は変数に入れておく**のがコツです。画面に出すのと数えるのを同時にやろうとすると難しくなります。

</details>

<details>
<summary>ヒント2: 使う文法の具体例</summary>

**コマンドの結果を変数に入れる**

```bash
MATCHED="$(grep -E -- "$PATTERN" "$LOG_FILE")"
```

`--` は「ここから先はオプションではない」という区切りです。パターンが `-` で始まっていてもオプションと誤解されなくなります。

`grep` は1件も見つからないと終了ステータス `1` を返しますが、このスクリプトは `set -e` を使っていないので、そこで止まることはありません。

**変数の中身をコマンドに流し込む**

```bash
MATCHED="$(printf '%s\n' "$MATCHED" | grep -Ev -- "$EXCLUDE_PATTERN")"
```

**変数の中身を1行ずつ処理する**

```bash
while IFS= read -r line; do
    printf '検知: %s\n' "$line"
done <<< "$MATCHED"
```

`<<<` はヒアストリングと呼ばれ、「変数の中身をそのコマンドの標準入力として渡す」書き方です。`IFS= read -r` は「行の前後の空白を削らず、バックスラッシュも文字として扱う」ための定番の組み合わせです。

</details>

<details>
<summary>ヒント3: 全体の骨組み</summary>

```bash
#!/bin/bash
set -u

LOG_FILE=""
PATTERN="ERROR|FATAL|CRITICAL"
EXCLUDE_PATTERN=""

usage() {
    echo "使い方: $(basename "$0") -f <ログファイル> [-p <検知パターン>] [-e <除外パターン>] [-h]"
}

while getopts "f:p:e:h" opt; do
    case "$opt" in
        f)  LOG_FILE="$OPTARG" ;;
        # p) と e) もここに書く
        h)  usage; exit 0 ;;
        \?) usage >&2; exit 1 ;;
    esac
done

# -f の未指定チェックと、ファイルの存在チェック([[ -f "$LOG_FILE" ]])

MATCHED="$(grep -E -- "$PATTERN" "$LOG_FILE")"
# 除外パターンがあれば、ここで MATCHED を絞り込む

COUNT=0
if [[ -n "$MATCHED" ]]; then
    while IFS= read -r line; do
        # 「検知: 行」を出して COUNT を1増やす
        :
    done <<< "$MATCHED"
fi

printf '検知件数: %d件\n' "$COUNT"
# 件数が1件以上なら exit 1、0件なら exit 0
```

</details>

## 6. よくあるつまずき

| 症状 | 原因と対処 |
|---|---|
| `grep: FATAL: No such file or directory` と出る | パターンとファイル名の順番が逆になっている。`grep -E <パターン> <ファイル>` の順に書く |
| `ERROR\|FATAL` で何も引っかからない | `-E` を付け忘れている。`-E` が無いと `\|` はただの文字として扱われる |
| `bash: FATAL: command not found` と出る | パターンをクォートしていない。`'ERROR\|FATAL'` のようにシングルクォートで囲む |
| 1件も無いのに `検知件数: 1件` になる | 空の変数を `wc -l` で数えている。`[[ -n "$MATCHED" ]]` で空かどうかを先に確かめる |
| 検知しているのに終了ステータスが0 | 最後の `exit` を書き忘れている。`検知件数` を出したあとに件数で分岐して `exit 1` / `exit 0` |
| 除外したはずの行が残る | `-v` を付け忘れているか、`grep -Ev` に渡す入力を間違えている。`echo "$MATCHED" \| grep -Ev ...` の形を確認する |

`./check.sh 11` が失敗したときは、**「期待」と「実際」の差分**を必ず読んでください。どこがどう違うかがそのまま書かれています。

## 7. 発展課題(採点対象外)

余裕がある人向けの追加課題です。実務では「もう一歩の気配り」が評価されます。

1. `-p` と `-e` を複数回指定できるようにする(配列に貯めて `|` でつなぐ)
2. 検知した行を重要度別に数え、`ERROR: 2件 / FATAL: 1件` のような内訳も表示する
3. `-n <件数>` で「最新の何件だけ表示するか」を指定できるようにする(`tail -n` を使う)
