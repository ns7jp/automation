## 1. どんな場面で必要になるか

社内の受注管理システムが `/var/log/app/error.log` にエラーを書き出しています。運用担当のあなたは「5分ごとにログを見て、新しいエラーが出ていたら気づく」仕組みを cron (指定した時刻にコマンドを自動実行する仕組み) で作ることになりました。

ここで素直に「毎回ログ全部を読む」と書くと、5分後にはまた同じエラーを見つけてしまいます。**同じ1件のエラーで、1日に288通の通知が飛ぶ**という笑えない事故になります。かといって「最後の10行だけ見る」では、5分間に20行出たときに10行を取りこぼします。

正しい答えは「**前回どこまで読んだかを覚えておいて、その続きから読む**」です。この「どこまで読んだか」を記録した小さなファイルを **状態ファイル** と呼びます。cron で定期実行するタイプの監視スクリプトでは、ほぼ必ずこの形になります。

案件No.3 の `log-watch-alert.sh` は `tail -F` で常駐する方式ですが、常駐プロセスを立てられない環境 (共用サーバーなど) では、この演習で作る「cron + 状態ファイル」方式を使います。どちらも「同じ行を二度処理しない」ための工夫であることは共通しています。

## 2. この演習で学ぶこと

| 学ぶこと | ひとことで言うと |
|---|---|
| 状態ファイル | 前回の実行結果を次回に引き継ぐための小さなファイル |
| `wc -l < ファイル` | ファイルの行数を数える。`<` を使うとファイル名が出力に混ざらない |
| `tail -n +N` | 「N行目から最後まで」を取り出す。`-n 10` (末尾10行) とは意味が違う |
| ローテート検知 | 行数が減っていたら「別のファイルに入れ替わった」と判断する |
| 更新のタイミング | 処理し終えてから状態ファイルを書き換える |
| 常駐との使い分け | `tail -F` の常駐方式と、cron + 状態ファイル方式の違い |

### 3分でわかる予備知識

**行数を数える**

```bash
wc -l app.log        # → 3 app.log      ファイル名まで出てしまう
wc -l < app.log      # → 3              数字だけが得られる
```

`<` は「ファイルの中身を、コマンドの標準入力に流し込む」という記号です。`wc` は自分が読んでいるファイルの名前を知らないので、数字だけを出します。**計算に使いたいときは必ず `<` の形**を使ってください。

**tail の `+` 付き指定**

```bash
tail -n 2 app.log     # 末尾から2行
tail -n +2 app.log    # 2行目から最後まで(先頭1行を飛ばす)
tail -n +1 app.log    # 1行目から最後まで = ファイル全体
```

`+` が付くかどうかで意味が正反対になります。この演習では「4行目から最後まで」のように **読み始める行番号** を指定したいので、`+` 付きを使います。`+1` が先頭であって、`+0` ではないことに注意してください。

**前回の行数から、読み始める行番号を求める**

```bash
LAST_LINE=3                      # 前回までに3行処理した
START=$((LAST_LINE + 1))         # → 4。つまり4行目から読めばよい
tail -n "+${START}" app.log      # 4行目から最後まで
```

`$(( ))` は算術式 (計算) の書き方です。`$((3 + 1))` は `4` になります。

**1行ずつ処理する**

```bash
while IFS= read -r line; do
    echo "新規行: ${line}"
done < <(tail -n "+${START}" app.log)
```

`while read` は「1行読んでは処理する」の繰り返しです。`IFS=` は行頭・行末の空白を削らないため、`-r` はバックスラッシュをそのまま扱うためのおまじないで、この2つはセットで書くと覚えてください。`< <(コマンド)` はプロセス置換といい、**コマンドの出力をファイルのように読み込む**書き方です。

**なぜローテート検知が必要か**

ログファイルは肥大化を防ぐため、定期的に中身を退避して空にする **ログローテート** が行われます (`logrotate` という仕組みが有名です)。10000行まで処理した記録が残っている状態でローテートされ、ファイルが50行に戻ったとします。このとき何も考えずに `tail -n +10001` すると、**新しい50行を永久に読み落とします**。

そこで「今の行数 < 前回記録した行数」なら、ローテートが起きたとみなして先頭から読み直します。行数が減ることは通常あり得ないので、この単純な比較で十分実用になります。

## 3. 課題

`work/read_new_lines.sh` を編集し、次の仕様を満たすスクリプトを完成させてください。

指定したログファイルを読み、**前回の実行以降に増えた行だけ**を表示します。どこまで読んだかは、ログファイルと同じ場所に置いた状態ファイルに記録します。

### 仕様

| No. | 条件 | 期待する動作 |
|---|---|---|
| 1 | 引数を1つ(ログファイル)付けて実行 | 新規行を表示し、状態ファイルを更新して終了ステータス `0` で終わる |
| 2 | 引数が0個または2個以上 | `エラー: ログファイルを1つ指定してください。` と使い方を**標準エラー出力**に表示し、`1` で終わる |
| 3 | 指定したログファイルが存在しない | `エラー: ログファイルが見つかりません: <指定されたパス>` を**標準エラー出力**に表示し、`1` で終わる |
| 4 | 状態ファイルが無い | 「0行目まで処理済み」とみなし、**全行**を新規として扱う |
| 5 | 現在の行数が状態ファイルの値より**少ない** | `ログがローテートされたため先頭から読み直します` を**標準出力**に表示してから、**全行**を新規として扱う |
| 6 | 新規行がある | 1行ずつ `新規行: <行の内容>` の形式で標準出力に表示する |
| 7 | 処理の最後 | `新規: <件数>行 (総行数: <総行数>行)` を表示し、状態ファイルを現在の総行数で更新して `0` で終わる |
| 8 | 新規行が0行 | 新規行は1行も表示しないが、仕様7のまとめ行は表示し、`0` で終わる |

### 状態ファイル

- 置き場所と名前は **`<ログファイルのパス>.offset`** です。`app.log` を指定したなら `app.log.offset` になります。
- 中身は **処理済みの行数を表す数字だけ** を1行書きます (`3` のように書き、`lines=3` などとは書かない)。

### 実行例 / 出力フォーマット

`app.log` が次の3行だとします。

```text
2026-09-06 10:00:00 INFO サービスを起動しました
2026-09-06 10:00:05 WARN ディスク使用率 82%
2026-09-06 10:00:09 ERROR データベースに接続できません
```

**1回目 (状態ファイルが無いので全行が新規)**

```text
$ bash read_new_lines.sh app.log
新規行: 2026-09-06 10:00:00 INFO サービスを起動しました
新規行: 2026-09-06 10:00:05 WARN ディスク使用率 82%
新規行: 2026-09-06 10:00:09 ERROR データベースに接続できません
新規: 3行 (総行数: 3行)
```

このとき `app.log.offset` の中身は `3` になります。

**2回目 (2行追記してから実行。増えた2行だけが出る)**

```text
$ bash read_new_lines.sh app.log
新規行: 2026-09-06 10:05:00 INFO 再接続に成功しました
新規行: 2026-09-06 10:05:30 ERROR タイムアウトが発生しました
新規: 2行 (総行数: 5行)
```

`app.log.offset` の中身は `5` に更新されます。

**3回目 (ログが増えていない)**

```text
$ bash read_new_lines.sh app.log
新規: 0行 (総行数: 5行)
```

**4回目 (ログをローテートして1行だけの状態にしてから実行)**

```text
$ bash read_new_lines.sh app.log
ログがローテートされたため先頭から読み直します
新規行: 2026-09-06 11:00:00 INFO ログをローテートしました
新規: 1行 (総行数: 1行)
```

**異常系**

```text
$ bash read_new_lines.sh
エラー: ログファイルを1つ指定してください。
使い方: read_new_lines.sh <ログファイル>
  前回の続きから、増えた行だけを読み取って表示します。
$ echo $?
1
```

```text
$ bash read_new_lines.sh /var/log/nothing.log
エラー: ログファイルが見つかりません: /var/log/nothing.log
$ echo $?
1
```

書式で注意する点は次のとおりです。すべて**半角**で書いてください。

- 新規行の行頭ラベルは `新規行: ` (コロンのあとに半角スペース1つ)
- まとめ行は `新規: 2行 (総行数: 5行)` (`行` の後ろに半角スペース1つ、括弧は半角、括弧内のコロンのあとにも半角スペース1つ)
- ローテートのメッセージは `ログがローテートされたため先頭から読み直します` (前後に記号を付けない)

## 5. ヒント

自力で20分考えてから開いてください。段階的に答えに近づくよう3段階に分けています。

<details>
<summary>ヒント1: 何を覚えておけばよいか</summary>

覚えておきたいのは「前回までに何行処理したか」という**数字1つ**だけです。この数字さえあれば、次回は「その次の行」から読めばよいことになります。

処理の流れを日本語で書き出すと、次の5ステップになります。

1. 状態ファイルから前回の行数を読む (無ければ 0)
2. 今のファイルの行数を数える
3. 「今の行数 < 前回の行数」ならローテートされたので、前回の行数を 0 に戻す
4. 「前回の行数 + 1」行目から最後までを表示する
5. 状態ファイルを「今の行数」で上書きする

**5を最後にやる**のが大事です。先に状態ファイルを更新してしまうと、途中で失敗したときに未処理の行が読み飛ばされてしまいます。

</details>

<details>
<summary>ヒント2: 使う文法の具体例</summary>

状態ファイルの読み書きは `cat` と リダイレクト でできます。

```bash
STATE_FILE="${LOG_FILE}.offset"        # 変数のうしろに文字列をつなげるだけ

LAST_LINE=0
if [[ -f "$STATE_FILE" ]]; then        # -f は「通常ファイルとして存在する」
    LAST_LINE="$(cat "$STATE_FILE")"
fi

printf '%s\n' "$TOTAL_LINES" > "$STATE_FILE"   # > は上書き。>> (追記) ではない
```

行数の比較と、読み始める位置の計算は次のとおりです。

```bash
TOTAL_LINES="$(wc -l < "$LOG_FILE")"

if [[ "$TOTAL_LINES" -lt "$LAST_LINE" ]]; then     # -lt は「より小さい」
    echo "ログがローテートされたため先頭から読み直します"
    LAST_LINE=0
fi

NEW_COUNT=$((TOTAL_LINES - LAST_LINE))
START=$((LAST_LINE + 1))
```

</details>

<details>
<summary>ヒント3: 全体の骨組み</summary>

```bash
#!/bin/bash
set -u

usage() {
    echo "使い方: $(basename "$0") <ログファイル>"
    echo "  前回の続きから、増えた行だけを読み取って表示します。"
}

# 1. 引数チェック($# が 1 でなければエラー)
# 2. ログファイルの存在チェック([[ ! -f "$LOG_FILE" ]])

LOG_FILE="$1"
STATE_FILE="${LOG_FILE}.offset"

# 3. 前回の行数を読む(LAST_LINE)
# 4. 今の行数を数える(TOTAL_LINES)
# 5. ローテート判定

NEW_COUNT=$((TOTAL_LINES - LAST_LINE))

if [[ "$NEW_COUNT" -gt 0 ]]; then
    while IFS= read -r line; do
        echo "新規行: ${line}"
    done < <(tail -n "+$((LAST_LINE + 1))" "$LOG_FILE")
fi

echo "新規: ${NEW_COUNT}行 (総行数: ${TOTAL_LINES}行)"

# 6. 状態ファイルを更新して exit 0
```

</details>

## 6. よくあるつまずき

| 症状 | 原因と対処 |
|---|---|
| 2回目も1行目から全部出てしまう | 状態ファイルを書いていない、または `>` ではなく別の場所に書いている。`cat app.log.offset` で中身を確認する |
| `tail: invalid number of lines: '+'` と出る | `tail -n "+${START}"` の `START` が空。`wc -l` の結果を変数に入れ忘れていないか確認する |
| 毎回1行多く/少なく出る | `+` の意味の取り違え。`tail -n +1` が先頭から、`tail -n +4` は4行目からで、`+0` は使わない |
| 数字を比べたり計算したりすると `syntax error: invalid arithmetic operator` (`[ ]` を使った場合は `integer expression expected`) と出る | `wc -l app.log` のようにファイル名付きで数えていて、変数に `3 app.log` という文字列が入っている。`wc -l < app.log` に直す |
| 最終行が読み飛ばされる | ログの最終行が改行で終わっていない。`wc -l` は改行の数を数えるため、この場合1行少なく数える。テスト用のログは `printf 'a\nb\n'` のように改行で終わらせる |
| ローテートしたのに何も出ない | 行数が減ったときに `LAST_LINE` を 0 に戻していない。メッセージを出すだけでは不十分 |

`./check.sh 13` が失敗したときは、**「期待」と「実際」の差分**を必ず読んでください。どこがどう違うかがそのまま書かれています。

## 7. 発展課題(採点対象外)

余裕がある人向けの追加課題です。実務では「もう一歩の気配り」が評価されます。

1. 状態ファイルの中身が数字でなかった場合 (人が手で書き換えた、途中で壊れた) に 0 として扱い、警告を表示する
2. 状態ファイルの置き場所を `-s <パス>` オプションで変更できるようにする (ログの置き場所が読み取り専用のときに必要になる)
3. 行数ではなく **バイト位置** (`wc -c` と `tail -c +N`) で覚える方式に書き換え、行数方式との得失を README にまとめる

## 8. この演習と案件のつながり

案件No.3 は `tail -F` でログを常時見張る「常駐方式」ですが、この演習の「cron + 状態ファイル方式」は、その代替として実務で頻繁に使われます。

- 「前回の実行結果をファイルに残して次回に引き継ぐ」という状態ファイルの使い方 → [`log-watch-alert.sh`](../../projects/03-log-monitoring-alert/src/log-watch-alert.sh) の `STATE_FILE` (案件では読んだ位置ではなく、直近通知時刻と抑制件数を保存している)
- 状態ファイルを置くディレクトリを設定値として外に出す考え方 → 同案件の `STATE_DIR`
- 常駐方式では `tail -F` がプロセスの中で読み進む位置を覚えているため、状態ファイルが不要です。裏を返すと、**プロセスが死ぬと位置を忘れる**ため、再起動時の取りこぼしが起きます。この演習の方式にはその弱点がありません
- ex12 で作った通知の抑止と組み合わせると、「差分だけを読み、通知しすぎない」監視スクリプトになります
