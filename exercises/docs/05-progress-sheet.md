# 学習記録シート

演習を進めながら「詰まったこと」を書き残し、それを**面接で話せるエピソード**に変えるためのシートです。このファイルはテンプレートなので、自分用にコピーして書き込みながら使ってください。

チェックリスト・振り返りテンプレート・面接エピソード変換シート・修了時のセルフチェックの4つが入っています。

---

## 1. なぜ記録を残すのか

未経験からの転職活動で最も効くのは、「何を作ったか」ではなく**「何に詰まって、どう解決したか」**です。作ったものは誰でも似たような説明になりますが、詰まった経験だけは自分にしかない具体性を持っています。

そして、その具体性は**驚くほど早く忘れます**。「3時間かけて解決したのに、1週間後には何で詰まったか思い出せない」ということが普通に起きます。だから、合格した直後の3分で書き残します。

```mermaid
flowchart LR
    A["演習で詰まる<br/>手が止まる"] --> B["記録する<br/>症状・原因・調べ方"]
    B --> C["ステージごとに振り返る<br/>点を線にする"]
    C --> D["エピソードに変換する<br/>状況→課題→やったこと→結果→学び"]
    D --> E["面接で語れる<br/>60秒の具体的な話"]

    style B fill:#e8f4ea,stroke:#4a7c59
    style D fill:#fff4e0,stroke:#b8860b
    style E fill:#fde8e8,stroke:#b03a3a
```

記録があるかないかで、面接での答え方はここまで変わります。

| 質問 | 記録がないときの答え | 記録があるときの答え |
|---|---|---|
| 「Bashは書けますか?」 | 「基本的なスクリプトなら書けます」 | 「CSVを1行ずつ読んでユーザーを作るスクリプトを書きました。パイプで `while` に渡すとサブシェルになって件数カウンタが0のままになる問題に詰まり、`bash -x` で切り分けてリダイレクトに書き換えました」 |
| 「一番苦労した点は?」 | 「エラーの解決に時間がかかりました」 | 「古いバックアップを削除する処理で、消してはいけないファイルまで対象に入っていました。対象を `backup_*.tar.gz` に絞り込み、ドライランで確認してから実行する形にしました」 |
| 「学んだことは?」 | 「シェルスクリプトの書き方です」 | 「削除処理は『何を消すか』より『何を消さないか』を先に決める、ということです」 |

右の列は、特別な経験をした人の答えではありません。**記録を残した人の答え**です。

## 2. 使い方

### 2.1 自分用にコピーする

このファイルはテンプレートです。編集するのはコピーしたほうだけにしてください。

```bash
# 演習ディレクトリで実行する
$ cd automation/exercises
$ cp docs/05-progress-sheet.md my-progress.md
$ ls -l my-progress.md
```

```text
# 実行結果イメージ
-rw-r--r-- 1 user user 18234 Apr  1 10:00 my-progress.md
```

あとは `my-progress.md` をエディタで開き、チェックボックスと表を埋めていきます。

```bash
$ nano my-progress.md
```

### 2.2 個人の記録はコミットしない

`my-progress.md` には、自分の弱点や試行錯誤の生ログが入ります。このリポジトリは**ポートフォリオとして採用担当者に読まれる前提**なので、下書きは分けておきましょう。

方法は2つあります。どちらでも構いません。

```bash
# 方法1: Gitの管理対象から外す(リポジトリのルートで実行する)
$ cd automation
$ echo "exercises/my-progress.md" >> .gitignore
$ git status --short
```

```text
# 実行結果イメージ(my-progress.md が一覧に出てこなければ成功)
?? .gitignore
```

```bash
# 方法2: リポジトリの外に置く(ホームディレクトリなど)
$ cp docs/05-progress-sheet.md ~/my-progress.md
```

**記録そのものは公開しなくて構いません。** 公開するのは、記録から作った「面接エピソード」と、案件パックのドキュメントです。

### 2.3 いつ書くか

書くタイミングを決めておかないと続きません。次の4回だけで十分です。

| タイミング | 書くもの | 目安 |
|---|---|---|
| 演習に合格した直後 | 進捗チェックリストの1行 + [4章](#4-1演習ごとの振り返りテンプレート)の振り返り | 3分 |
| ステージを終えたとき | [5章](#5-ステージごとの振り返りテンプレート)のステージ振り返り | 10分 |
| 全21演習を終えたとき | [6章](#6-面接エピソード変換シート)のエピソードを3本 + [7章](#7-修了時のセルフチェック)のセルフチェック | 45分 |
| 応募書類を書くとき | エピソードの見直し(古くなった表現を直す) | 15分 |

**合格した直後の3分が最も重要です。** 詰まった内容は、翌日にはもう「なんとなく大変だった」に変わってしまいます。

## 4. 1演習ごとの振り返りテンプレート

合格した直後に、下のテンプレートをコピーして埋めます。**5項目・3分**です。長く書く必要はありません。

```markdown
### exNN: 演習タイトル

- 合格日 / 所要時間:
- 詰まったこと:
- 原因:
- どう調べたか:
- 学んだこと(1行):
- 実務で使えそうな場面:
```

各項目の狙いは次のとおりです。

| 項目 | 何を書くか | なぜ書くか |
|---|---|---|
| 詰まったこと | 出たエラーメッセージや、期待と違った出力を**そのまま** | 面接で「具体的に何が起きたか」を語る材料になる |
| 原因 | 分かった原因を1文で | 同じ原因は必ずまた出る。2回目は数分で解決できる |
| どう調べたか | `bash -x` / README / man / 検索した語句 | 「自力で解決する手順を持っているか」は必ず見られる |
| 学んだこと | 1行だけ。次に活かせる形で | 長く書くと読み返さない。1行なら読み返せる |
| 実務で使えそうな場面 | 運用のどんな場面で効くか | 「学んだ」で終わらせず「使える」に変える |

**詰まらずに合格した演習は、「詰まったこと: なし」と1行書くだけで十分です。** 全部を丁寧に書こうとすると続きません。

### 記入例

実際に書くとこうなります。

```markdown
### ex03: CSVを1行ずつ処理する

- 合格日 / 所要時間: 4/12 / 80分(目安50分)
- 詰まったこと: 1行ずつの出力は正しいのに、最後のサマリだけ
  「合計: 0件 (スキップ: 0件)」になり、テストが落ちた。
- 原因: `cat users.csv | while read ...` と書いていた。パイプの右側は
  別プロセス(サブシェル)で動くため、ループの中で増やしたカウンタが
  ループを抜けると元に戻っていた。
- どう調べたか: `bash -x` で追いかけたら、ループ内では count=1,2,3 と
  増えているのに、done の直後の echo では 0 に戻っていた。
  「bash while パイプ 変数 消える」で検索してサブシェルの話にたどり着いた。
- 学んだこと(1行): パイプの右側は別プロセスなので、そこで変えた変数は外に残らない。
- 実務で使えそうな場面: ログを1行ずつ数えて「エラー何件」と集計するスクリプト。
  件数がいつも0になる、という不具合はこれが原因のことが多い。
```

## 5. ステージごとの振り返りテンプレート

ステージを終えたら、対応する案件のREADMEを読む**前**に10分だけ振り返ります。演習1件ごとの点を、ステージという線につなぐ作業です。

```markdown
## ステージN: ステージ名 の振り返り

- 期間 / 合計時間:
- このステージで一番学びが大きかったこと:
- まだ自信がないこと(説明できない・見ないと書けないこと):
- 案件パックのどこにつながったか:
- 次のステージに入る前にやること:
```

### 卒業条件のセルフ判定

各ステージには「ここまで来ていれば次に進んでよい」という自己判定の目安があります([01-design.md](01-design.md) の設計と同じ基準です)。

| ステージ | 卒業条件(自己判定) |
|---|---|
| 1. Bashの基礎体力 | ex06(ユーザー一括作成ミニ版)を、解答例を見ずに書ける |
| 2. バックアップと定期実行 | 世代管理の必要性とドライランの価値を、自分の言葉で説明できる |
| 3. ログ監視と常駐化 | 状態ファイルが必要な理由を説明できる |
| 4. 死活監視と状態管理 | 「1回の失敗で即通知」がなぜ良くないかを説明できる |
| 5. IaC(Ansible) | べき等性(=何度実行しても結果が同じになる性質)を具体例で説明できる |
| 6. CI/CD | Secrets(=パスワードや鍵をコードに書かずに渡す仕組み)を使う理由を説明できる |

**「まだ自信がないこと」に書いた項目こそが、次に読むべき案件ドキュメントの入口です。** 空欄のまま先に進まないでください。

### 案件パックへの橋渡し

ステージを終えたら、対応する案件を読みます。演習で書いた部品が、実際のスクリプトの中でどう組み合わさっているかを確認する時間です。

```bash
# 例: ステージ1(ex01-ex06)が終わったら
$ cat ../projects/01-user-account-automation/README.md
$ cat ../projects/01-user-account-automation/src/create_users.sh
```

読みながら「これは ex03 でやったループだ」「この判定は ex02 と同じだ」と紐づけられれば、そのステージは身についています。

## 6. 面接エピソード変換シート

### 6.1 変換の型

記録をそのまま話しても伝わりません。**話す順番**を決めておくと、緊張していても崩れずに話せます。使う型は5段階です(採用面接でよく使われる STAR 法に「学び」を足した形です)。

| 段階 | 話すこと | 分量の目安 |
|---|---|---|
| 状況 (Situation) | 何をしようとしていたか。前提を1文で | 1文 |
| 課題 (Task) | 何が問題だったか。**具体的な症状**で言う | 1〜2文 |
| やったこと (Action) | どう調べ、どう直したか。**判断の理由**まで | 2〜3文 |
| 結果 (Result) | どうなったか。数字を入れられれば入れる | 1文 |
| 学び (Learning) | 次に活かせる形にした一般化 | 1文 |

**最も評価されるのは「やったこと」と「学び」です。** 「エラーが出たので直しました」ではなく「なぜその直し方を選んだか」を話せると、実務でも同じ判断ができる人だと伝わります。

### 6.2 記入テンプレート

```markdown
## エピソードN: タイトル(元にした演習: exNN)

- 状況:
- 課題:
- やったこと:
- 結果:
- 学び:
- 60秒で話すときの言い方:
```

### 6.3 記入例(完成形)

ex08「世代管理(古い世代の削除)」の記録から作った例です。

```markdown
## エピソード1: 削除処理は「何を消さないか」から決める(元にした演習: ex08)

- 状況: 古いバックアップでディスクが埋まらないよう、保存ディレクトリから
  指定した世代数より古いファイルを削除するスクリプトを書いていた。
- 課題: 最初は「更新日時が古い順に並べて、残す数より後ろを消す」とだけ考えて
  実装したところ、同じディレクトリにあった別のファイルまで削除対象に
  入ってしまった。バックアップ以外のファイルが消える作りになっていた。
- やったこと: 削除対象を backup_*.tar.gz というパターンに限定し、
  それ以外は絶対に触らないようにした。さらに -n (ドライラン)オプションを付け、
  実行前に「[dry-run] 削除します: <ファイル名>」と対象一覧だけを表示して
  目視確認できるようにした。本番実行はドライランで確認してから、という手順にした。
- 結果: 保持3世代の指定で、5個あるバックアップのうち古い2個だけが削除され、
  同じディレクトリの他のファイルは残ることを確認できた。
  ドライランでは1件も削除されないことも確認した。
- 学び: 削除処理は「何を消すか」ではなく「何を消さないか」を先に決める必要がある。
  対象を絞り込まないと、変数が空だったときに関係ないファイルまで消える事故になる。
  だから運用では、本番実行の前に必ずドライランで対象を確認する。
- 60秒で話すときの言い方: 下記の引用を参照
```

面接で話すときは、次のように地の文でつなぎます。

> 「バックアップの世代管理を作ったときに、削除対象の絞り込みが甘くて、バックアップ以外のファイルまで消える作りになっていたことがあります。テストで気づいたのですが、そこで『何を消すか』ではなく『何を消さないか』を先に決めるべきだと考え直しました。対象を `backup_*.tar.gz` に限定した上で、ドライランのオプションを用意して、実行前に消える対象の一覧だけを表示できるようにしています。削除や上書きを伴う処理では、実行前に対象を目で確認できることが事故を防ぐと考えていて、それ以降に書いたスクリプトにも同じ仕組みを入れています。」

### 6.4 エピソードは3本用意する

面接では聞かれ方が変わるので、性質の違う3本を用意しておくと対応できます。

| 種類 | 何を示すか | 元にしやすい演習 |
|---|---|---|
| 事故を防いだ話 | 安全意識・運用の想像力 | ex05(ドライラン) / ex08(世代管理) / ex02(入力チェック) |
| 原因を切り分けた話 | デバッグ力・自力で解決する力 | ex03(サブシェル) / ex13(差分処理) / ex11(正規表現) |
| 設計を選んだ話 | 技術選定の理由を語れるか | ex10 と ex14(cronとsystemdの使い分け) / ex16(しきい値設計) / ex19(べき等性) |

**3本とも同じ演習から作らないでください。** 学習の幅が伝わりません。

作ったエピソードは、[../../docs/01-portfolio-guide.md](../../docs/01-portfolio-guide.md)(ポートフォリオ活用ガイド)の想定質問と突き合わせておくと、本番で使う場所が決まります。

## 7. 修了時のセルフチェック

全21演習に合格したら、**説明できるか**を確認します。合格したかどうかではなく、人に説明できるかどうかが到達点です。

声に出して30秒で説明してみてください。詰まった項目は、括弧内の演習の README と `answer/` を読み返します。

- [ ] なぜドライラン(dry-run)を用意するのか (ex05 / ex08)
- [ ] べき等性とは何か。具体例を1つ挙げて説明できるか (ex06 / ex19)
- [ ] 「1回の失敗で即通知」がなぜ良くないのか (ex16)
