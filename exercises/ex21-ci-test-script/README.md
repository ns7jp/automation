## 1. どんな場面で必要になるか

ex20で書いたワークフローには、次の1行がありました。

```yaml
      - name: テストを実行する
        run: bash scripts/test.sh
```

この `scripts/test.sh` の中身を、今回自分で書きます。ここが**「配布してよいか」を判断する関所**です。ここが常に成功を返すだけの空っぽのスクリプトなら、CI/CDの仕組みを組んでも壊れたものがそのまま本番へ流れていきます。

小さな会社の現場では、いきなり本格的なテストフレームワークを入れられないことがよくあります。それでも「必須ファイルがある」「スクリプトが文法的に壊れていない」「HTMLに `<title>` がある」くらいなら、シェルスクリプトと `grep` だけで確かめられます。**完璧なテストより、毎回必ず動く最低限のテストのほうが事故を防ぎます。**

この演習は演習パックの最後です。ex01の終了ステータス、ex02の入力チェック、ex04のログ関数と件数の集計、ex05のグロブの扱いといった、これまでの積み重ねをひとつのスクリプトにまとめます。完成したものは、案件No.6の [`scripts/test.sh`](../../projects/06-cicd-pipeline/src/scripts/test.sh) とほぼ同じ役割を果たします。

## 2. この演習で学ぶこと

| 学ぶこと | ひとことで言うと |
|---|---|
| テストの関数化 | `pass` / `fail` / `skip_test` にまとめ、表示と集計を1か所で行う |
| 件数の集計 | `COUNT=$((COUNT + 1))` で数を増やし、最後にまとめて報告する |
| `command -v` | そのコマンドが使える環境かどうかを調べる |
| スキップと失敗の区別 | 「壊れている」と「確かめられなかった」は別物として記録する |
| 終了ステータスによる通知 | CIは画面の文字ではなく `exit` の値だけを見て緑と赤を決める |
| `set -e` を使わない判断 | 1件目で止めず、失敗を全部集めてから報告するため |

### 3分でわかる予備知識

**引数の既定値**

```bash
PROJECT_DIR="${1:-.}"     # $1 があればその値、無ければ "." (カレントディレクトリ)
```

`${変数:-既定値}` は「変数が空か未定義なら既定値を使う」という書き方です。CIからは引数なしで呼ばれることが多いので、既定値を用意しておくとそのまま使えます。

**結果表示と集計を関数にまとめる**

```bash
PASS_COUNT=0

pass() {
    echo "[PASS] $1"
    PASS_COUNT=$((PASS_COUNT + 1))     # 数を1つ増やす
}
```

こうしておくと、テストを何個増やしても数え漏れが起きません。表示の書式を直したくなったときも、この関数だけを直せば済みます。

**`set -e` を付けない理由**

`set -e` は「コマンドが失敗したら即座に終了する」オプションです。便利ですが、テストスクリプトでは**あえて付けません**。1件目の失敗で止まってしまうと、他にも壊れている箇所があるかどうかが分からず、直しては再実行、を何度も繰り返すことになるからです。失敗しても最後まで走らせ、まとめて報告するほうが早く直せます。

**`command -v` でコマンドの有無を調べる**

```bash
if command -v shellcheck > /dev/null 2>&1; then
    echo "shellcheck が使えます"
else
    echo "shellcheck がありません"
fi
```

`command -v` は、そのコマンドが使えれば終了ステータス0を返します。`> /dev/null 2>&1` は「標準出力も標準エラー出力も捨てる」という意味で、判定だけしたいときの定番です。

**スキップは失敗ではない**

道具が入っていない環境で「失敗」にしてしまうと、手元では常に赤いままになり、やがて誰も結果を見なくなります。それは「テストが無い」のと同じです。**確かめられなかったものは、正直に「スキップ」として記録します。**

**`bash -n` と `grep -q`**

```bash
bash -n script.sh          # 実行せずに文法だけ確かめる。壊れていれば0以外を返す
grep -qi "<title>" a.html  # 見つかれば0を返す。-q は画面に出さない、-i は大文字小文字を無視
```

**グロブが一致しないときの用心**

```bash
for f in "${PROJECT_DIR}"/scripts/*.sh; do
    [[ -f "$f" ]] || continue      # 実在するファイルだけを処理する
    ...
done
```

`*.sh` に一致するファイルが1つも無いと、シェルはパターンの文字列(`scripts/*.sh`)をそのままループに渡してきます。実在チェックを1行入れておけば、この落とし穴を避けられます。

## 3. 課題

`work/ci_test.sh` を編集し、次の仕様を満たすスクリプトを完成させてください。

### 仕様

| No. | 条件 | 期待する動作 |
|---|---|---|
| 1 | 引数にプロジェクトディレクトリを指定 | そのディレクトリを検査する |
| 2 | 引数を省略 | カレントディレクトリ(`.`)を検査する |
| 3 | 指定したディレクトリが存在しない | 標準エラー出力にエラーを出し、終了ステータス `1` で終わる |
| 4 | T1 必須ファイル | `app/index.html` と `scripts/deploy.sh` が両方あれば `[PASS]`、1つでも無ければ `[FAIL]` |
| 5 | T2 構文チェック | `scripts/` 配下のすべての `.sh` が `bash -n` を通れば `[PASS]`、1つでも落ちれば `[FAIL]` |
| 6 | T3 HTMLの中身 | `app/index.html` に `<title>` があれば `[PASS]`、無ければ `[FAIL]` |
| 7 | T4 シバン | `scripts/` 配下のすべての `.sh` の1行目が `#!/bin/bash` なら `[PASS]`、違えば `[FAIL]` |
| 8 | T5 静的解析(shellcheckがある環境) | `shellcheck scripts/*.sh` が成功すれば `[PASS]`、失敗すれば `[FAIL]` |
| 9 | T5 静的解析(shellcheckが無い環境) | `[SKIP]` として記録する。**失敗にはしない** |
| 10 | 最後の集計 | 成功・失敗・スキップの件数を1行で表示する |
| 11 | 失敗が1件以上 | 終了ステータス `1` で終わる |
| 12 | 失敗が0件 | 終了ステータス `0` で終わる |

### 出力フォーマット

各テストの結果は、次の**1行**で表示します。

```text
[PASS] T1: 必須ファイルが存在する
[PASS] T2: scripts配下のシェルスクリプトに構文エラーが無い
[PASS] T3: app/index.html に <title> タグがある
[PASS] T4: scripts配下のシェルスクリプトの1行目が #!/bin/bash である
[PASS] T5: shellcheck の警告が無い
テスト結果: 5件成功 / 0件失敗 / 0件スキップ
```

- 先頭は `[PASS]` `[FAIL]` `[SKIP]` のいずれか。**半角の角括弧**で囲み、直後に**半角スペース1つ**
- 続けて `T1: ` のようにテスト番号と半角コロン+半角スペース、そのあとにテストの説明
- 説明文は上の例(`T1: 必須ファイルが存在する` など)の文言を**そのまま**使ってください。採点はこの文字列を探すので、「3. 課題」の仕様表にある短い言い回しではなく、この例のほうを写してください
- 失敗した理由などの補足は、**次の行以降**に自由に書いてかまいません。採点は上の1行だけを見ます

失敗したときは `[PASS]` を `[FAIL]` に置き換えるだけです。

```text
[FAIL] T3: app/index.html に <title> タグがある
```

`shellcheck` が使えない環境では、T5の代わりに次の行を出します。この文言も採点で使うのでそのまま書いてください。

```text
[SKIP] shellcheck が未インストールのため省略します
```

最後の集計行の書式は次のとおりです。区切りは**半角スラッシュの前後に半角スペース**です。

```text
テスト結果: <成功件数>件成功 / <失敗件数>件失敗 / <スキップ件数>件スキップ
```

### 実行例

`shellcheck` が入っている環境で、`app/index.html` から `<title>` を消したプロジェクトを検査した場合。

```text
===== CIテスト開始: proj =====
[PASS] T1: 必須ファイルが存在する
[PASS] T2: scripts配下のシェルスクリプトに構文エラーが無い
[FAIL] T3: app/index.html に <title> タグがある
[PASS] T4: scripts配下のシェルスクリプトの1行目が #!/bin/bash である
[PASS] T5: shellcheck の警告が無い
テスト結果: 4件成功 / 1件失敗 / 0件スキップ
```

このとき終了ステータスは `1` です。`echo $?` で確かめられます。

なお `===== CIテスト開始: <ディレクトリ> =====` の見出し行は雛形に用意してあります。採点対象ではありませんが、消さずに残しておいてください。

### エラーメッセージ(仕様3のとき)

存在しないディレクトリを指定した場合は、**標準エラー出力**に次の形式で出します。ディレクトリ名を必ず添えてください。

```text
エラー: ディレクトリが見つかりません: no_such_dir
使い方: ci_test.sh [<プロジェクトディレクトリ>]
  省略した場合はカレントディレクトリを検査します。
```

## 4. やり方

```bash
# 1. exercises ディレクトリに移動する
cd exercises

# 2. 編集する(エディタは vim でも nano でも VS Code でもよい)
nano ex21-ci-test-script/work/ci_test.sh

# 3. 手元で動かしてみる(案件No.6のサンプルアプリを検査対象にできる)
bash ex21-ci-test-script/work/ci_test.sh ../projects/06-cicd-pipeline/src
echo $?

# 4. 採点する
./check.sh 21
```

手順3で案件No.6のサンプルを検査すると、**T4だけが `[FAIL]` になります**。これは不具合ではありません。案件のスクリプトは1行目が `#!/usr/bin/env bash` と書かれており、今回のルール(`#!/bin/bash` であること)には合わないからです。テストのルールは現場ごとに決めるもので、「どちらが正しいか」ではなく「そのチームがどう決めたか」で変わります。正しく `[FAIL]` が出れば、あなたのスクリプトは期待どおり動いています。

採点に合格すると、次のように表示されます。

```text
  ✓ [1] bashの構文エラーがない
  ✓ [2] 失敗が無いときは終了ステータス0で終わる
  ...
  結果: 16/16 合格
```

## 5. ヒント

自力で20分考えてから開いてください。段階的に答えに近づくよう3段階に分けています。

<details>
<summary>ヒント1: どこから手を付けるか</summary>

いきなり5つのテストを書こうとせず、**「1つのテストを最後まで通す」**ところから始めてください。

1. まず `pass` / `fail` / `skip_test` の3つの関数でカウンタを増やすようにする
2. 次に T1(必須ファイル)だけを書き、最後の集計行と `exit` まで書く
3. `bash ci_test.sh ../projects/06-cicd-pipeline/src` で動かし、`echo $?` で終了ステータスを確かめる
4. 通ったら T2、T3、T4、T5 を同じ形で足していく

T1が動けば、残りは「判定の条件が違うだけ」の同じ形です。

判定の形はどれも共通です。

```bash
if (条件); then
    pass "$T1_DESC"
else
    fail "$T1_DESC"
fi
```

</details>

<details>
<summary>ヒント2: 使う文法の具体例</summary>

**ファイルの存在**

```bash
if [[ -f "${PROJECT_DIR}/app/index.html" ]]; then
    echo "ある"
fi
```

**scripts配下の .sh を1つずつ調べて、失敗の数を数える**

```bash
NG=0
for f in "${PROJECT_DIR}"/scripts/*.sh; do
    [[ -f "$f" ]] || continue
    if ! bash -n "$f" 2> /dev/null; then
        NG=$((NG + 1))
    fi
done
```

`!` は「終了ステータスを反転する」という意味で、`if ! コマンド` は「コマンドが失敗したら」と読みます。`2> /dev/null` はエラーメッセージを画面に出さないための指定です。

**1行目の取り出しと比較**

```bash
if [[ "$(head -n 1 "$f")" != "#!/bin/bash" ]]; then
    NG=$((NG + 1))
fi
```

**コマンドがあるかどうかで分岐する**

```bash
if command -v shellcheck > /dev/null 2>&1; then
    # ある場合
else
    skip_test "shellcheck が未インストールのため省略します"
fi
```

</details>

<details>
<summary>ヒント3: 全体の骨組み</summary>

```bash
#!/bin/bash
set -u

PROJECT_DIR="${1:-.}"

PASS_COUNT=0
FAIL_COUNT=0
SKIP_COUNT=0

pass() {
    echo "[PASS] $1"
    PASS_COUNT=$((PASS_COUNT + 1))
}
# fail と skip_test も同じ形で書く

if [[ ! -d "$PROJECT_DIR" ]]; then
    echo "エラー: ディレクトリが見つかりません: ${PROJECT_DIR}" >&2
    usage >&2
    exit 1
fi

echo "===== CIテスト開始: ${PROJECT_DIR} ====="

# T1: 必須ファイル
T1_DESC="T1: 必須ファイルが存在する"
# ここで app/index.html と scripts/deploy.sh の両方を確かめ、pass か fail を呼ぶ

# T2 〜 T5 も同じ形で並べる

echo "テスト結果: ${PASS_COUNT}件成功 / ${FAIL_COUNT}件失敗 / ${SKIP_COUNT}件スキップ"

if [[ "$FAIL_COUNT" -gt 0 ]]; then
    exit 1
fi
exit 0
```

</details>

## 6. よくあるつまずき

| 症状 | 原因と対処 |
|---|---|
| 集計が常に `0件成功` になる | `pass` 関数の中でカウンタを増やしていない。`PASS_COUNT=$((PASS_COUNT + 1))` を書く |
| `[PASS] T1:必須ファイルが存在する` で不合格になる | コロンの後ろの半角スペースが抜けている。`T1: 必須ファイルが存在する` と書く |
| 失敗しているのに終了ステータスが0 | 最後の `if [[ "$FAIL_COUNT" -gt 0 ]]; then exit 1; fi` を書き忘れている。`echo $?` で確認する |
| 1件目のテストで処理が止まる | `set -e` を付けている。テストスクリプトでは付けない |
| `scripts/*.sh: No such file or directory` と出る | `.sh` が1つも無いとき、パターンの文字列がそのままループに渡される。`[[ -f "$f" ]] \|\| continue` を入れる |
| `head: cannot open ... for reading` | 上と同じ原因。ループの先頭で実在チェックを入れる |
| shellcheckが無い環境で毎回不合格になる | `command -v` で有無を調べ、無ければ `[SKIP]` にする。失敗として数えない |

`./check.sh 21` が失敗したときは、**「期待」と「実際」の差分**を必ず読んでください。どの文字列が見つからなかったかがそのまま書かれています。
