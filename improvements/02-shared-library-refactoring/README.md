# 改善案件No.2: コピペで増えた運用スクリプトを共通ライブラリ化して保守性と潜在バグを改善

## 難易度

★★☆☆☆(初級)

新しい技術を覚える案件ではなく、**すでに書いたBashコードを読み直して整理する**案件である。使う道具は `source`(=別のファイルを読み込んで、その中の関数を自分のスクリプトから使えるようにする命令)と `jq`(=JSONを安全に組み立て・加工するコマンド)、`shellcheck`(=シェルスクリプトの書き方の問題を自動指摘するツール)の3つだけで、いずれも初級の範囲に収まる。

一方で「どこまでを共通化し、どこからを各スクリプトに残すか」という**設計の判断**が求められるため、単純な写経では終わらない。また、動いている4本のスクリプトを壊さずに移行する必要があり、**段階的な移行とロールバック(=元に戻すこと)の考え方**を実際に手を動かして学べる。

## 想定依頼元・背景

> **この案件は学習用に設定した架空の依頼である。** 実在の企業での実務実績ではない。
> ただし、**改善の対象となるコードは架空ではなく、このリポジトリの `projects/` 配下に実在する自分の成果物**である。「自分が書いたコードを、自分で読み直して問題を見つけ、自分で直した」という記録がこの案件の中身である。

株式会社サンプル商事(架空の企業)情報システム部門。

同社では案件を重ねるごとに運用スクリプトが増えていった。1本目を書くときに作った「ログを出す関数」「Slackへ通知する関数」を、2本目・3本目・4本目でもそのままコピー&ペーストして使い回してきた。

その結果、4本のスクリプトに**同じような処理が少しずつ違う形で散在**する状態になった。担当者からは次のような相談が来た、という想定である。

> 「一度、Slack通知の書き方を直したはずなんですが、他のスクリプトでは直っていませんでした。これ以上スクリプトが増える前に、共通で使う部分を整理してもらえませんか」

## 改善前の状況(As-Is)の要約

対象は `projects/` 配下に実在する4本のスクリプトである。

| 案件 | ファイル | 抱えていた問題 |
|---|---|---|
| No.1 ユーザーアカウント自動化 | `projects/01-user-account-automation/src/create_users.sh` | 独自の `log()` を持つ。書式は `[時刻] [レベル] メッセージ` |
| No.2 バックアップ自動化 | `projects/02-backup-automation/src/backup.sh` | 独自の `log()` を持つ。書式は `時刻 [レベル] メッセージ`(No.1と違う)。`notify_slack()` が**JSONを手組み** |
| No.3 ログ監視・アラート | `projects/03-log-monitoring-alert/src/log-watch-alert.sh` | `log_info` / `log_warn` / `log_error` の3つ。**ファイル出力なし**。Slack通知だけ `jq` で正しく実装済み |
| No.4 サーバー死活監視 | `projects/04-server-health-check/src/health_check.sh` | `log()` と `notify_slack()` がNo.2の**完全なコピペ**。JSON手組みの問題もそのままコピーされている |

**3つの具体的な症状**

1. **ログ書式が3種類に分裂している** — 4本のログを1か所に集めても、時刻の位置が揃わないため `sort` で時系列に並べられず、`awk` でレベルだけを取り出す方法もファイルごとに変えなければならない。
2. **同じ修正を4か所に書かなければならない** — 「ログにホスト名を足したい」といった1つの要望に対し、4ファイルを開いて同じ編集を4回繰り返すことになる。1つでも忘れれば、そのスクリプトだけ挙動が違う状態になる。
3. **修正が伝播しなかった潜在バグが実際に残っている** — 案件No.3では `jq` を使ってJSONエスケープの問題を解決済みだが、**その修正がコピペ元だった案件No.2・No.4には反映されていない**。両者は今も文字列連結でJSONを組み立てており、通知メッセージに `"` `\` 改行が含まれると壊れたJSONを送信してしまう。

3つ目は、この案件が「コピペの危険性」を主張するために作った例え話ではなく、**このリポジトリのコードに実際に存在していた不具合**である。詳細な再現手順は [01-current-analysis.md](./01-current-analysis.md) に記載した。

## 依頼内容(改善要求)

- 4本のスクリプトに散在している共通処理(ログ出力・Slack通知・設定読み込み・前提コマンドチェック)を、**1つの共通ライブラリにまとめる**こと
- ログの書式を**1種類に統一**し、複数のログをまとめて `grep` や集計にかけられるようにすること
- Slack通知のJSONエスケープ漏れを解消し、**同種の修正が1か所の変更で全スクリプトに反映される**状態にすること
- 稼働中のスクリプトを壊さないよう、**1本ずつ段階的に移行**し、問題があればすぐ元に戻せるようにすること
- 共通ライブラリには**テストを用意**し、ライブラリ側の変更が全体を壊していないことを機械的に確認できるようにすること
- 既存の設定ファイル(`backup.conf` / `health_check.conf` / `.env`)の書式は変えないこと(運用担当者の作業を発生させないため)

## 改善結果サマリ(Before→After)

すべての数値は、**このリポジトリの実コードを対象に実際に数えた実測値**である。数え方は `src/count_duplication.sh` として実行可能な形で残してあり、誰でも同じ数値を再現できる。

| 指標 | Before(改善前) | After(改善後) | 数え方 |
|---|---|---|---|
| 重複していた共通処理 | **4ファイルに散在(合計120行)** | **共通ライブラリ1ファイルに集約** | `src/count_duplication.sh` で計測。対象ブロックの開始行〜終了行のうち、コメントのみの行を除いた行数 |
| 同種の修正で触るファイル数 | **4ファイル** | **1ファイル** | ログ書式やSlack送信方法を変更する場合に編集が必要なファイル数 |
| 潜在バグ(JSONエスケープ未対応) | **2箇所** | **0箇所** | `--data "{\"text\": ...}"` と手組みでJSONを作っている関数の数(No.2とNo.4の `notify_slack`) |
| ログ書式 | **3種類** | **1種類** | 4本のスクリプトが出力するログ行の書式の種類数 |
| 共通ライブラリのテスト | **0件** | **35件(全件成功)** | `src/test_opslib.sh` の実行結果 |

**正直に書いておくべきこと**: 共通ライブラリ `opslib.sh` そのものは161行(コメント・空行を除く)あり、集約された120行より**行数は増えている**。これは、戻り値の設計・ログレベルによる出力抑制・ドライラン機能など、改善前には無かった機能を足したためである。**この改善の目的は行数を減らすことではなく、「同じ修正を何ファイルに書くか」を4から1に減らすこと**である。詳細は [05-effect-measurement.md](./05-effect-measurement.md) に記載した。

## 使用技術・ツール

- **OS**: Ubuntu Server 22.04 LTS(動作確認は Bash 5.2 / ShellCheck 0.9.0 で実施)
- **Bash**: `source` によるライブラリ読み込み、関数設計、`local` による変数スコープ管理
- **`${BASH_SOURCE[0]}`**: スクリプト自身の場所を基準に相対パスを解決する仕組み
- **jq**: JSON文字列の安全なエスケープ(`jq -n --arg`)
- **shellcheck**: シェルスクリプトの静的解析(=実行せずにコードを読んで問題を指摘すること)
- **Bashだけで書く簡易テスト**: 追加インストール不要のテストスクリプト
- **curl**: Slack Incoming Webhook への通知送信

## この案件で身につくスキル

- **コピペによる重複がなぜ危険かを、実例を挙げて説明できる** — 「1か所直しても他に伝播しない」という抽象論ではなく、自分のコードで実際に起きた事象として語れる
- **`source` の仕組みを理解している** — 別プロセスではなく同じシェルの中でファイルが読み込まれること、そのため変数や関数が呼び出し側と同じ空間を共有することを説明できる
- **ライブラリ設計の原則を実践できる** — 呼び出し側の変数に暗黙依存しない、副作用を減らす、`exit` せず戻り値で状態を返す、名前空間を接頭辞で分ける
- **後方互換を保った段階的な移行を計画・実施できる** — いきなり全部を差し替えず、1本ずつ移行し、各段階でロールバック手段を用意する
- **リファクタリングにテストが必要な理由を説明できる** — 共通化は「壊れたときの影響範囲」も広げるため、安全網としてテストが要ることを理解している
- **改善の効果を数値で示せる** — 計測方法まで含めて説明し、都合の良い数字だけを並べない

## 面接でアピールできるポイント(3つ、実際に話すセリフ例つき)

> 以下はすべて「**自分のポートフォリオのコードを対象に、自分で問題を見つけて直した**」という話である。実務での経験として語らないこと。

1. **自分のコードを読み直して、潜在バグを自力で発見・修正した**

   > 「自分で作った運用スクリプト4本を後から読み直したところ、Slack通知のJSONを文字列連結で組み立てている箇所が2つ残っていることに気づきました。メッセージ本文にダブルクォートや改行が入ると壊れたJSONを送ってしまう作りです。3本目のスクリプトを書いたときに `jq` を使う方法で直していたのですが、その修正が**コピペ元だった他の2本には反映されていなかった**んです。実際に壊れたJSONが生成されることを検証スクリプトで再現してから、共通ライブラリに集約して修正しました。Slackへは実送信せず、生成されるJSON文字列を `jq empty` で妥当性判定する形で確認しています。」

2. **「なぜコピペが危険か」を、体験した事実として説明できる**

   > 「よく『コピペは良くない』と言われますが、自分の場合は**なぜ良くないのかを身をもって知る**ことになりました。同じ処理が4ファイルに散らばっていて、実測で120行が重複していました。この状態だと、ログにホスト名を足すような小さな変更でも4ファイルを編集する必要があり、1つ忘れればそのスクリプトだけ挙動が変わってしまいます。共通ライブラリに集約したことで、同種の修正で触るファイルは**4から1**になりました。行数を数えるスクリプトも成果物として残し、効果を再現できる形にしています。」

3. **動いているものを壊さないための、段階的移行とテストを設計した**

   > 「4本を一度に書き換えると、問題が起きたときに原因の切り分けができません。そこで**1本ずつ移行し、各段階で元のファイルを退避してすぐ戻せる**手順にしました。また、共通化は便利な反面『ライブラリの1行のミスが4本すべてに一度に波及する』というリスクも生みます。そのリスクを抑えるために、Bashだけで書いた簡易テストを35件用意し、エスケープ処理や戻り値、ライブラリが呼び出し側の設定を壊さないことなどを機械的に確認できるようにしました。既存の設定ファイルは書式を一切変えていないので、運用担当者の作業を発生させずに移行できる設計です。」

## 前提知識

- シェルスクリプトの基礎文法(変数、`if` による条件分岐、関数の定義と呼び出し、終了コードという概念)
- コマンドの終了ステータス(`$?`)と、`if コマンド; then` という書き方の意味
- `projects/` 配下の案件No.1〜No.4のスクリプトを一度読んだことがあること(自分で作っていればなお良い)
- `jq` は未経験でも問題ない(この案件で使うのは `jq -n --arg` と `jq empty` の2つだけで、本文中で解説している)
- テストフレームワークの知識は不要(この案件のテストはBashの `if` と `echo` だけで書かれている)
