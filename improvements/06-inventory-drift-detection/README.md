# 改善案件No.6: 手動更新のサーバー台帳を構成情報の自動収集・差分検知に改善

## 難易度

★★★★☆(上級)

この案件が上級である理由は、次の3つが同時に求められるためである。

1. **複数台のサーバーへ非対話で入り込む技術**: SSHの鍵認証、`BatchMode=yes`、タイムアウト設計など、「人が見ていない状態で他サーバーを操作する」ための作法を正しく理解する必要がある。1つ間違えると、cronの中で入力待ちのまま固まる・全台の収集が止まる、といった事故になる。
2. **構造化データ(JSON)を作り、比較する設計力**: 単にコマンド結果をテキストで残すだけでは差分比較ができない。「どういう形で保存すれば、機械で正しく比較できるか」というデータ設計そのものが問われる。
3. **ノイズとの戦い**: 差分検知ツールは、作った直後は必ず「毎日大量の差分が出る」状態になる。何を差分とみなし、何を無視するかを決める判断が、ツールが使われ続けるかどうかを分ける。

一方で、使っている道具そのもの(Bash・ssh・jq・diff・cron)は構築パックNo.1〜No.4で扱ったものの延長線上にある。**新しいコマンドを覚える難しさではなく、設計判断の難しさ**が★4つの理由である。

### 前提: 「構成ドリフト」とは何か

**構成ドリフト(configuration drift)** とは、**「台帳やドキュメントに書かれた"あるべき構成"と、サーバーの"実際の構成"が、時間とともに少しずつズレていく現象」** のことである。drift は英語で「漂流」の意味で、放っておくと勝手に離れていく様子を表している。

ドリフトは、悪意や怠慢がなくても必ず発生する。

```mermaid
flowchart LR
    A["台帳作成時<br/>台帳 = 実態"] --> B["障害対応で<br/>設定を緊急変更"]
    B --> C["台帳の更新は<br/>あとで、と先送り"]
    C --> D["別の作業が入り<br/>更新を忘れる"]
    D --> E["台帳 ≠ 実態<br/>(ドリフト発生)"]
    E --> F["台帳が信用できない<br/>ので誰も見なくなる"]
    F --> G["さらに更新されなくなる<br/>(悪循環)"]
```

重要なのは、**これは人の努力では解決できない構造的な問題**だという点である。「次からは必ず台帳を更新しましょう」というルールを作っても、緊急対応の最中に台帳を開く人はいない。だからこそ、「人が更新する台帳」をやめて、「サーバー自身に現状を報告させる台帳」に作り変える、というのが本改善の考え方である。

詳しい分析は [01-current-analysis.md](./01-current-analysis.md) を参照。

## 改善前の状況(As-Is)の要約

| 項目 | 改善前の状態 |
|---|---|
| 台帳の形式 | Excelファイル(共有フォルダに配置。更新は手動) |
| 更新のきっかけ | 担当者が「思い出したとき」。更新義務のルールはあるが守られていない |
| 棚卸しの方法 | 四半期ごとに、担当者が全6台へ順にSSHでログインし、コマンドを打って目視確認してExcelへ転記 |
| 棚卸しの所要時間 | 1台あたり約80分 × 6台 = **約8時間**(年4回で **年32時間**) |
| 前回発見された食い違い | **12件**(IPアドレス、OS版数、ユーザー、sudo権限、開放ポート、廃止済みサーバーの残存など) |
| 乖離に気づくまでの時間 | 最大3ヶ月(次の棚卸しまで気づけない) |
| 変更履歴 | **追跡不可**。「いつ・誰が・何を変えたか」を後から調べる手段がない |

## 依頼内容(改善要求)

- 6台のサーバーから、構成情報を**自動で**収集すること。収集する項目は次のとおり。
  - OS名・カーネル版数・ホスト名・IPアドレス
  - ディスク使用状況
  - 主要パッケージのバージョン
  - 起動中のサービス
  - ユーザー一覧(および管理者権限の有無)
  - 開放されている(待ち受け中の)ポート
- 収集結果を**日付ごとのスナップショット**として保存し、後から「あの日の構成」を参照できること
- 前回の収集結果と比較して、**差分(構成ドリフト)を検知**すること
- 差分があればSlackへ通知し、日次のレポートにも残すこと
- 人間が読める**台帳(Markdown / CSV)を自動生成**すること
- 対象サーバーで動いているサービスを止めないこと(**読み取り専用の収集に徹する**こと)
- 収集のために使うSSHの権限は、必要最小限にすること

詳細な提案・比較検討は [02-improvement-proposal.md](./02-improvement-proposal.md)、設計は [03-design.md](./03-design.md) を参照。

## この案件で身につくスキル

- **構成ドリフトという概念**を説明でき、「なぜ手動の台帳は必ず腐るのか」を構造的な問題として語れる
- SSHの**非対話実行**(`BatchMode=yes`・`ConnectTimeout`・鍵認証)を、cronから安全に回すための作法として理解し実装できる
- **最小権限の設計**ができる。収集専用ユーザーを作り、`authorized_keys` の `command=` や `from=` で「その鍵でできること」を限定する方法を知っている
- `jq` を使って、**素のコマンド出力を構造化データ(JSON)に変換**し、抽出・整形・CSV出力まで一貫して扱える
- 「JSONをそのまま比べる」のではなく、**比較しやすい形に平坦化してから `diff` を取る**という、差分検知の定石を理解している
- 「毎回変わる値」を除外する**ノイズ対策**の必要性を、実体験として説明できる(=アラート疲れを起こさない監視設計)
- 日付ディレクトリによる**スナップショット管理**で、変更履歴を残し、保持期間で自動的に世代を掃除する設計ができる
- **IaC(Ansible)との補完関係**を説明できる。「あるべき姿に揃える」ことと「ズレを検知する」ことは別の課題であり、両方が必要だと理解している
- 稼働中サーバーに対して、**サービスを止めずに読み取り専用で情報を集める**という、運用改善で最も重視される安全性の観点を持っている

## 面接でアピールできるポイント(3つ、実際に話すセリフ例つき)

> **前置きの注意**: 以下はいずれも「架空の案件として自分で設計し、検証環境で実際に動かして確かめた」という前提で話すためのセリフ例である。実務経験として話すと経歴詐称になるため、必ず「学習用に自分で設計した架空案件」であることを最初に伝えること。

1. **「台帳が腐る」問題を、人の努力ではなく仕組みで解いた**

   > 「これは学習のために自分で設計した架空の案件なのですが、"Excelの台帳が実態と合わなくなる"という、どの現場にもある問題を題材にしました。最初は"更新ルールを厳格にする"案も考えたのですが、障害対応の最中に台帳を開く人はいないので、ルールでは必ず破綻すると考えました。そこで発想を変えて、**人が更新する台帳をやめて、サーバー自身に毎日現状を報告させ、その結果から台帳を自動生成する**設計にしました。台帳を手で編集しても翌日には上書きされる、という作りにしたことで、"更新漏れ"という概念そのものをなくしています。想定シナリオでは、四半期に8時間かけていた棚卸しが0分になり、乖離に気づくまでの時間が最大3ヶ月から翌日になる、という試算です。」

2. **Ansible(IaC)で"揃える"のではなく、まず"ズレを検知する"を選んだ理由を説明できる**

   > 「構成管理といえばAnsibleですが、今回あえて第一選択にしませんでした。理由は2つあります。1つは、既存の6台は手作業で作られた稼働中のサーバーで、**そもそも"あるべき姿"がまだ誰にも定義できていない**状態だったからです。正解が分からないまま上書きすると、動いているサービスを壊しかねません。もう1つは、Ansibleは**管理下に入れた項目しか揃えられない**という性質です。誰かが手で開けたポートや、追加した管理者権限のように、Playbookに書いていない変更は検知できません。なので、まず読み取り専用の収集で現状を可視化し、それを材料に"あるべき姿"を決めてからAnsibleでコード化する、という順番にしました。**IaCで揃えることと、ドリフトを検知することは対立ではなく補完関係**だと考えています。実際、構築パックで作ったAnsibleのPlaybookと並べて使う前提で設計しました。」

3. **「差分が出すぎて誰も見なくなる」ことを見越して、ノイズ対策を設計に組み込んだ**

   > 「差分検知ツールで一番怖いのは、**毎日大量の差分が出て、そのうち誰も通知を見なくなること**だと考えました。実際、検証環境で最初に動かしたとき、ディスク使用率のように毎回変わる値がそのまま差分として出てきました。そこで、JSONを `packages[nginx]=1.24.0` のような1行1項目の形に平坦化してから比較し、設定ファイルに書いた正規表現に一致するキー(ディスク使用率など)を比較対象から除外する仕組みを入れています。さらに、ユーザー・sudo権限・開放ポート・パッケージという**セキュリティに直結する項目だけを重要度『高』として強調表示**するようにしました。検証では、実際にサーバー上で新しいポートを待ち受けさせた状態で収集し、その1件だけが重要度『高』として検知されること、同時に変化させたディスク使用率が差分として出てこないことを確認しています。」
