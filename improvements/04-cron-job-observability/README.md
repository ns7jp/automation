# 改善案件No.4: cronのサイレント障害を実行結果の可視化と失敗検知で撲滅

cronで動いている8本の定期処理を、**共通ラッパースクリプト経由の実行**に置き換えることで、「動いたのか」「成功したのか」「そもそも起動したのか」を可視化し、失敗と未実行の両方を検知できるようにした改善案件。

> **この案件は架空の設定です。**
> 実在企業での実務経験ではなく、学習用に自分で組み立てた疑似案件である。依頼元「株式会社サンプル商事」は架空の会社であり、後述するインシデント(バックアップが2週間止まっていた等)も、運用現場で実際によく起きる事象を参考に自分で作成したシナリオである。
> 効果測定の数値は、**(a) 検証環境で実際に測定した実測値** と **(b) 想定シナリオに基づく試算値** の2種類があり、[05-effect-measurement.md](./05-effect-measurement.md) では両者を必ず区別して記載している。

## 難易度

★★★☆☆(中級)

シェルスクリプトの文法そのものは難しくない。難しいのは次の3点であり、どれも「コマンドの使い方」ではなく**設計の考え方**を問う内容のため、中級に位置づけている。

| 難所 | なぜ難しいか |
|---|---|
| 終了ステータスの正確な扱い | `$?` は直後にしか取れない、パイプや `tee` を挟むと消える、`set -e` の挙動が直感と違う、といった落とし穴が多い。「失敗を検知する仕組み」自体が失敗を取りこぼすと意味がない |
| デッドマン監視の発想 | 「起きたこと」ではなく「**起きるはずのことが起きていないこと**」を検知する。監視対象の外側に監視役を置く必要があり、初学者が最もイメージしづらい部分 |
| 既存を壊さない移行 | 既に本番で動いているジョブを止めずに、1本ずつ切り替える手順とロールバック手順を設計する必要がある |

## 想定依頼元・背景

| 項目 | 内容 |
|---|---|
| 依頼元 | 株式会社サンプル商事(**架空の会社**。構築案件パック No.1〜No.6 と同一の会社という想定) |
| 部署 | 情報システム部門(担当者1名体制) |
| これまでの経緯 | 過去の案件で[バックアップ自動化](../../projects/02-backup-automation/README.md)や[死活監視](../../projects/04-server-health-check/README.md)を導入し、手作業は確かに減った。その結果、cronで動く定期処理が少しずつ増えて8本になった |
| 起きた問題 | 自動化されたことで**誰も見なくなった**。ジョブが失敗しても、そもそも起動しなくても、誰も気づかない状態が常態化していた |
| きっかけ | 「先週のファイルを戻したい」という依頼をきっかけに、**バックアップが2週間止まっていた**ことが発覚した |

**構築案件パックとの関係**: 構築パックは「無かったものを作る」案件だった。本改善パックは、その**作ったものが増えた結果として生まれた新しい課題**を扱う。自動化は「導入して終わり」ではなく、「動き続けていることをどう確かめるか」までが仕事である、という点が本案件のテーマである。

## 改善前の状況(As-Is)の要約

| 観点 | 改善前の状態 |
|---|---|
| 実行記録 | **無し**。ジョブが動いたのかどうかを後から確認する手段が無い |
| ジョブ台帳 | **無し**。`crontab -l` を叩かないと何が動いているか分からず、全体像を把握している人がいない |
| 失敗の検知 | **できない**。cronの標準のメール通知(`MAILTO`)は未設定で、メール配送の仕組み自体も整っていない |
| 未実行の検知 | **原理的に不可能**。ジョブが起動していないのだから、ジョブ自身が通知することはできない |
| 多重起動の防止 | **無し**。処理が長引くと前回の実行と重なる |
| 実際に起きた事故 | バックアップ停止に2週間気づかなかった / 死活監視が多重起動し、状態ファイルが破損した |

用語:**サイレント障害**(silent failure)= 障害が起きているのに、誰にも知らされないまま静かに継続している状態。エラーで止まる障害よりも発見が遅れ、被害が大きくなりやすい。

詳細は [01-current-analysis.md](./01-current-analysis.md) を参照。

## 依頼内容(改善要求)

- 現在動いているcronジョブ8本を洗い出し、**一覧できる状態**にしてほしい
- ジョブが失敗したら**すぐ気づける**ようにしてほしい(メールではなくSlackで)
- 「ジョブがそもそも動かなかった」ケースにも気づけるようにしてほしい
- 処理が長引いたときに次の実行と重なる事故を防いでほしい
- **既存のジョブスクリプトはできるだけ触らないでほしい**(バックアップ処理などに手を入れて壊すのが怖いため)
- 有償の監視ツールを導入する予算は無い。まずは今あるLinuxの標準機能でできる範囲で
- 移行作業で定期処理が止まることが無いようにしてほしい

詳細と、改善案の比較・選定理由は [02-improvement-proposal.md](./02-improvement-proposal.md) を参照。

## 改善結果サマリ(Before → After)

| 指標 | Before(改善前) | After(改善後) | 測定区分 |
|---|---|---|---|
| 失敗に気づくまでの時間 | **平均18時間** | **5分以内** | 試算 + 実測([05](./05-effect-measurement.md)参照) |
| 未実行(ジョブが起動しなかった)の検知 | **不可能** | **予定時刻+猶予時間の超過で検知可能** | 実測 |
| 多重起動事故 | **発生あり**(死活監視の状態ファイル破損) | **`flock` で防止(0件)** | 実測 |
| 管理対象ジョブの可視化 | **台帳なし**(全体像を誰も把握していない) | **cronジョブ8本を台帳と日次レポートで一覧化** | 実測 |
| 実行記録 | 残らない | 全実行を1件1行のCSVに記録(開始/終了/終了ステータス/所要時間) | 実測 |
| 既存ジョブスクリプトの改修 | — | **0行**(crontabの書き方を変えるだけ) | 実測 |

補足:

- 「平均18時間」は、改善前の3か月分のログを調査し、**失敗に気づけた5件について** 「最初に失敗した時刻」と「担当者が気づいた時刻」の差を平均した想定値。**気づけなかった事例(2週間のバックアップ停止)は母数に含まれていない**ため、実態としてはこれより悪い、という前提の数字である。算出根拠は [01-current-analysis.md](./01-current-analysis.md#6-現状をどう把握したか) に記載。
- 「5分以内」は運用上の目標値。検証環境の実測では、**ジョブ本体の終了から実行記録の書き込み・失敗通知の組み立てまでラッパー全体で0.04秒未満**だった(通知送信はドライランモードでの計測。実際のSlack配信の所要時間は別途加わる)。目標に対して十分な余裕がある。
- 「0件」は、検証環境で多重起動を意図的に発生させたテストにおいて、`flock` が想定どおり後発の実行をすべてスキップした結果を指す。

## この案件で身につくスキル

- **サイレント障害という概念**を理解し、「エラーで止まる障害」より「静かに止まっている障害」のほうが危険である、という運用の勘所を説明できる
- 終了ステータス(`$?`)の意味と伝播を正確に理解し、**パイプや `tee` を挟むと成否が消える**という典型的な罠を回避した実装ができる
- `flock` による排他制御を実装でき、**なぜ多重起動が危険なのか**(ファイル破損・二重処理・負荷)を具体例で説明できる
- **デッドマン監視**(起きるはずのことが起きていないことを検知する)という監視設計の考え方を理解し、実装できる
- **ラッパー方式**という設計手法を理解し、「既存の資産に手を入れずに横断的な機能を足す」という発想ができる
- 稼働中のシステムに対する**段階的移行とロールバック**の手順を、自分で設計・文書化できる
- 改善の効果を、**わざと壊すテスト**(意図的に失敗させる・意図的に実行させない)で検証し、数値で示せる

## 面接でアピールできるポイント(3つ、実際に話すセリフ例つき)

### 1. 「失敗が検知できない」ではなく「未実行が検知できない」ことこそが本質的な課題だと分析した

> 「架空の改善案件として自分で設定し、検証環境で実装・測定したものですが、最初は『失敗したら通知する』だけを考えていました。しかし現状分析をするうちに、**一番怖いのはジョブがそもそも起動していないケース**だと気づきました。ジョブが起動していなければ、そのジョブに通知処理を何行足しても絶対に鳴りません。監視対象の内側に監視を置いても検知できないので、**外側に『予定時刻を過ぎても実行記録が無いことを検知する仕組み』**、いわゆるデッドマン監視を置きました。実行記録CSVの最終実行時刻と、台帳に定義した想定実行間隔＋猶予時間を比較する方式です。検証環境で、わざとcronの登録を外して2時間放置するテストを行い、猶予時間の超過を検知して通知が出ることを確認しています。」

### 2. 既存のジョブスクリプトを1行も変更せずに、可視化・失敗検知・多重起動防止をまとめて追加した

> 「改善案としては、各スクリプトに通知処理を追加する案も検討しました。ただ、対象が8本あり、バックアップやDBダンプなど**壊すと影響が大きいスクリプト**も含まれていたため、既存に手を入れない方式を選びました。採用したのは、`run_job.sh <ジョブID> <元のコマンド>` という形で既存ジョブを包んで起動する共通ラッパー方式です。crontabの書き方を変えるだけで、実行記録の保存・失敗通知・`flock` による多重起動防止の3つが一度に付いてきます。**改修行数はジョブ側で0行**で、逆に言えば1本のラッパーを直せば8本すべての挙動が改善される、という保守性も狙いました。移行も8本を一度に切り替えるのではなく、影響が小さい死活監視から1本ずつ、旧設定をコメントとして残したまま切り替える手順にして、いつでも戻せるようにしています。」

### 3. 「失敗を検知する仕組み」が失敗を取りこぼさないよう、終了ステータスの扱いを設計した

> 「ラッパーで一番気をつけたのは終了ステータスの扱いです。`$?` は直前のコマンドの結果しか保持しないので、ジョブ実行の直後に必ず変数へ退避しています。また、ログを残そうとして安易に `ジョブ | tee ログ` と書くと、受け取れるのは `tee` の終了ステータスになってしまい、**ジョブが失敗しても成功扱いになる**という罠があります。検証環境で `false | tee` の終了ステータスが0になることを実際に確認したうえで、パイプを使わず `>> ログ 2>&1` のリダイレクトで出力を保存する設計にしました。ラッパー自身も、受け取った終了ステータスをそのまま `exit` で返して呼び出し元に伝播させています。さらに、ラッパー自身のエラーはジョブの終了ステータスと混ざらないよう90番台に分けています。」
