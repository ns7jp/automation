# 改善案件No.1: 月次運用報告書の作成を自動集計・自動生成に改善

## 難易度

★☆☆☆☆(入門)

改善パックの入口となる案件。使う技術は Bash / awk / date / cron / curl と、どれも構築パックで一度は触れたものだけに絞っている。

ただし「作れるか」ではなく **「現状を数字で把握し、改善案を比較して選び、効果を測る」** という改善案件特有の進め方に慣れることが目的なので、コードを書く時間よりも **現状分析と効果測定に時間を使う** ことになる。

## 想定依頼元・背景

> **重要(正直な但し書き)**
> この案件は **学習用に自分で組み立てた架空の設定** である。実在する企業の実務案件ではなく、ここに書かれた「依頼」も「担当者」も存在しない。
> 数値はすべて、この架空シナリオのために設定した前提値、または **自分の検証環境(仮想マシン1台)で実際に測った実測値** である。どちらなのかは各ドキュメント内で必ず明示している。

**株式会社サンプル商事**(架空の企業)。構築パック(`projects/`)と同じ依頼元という設定。

| 項目 | 内容 |
|---|---|
| 業種・規模 | 卸売業・従業員50名 |
| 情報システム体制 | 専任担当1名(兼務なし・バックアップ担当も同一人物) |
| 管理サーバー | 6台(Web 2台 / API 1台 / DB 1台 / アプリ 1台 / ファイル 1台) |
| 既に導入済みの仕組み | 案件No.2「定期バックアップ自動化」<br>案件No.4「サーバー死活監視・障害検知」 |

自動化ツールの導入によって「バックアップを取る」「障害に気づく」ところまでは仕組み化できた。しかし **その結果を毎月まとめて経営層へ報告する作業だけが、いまだに完全な手作業のまま残っている** ——それが今回の改善対象である。

## 改善前の状況(As-Is)の要約

毎月末、担当者は次の作業を **約3時間** かけて手作業で行っている。

```mermaid
flowchart LR
    A["ターミナルで<br>サーバー6台にSSH"] --> B["backup.log を<br>less で開く"]
    B --> C["grep しながら<br>成功・失敗を目で数える"]
    C --> D["数えた件数を<br>Excelに手入力"]
    D --> E["死活監視ログでも<br>同じことを繰り返す"]
    E --> F["Excelを整形して<br>報告書を完成"]
    style C fill:#ffe0e0
    style D fill:#ffe0e0
```

| 問題 | 具体的な影響 |
|---|---|
| 時間がかかる | 毎月3時間、年間36時間。担当1名の貴重な時間が集計作業に消える |
| 転記ミスが起きる | 目で数えてExcelに手入力するため、**年6件**の転記ミスが発生(修正版の再送が必要になる) |
| 属人化している | 手順が担当者の頭の中にしかなく、休むと誰も報告書を作れない |
| 過去との比較がしにくい | Excelファイルが月ごとにバラバラで、差分が追えない |

詳細は [01-current-analysis.md](./01-current-analysis.md) を参照。

## 依頼内容(改善要求)

- ログから **自動で集計** し、月次運用報告書を **自動生成** すること
- 出力形式は **Markdown**(必要に応じてHTMLも)。Excelの手入力をなくすこと
- `cron` で **月初に自動生成** し、完成したら **Slackへ通知** すること
- 人間の作業は **「生成物を目視確認して特記事項を書く」だけ** にすること
- **既存のバックアップ・死活監視の運用は絶対に止めない**こと(読み取り専用で動くこと)
- 移行はいきなり切り替えず、**手作業と並行運用して結果を突き合わせられる**こと

詳細は [02-improvement-proposal.md](./02-improvement-proposal.md) を参照。

## 改善結果サマリ(Before→After)

| 指標 | Before(改善前) | After(改善後) | 効果 |
|---|---|---|---|
| 月次報告書の作成時間 | **3時間/月** | **5分/月**<br>(自動生成2分+目視確認3分) | **約97%削減** |
| 年間の作業時間 | **36時間/年** | **1時間/年** | **35時間の創出** |
| 転記ミス | **年6件** | **0件**<br>(集計を人手で写さないため) | **根絶** |
| 作成できる人 | **担当者1人のみ** | **コマンド1つで誰でも** | 属人化の解消 |
| 過去との比較 | Excelがバラバラで困難 | Gitで履歴管理・差分表示が可能 | 傾向分析が可能に |

> 数値の出どころ:
> - 「3時間/月」「年6件」は **この架空シナリオの前提として設定した値**(改善前の状態を表す設定)。
> - 「5分/月」の内訳のうち、**自動生成部分は検証環境での実測**(レポート生成本体は 0.19〜0.20 秒、ログ収集を含めた一連の流れを2分と見込む)、**目視確認3分は想定シナリオに基づく試算**。
> - 測り方の詳細は [05-effect-measurement.md](./05-effect-measurement.md) に全部書いてある。

## 使用技術・ツール

| 技術 | 本案件での用途 |
|---|---|
| **Bash** | 全体の制御・レポートの組み立て |
| **awk** | ログの集計(列の取り出し・条件で絞り込み・サーバー別カウント) |

| **rsync / scp** | 6台のサーバーからのログ収集 |
| **find / basename** | サーバーごとのログディレクトリの列挙 |
| **shellcheck** | シェルスクリプトの静的検査(=実行せずに文法・危険な書き方を検査するツール) |

## この案件で身につくスキル

- **現状を数字で捉える力**: 「なんとなく大変」を「1回3時間・年36時間・ミス年6件」という測定可能な指標に落とし込める
- **awkによるログ集計**: 列の取り出し(`$1`, `$5`)、条件での絞り込み、連想配列によるサーバー別カウントを、意味を理解して書ける
- **dateコマンドの実務的な使い方**: 「前月の初日と末日」を月末日の罠(`-1 month`問題)を避けて安全に求められる
- **ヒアドキュメントによる帳票生成**: 完成形が目で見える形でレポートを組み立てられる
- **改善案を比較して選ぶ力**: 複数案を評価軸つきの表で比較し、「なぜその案なのか」を説明できる
- **運用を止めない移行設計**: 並行運用 → 段階的切替 → ロールバック手順、という現場で必須の進め方を設計できる
- **効果測定**: Before/Afterを定量比較し、「何が達成でき、何が未達か」を正直に報告できる

## 面接でアピールできるポイント(3つ)

### 1. 「作れる」だけでなく「現状を数字にしてから直せる」こと

> 「これは実務案件ではなく、**学習用に自分で組み立てた架空の改善案件**です。まず改善前の作業を1ステップずつ書き出して、どこに何分かかるかを分解しました。『月次報告に3時間かかっている』という設定に対して、内訳を出すと **6台分のログを目で数える作業だけで105分**、つまり全体の6割弱を占めていることが見えました。そこで最初に手を付けるのはExcelの整形ではなく集計の自動化だ、と判断しています。いきなりコードを書くのではなく、**時間の内訳を出してから直す場所を決めた**のがこの案件で一番意識したところです。」

### 2. 改善案を1つに決め打ちせず、比較して選んだこと

> 「改善案を3つ出しました。Excelマクロ化、Zabbixのようなツール導入、そして今回選んだ **Bash+awkでのレポート自動生成** です。導入コスト・保守性・担当1名体制でも運用できるか、という3つの軸で比較表を作って評価しました。Zabbixは機能では圧勝ですが、**担当者が1名しかいない体制では監視基盤そのものの保守が新しい負担になる**と考えて外しています。技術的に一番すごい案ではなく、**その組織が回せる案**を選んだ、という説明ができるのがこの案件の価値だと思っています。」

### 3. 既存運用を止めずに切り替える移行設計をしたこと

> 「改善で一番怖いのは、直したことで既存の運用が止まることです。そこでツールは **ログを読むだけで一切書き換えない読み取り専用** の設計にし、さらに `-n`(ドライラン)オプションを付けて、**ファイルを保存せず結果だけ表示できる**ようにしました。移行も1か月分は手作業と並行して走らせ、両方の数字を突き合わせて一致を確認してから切り替える手順にしています。ロールバックは **cronの1行をコメントアウトするだけで元の手作業に戻せる** ——ここまで含めて設計書に書きました。実際に検証環境で、死活監視ログを意図的に消した状態でも『読めたログの分だけレポートを出して警告を残す』ことを確認しています。」
