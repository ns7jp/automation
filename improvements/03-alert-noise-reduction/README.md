# 改善案件No.3: アラート過多(アラート疲れ)を棚卸しと重要度分類で改善

## 難易度

★★★☆☆(中級)

技術的に難しいコマンドを使うわけではない。難しいのは**「何を減らして、何を絶対に減らしてはいけないかを、自分で決めて説明できること」**にある。

| 難しさの内訳 | 内容 |
|---|---|
| 技術面 | Bashの連想配列、正規表現、状態ファイル、jq。構築案件No.3・No.4を終えていれば手が届く範囲 |
| 設計面 | 重要度(P1/P2/P3)の線引き、集約ウィンドウの長さ、通知先の分け方を**自分で決める**必要がある |
| 運用面 | 「通知を減らす=障害を見逃すリスクを増やす」ため、いきなり本番を絞らない段階的な移行とロールバックの設計が要る |

構築案件(projects/)が「無いものを作る」のに対し、この改善案件は「**すでに動いているものを壊さずに直す**」ことがテーマになる。

## 想定依頼元・背景

> **⚠️ この案件は架空の設定です。**
> 実在する企業での実務経験ではありません。学習用のポートフォリオとして、依頼元・課題・データのすべてを自分で設定し、自分の検証環境で実際に構築・測定したものです。
> 本文中の数値は「検証環境での実測値」または「想定シナリオに基づく試算」であり、どちらであるかを [05-effect-measurement.md](./05-effect-measurement.md) で明示しています。

**依頼元(架空)**: 株式会社サンプル商事 情報システム部(構築案件パックと同じ架空の依頼元)

**背景(架空)**:

同社では、これまで監視の仕組みがまったく無く、障害に気づくのはいつも「利用者からの電話」だった。そこで前段の案件として、

- [projects/03-log-monitoring-alert](../../projects/03-log-monitoring-alert/README.md) — アプリログを監視し、`ERROR`/`CRITICAL` を検知したらSlackへ通知
- [projects/04-server-health-check](../../projects/04-server-health-check/README.md) — サーバーの死活監視を行い、連続NGならSlackへ通知
- [projects/02-backup-automation](../../projects/02-backup-automation/README.md) — バックアップの結果と容量をSlackへ通知

の3つを導入した。**検知はできるようになった。しかし、今度は通知が多すぎて誰も見なくなった。**

Slackの監視チャンネル `#monitoring` には1日約200件の通知が流れる。その9割は対応不要な通知で、メンバーは通知を開かなくなり、チャンネルはミュートされた。結果として、**本当に対応が必要な通知が大量の通知に埋もれ、月2件の見逃しが発生している**。

この「通知が多すぎて誰も見なくなる状態」を、運用の世界では**アラート疲れ(alert fatigue)**(=通知に慣れてしまい、反応しなくなる現象)と呼ぶ。監視を入れた現場で非常によく起きる、典型的な次の課題である。

## 改善前の状況(As-Is)の要約

| 項目 | 改善前の状態 |
|---|---|
| 1日の通知件数 | 約200件(すべて同じチャンネル `#monitoring` に流れる) |
| そのうち対応が必要だったもの | 約20件(10%) |
| 対応不要だったもの | 約180件(**90%**) |
| 通知の見られ方 | チャンネルはミュート。朝まとめてスクロールして流し読み |
| 重要な通知の見逃し | 月2件 |
| 一次対応の着手までの時間 | 平均25分 |
| 通知の内訳(上位3種) | アプリログの同一ERROR繰り返し 62件 / 死活監視の復旧通知 35件 / バックアップ正常終了通知 32件 |

詳細な棚卸し結果は [01-current-analysis.md](./01-current-analysis.md) を参照。

## 依頼内容(改善要求)

依頼元(架空)から出された要求は次のとおり。

1. **通知件数を大幅に減らすこと。** ただし「監視をやめる」のではなく、対応が必要な通知には確実に気づける状態にすること
2. **重要な通知を絶対に消さないこと。** 減らした結果として見逃しが増えるのでは本末転倒である
3. **記録は全件残すこと。** 通知しなかった内容も、後から必ず追跡できるようにすること
4. **どの通知をどう扱うかのルールを、あとから運用担当者が変更できるようにすること。** スクリプトを書き換えないと調整できない作りは避けること
5. **いきなり本番の通知を止めないこと。** 段階的に移行し、問題があればすぐ元に戻せること
6. **改善の効果を数字で示すこと。** 「減った気がする」ではなく件数で説明できること

具体的な改善の方針は次の4段階とした。

| 段階 | やること | ねらい |
|---|---|---|
| 1. 棚卸し | 過去の通知ログを集計し、種類別の件数を可視化する | **まず現状を数える。** どこから手を付けるべきかを数字で決める |
| 2. 重要度分類 | P1(即時対応)/ P2(翌営業日)/ P3(記録のみ)をルール定義ファイルで管理する | 「全部同じ重さ」をやめる |
| 3. 集約 | 同一種別の連続通知を一定時間内でまとめて1件にする | 情報を失わずに件数だけ減らす |
| 4. 振り分け | P1のみメンション付きで即時通知、P2/P3は別チャンネルと日次サマリへ回す | 「鳴ったら必ず何かある」状態を作る |

| 指標 | 改善前(As-Is) | 改善後(To-Be) | 変化 | 数値の出どころ |
|---|---:|---:|---|---|
| 1日あたりの通知件数 | 200件 | **12件** | **▲94.0%** | 検証環境での実測値 |
| うち即時通知(P1) | 200件 | 4件 | ▲98.0% | 検証環境での実測値 |
| うちまとめ通知(P2) | ― | 7件 | ― | 検証環境での実測値 |
| うち日次サマリ | ― | 1件 | ― | 検証環境での実測値 |
| **記録として残る件数** | **200件** | **200件** | **±0(全件保持)** | 検証環境での実測値 |
| 重要な通知の見逃し | 月2件 | **0件** | ▲2件 | 想定シナリオに基づく試算(検証は実測) |

> **いちばん大事な行は「記録として残る件数」です。**
> 通知は200件から12件へ減らしましたが、記録は200件のまま1件も減っていません。
> この改善は「監視をやめた」のではなく、「**届け方を変えた**」ものです。

## 使用技術・ツール

- **OS**: Ubuntu Server 22.04 LTS(検証環境)
- **Bash 5.1**: 分類・集約・振り分けロジックの実装
- **連想配列(`declare -A`)**: ルールIDをキーにした定義の保持、種類別の件数集計
- **ルール定義ファイル**: `パターン|重要度|通知先` 形式の外部設定ファイル。ロジックと設定の分離
- **正規表現(ERE)**: Bash組み込みの `=~` によるパターン照合(grepプロセスを起動しない高速な判定)
- **状態ファイル(state file)**: 集約ウィンドウ・重複排除・P1発報中フラグの保持
- **jq**: JSON Lines形式の全件記録の生成と集計
- **awk**: 割合・平均などの小数計算と集計
- **cron**: 集約ウィンドウの締め処理と日次サマリの定期実行
- **Slack Incoming Webhook**: 通知先を重要度別に分けた振り分け

## この案件で身につくスキル

- **「まず数える」**という改善の型を身につける(棚卸し → 課題の特定 → 施策 → 効果測定)
- **アラート疲れ**という現象を説明でき、なぜ危険なのかを言葉にできる
- **重要度(severity)設計**の考え方を理解し、「同じ死活NGでも対象が本番かどうかで重要度は変わる」といった線引きを自分で設計できる
- **集約(aggregation)と抑制(suppression)の違い**を説明でき、どちらを使うべきかを判断できる
- 「通知を減らす」ことと「記録を減らす」ことは**まったく別だ**という設計思想を持てる
- しきい値やルールを**設定ファイルへ外出しする理由**を説明でき、実際にそう作れる
- **影実行(shadow mode)による段階的移行**と**ロールバック手順**を設計でき、本番リスクを下げられる
- 改善の効果を**件数・割合の数字**で示し、「消してよかったか」まで検証できる

## 面接でアピールできるポイント(3つ、実際に話すセリフ例つき)

> セリフ例はすべて「架空案件として自分で設計し、検証環境で実測した」という前提で書いています。実務経験として話すことはできません。

### 1. 感覚ではなく数字から入る、改善の進め方

> 「これは学習用に自分で設定した架空の改善案件です。『通知が多すぎる』という課題に対して、いきなり通知を止めるのではなく、まず**棚卸しから始めました**。過去の通知ログを種類別に集計するスクリプトを書いて数えたところ、1日200件のうち上位3種類だけで129件、全体の64%を占めていることが分かりました。逆に、本当に対応が必要だった通知は1日20件、全体の10%でした。**どこを削れば一番効くかが数字で分かってから施策を決めた**ので、削減率94%という結果まで一直線に進められました。この数字は検証環境で実際に200件のサンプル通知を流して測定した実測値です。」

### 2. 「通知を減らす」と「監視をやめる」を分けて考えた設計

> 「この改善でいちばん気をつけたのは、**通知を減らした結果として障害を見逃す**という本末転倒を避けることです。そこで、受け取った通知は**通知するかどうかに関わらず全件JSON Lines形式で記録に残す**という設計にしました。通知は200件から12件へ94%減らしましたが、記録は200件のままです。P3(記録のみ)に落とした通知も、毎朝の日次サマリに必ず載るので、人の目に触れなくなることはありません。加えて、**どのルールにも一致しない未知の通知は自動的にP1として即時通知する**というフェイルセーフも入れています。『分類できないものは安全側に倒す』という考え方です。集約(aggregation)と抑制(suppression)の違い、つまり『まとめて件数の情報を持ち回る』のか『捨てる』のかを区別して設計した点は、面接でも説明できるようにしています。」

### 3. 本番を止めずに切り替える、段階的移行とロールバックの設計

> 「監視の設定変更は、間違えると障害に気づけなくなる怖い作業です。そこで**影実行(shadow mode)**という段階を作りました。第1段階では、新しいルールで判定と記録だけを行い、**通知は従来どおり全件を既存のチャンネルへ流します**。現場の見え方は1ミリも変わりません。その状態で数日ぶん動かしてから、突き合わせスクリプトで『新方式なら何件になるか』『P3に落とす予定の通知の中に本当は重要なものが無いか』を人の目で確認しました。確認が済んでから、設定ファイルの1行を `shadow` から `active` に変えるだけで本稼働に切り替わり、問題があれば同じ1行を戻すだけでロールバックできます。**切り替えとロールバックが同じ1行**という作りにしたのは、慌てている状況でも間違えないようにするためです。」
