# 効果測定ガイド: 何をどう測り、どう正直に語るか

改善案件は「良くなりました」では終われない。**どれだけ良くなったかを数字で示せて初めて、改善の仕事をしたことになる。**

この文書は、改善案件パック全6件で使っている指標の選び方・測り方・語り方をまとめたものである。実務でも学習でもそのまま使える。

---

## 1. 測る前に決めること

測定の前に、次の3つを先に決める。あとから決めると、都合のいい数字を選んでしまう。

| 決めること | 例 |
|---|---|
| 何を良くしたいのか | 作業時間を減らす / ミスを無くす / 気づくのを早くする |
| どの数字で表すか | 分・件数・時間・人数 |
| どう測るか | ストップウォッチ / ログから集計 / 意図的に故障させて計測 |

> 💡 順番が逆になると「測れたものを効果ということにする」になり、説得力が落ちる。**先に目的、次に指標、最後に測定方法**である。

---

## 2. 改善でよく使う6つの指標

改善案件パックで実際に使っている指標は、次の6種類に収まる。まずこれだけ覚えれば十分である。

| 指標 | 意味 | 単位 | 使っている案件 |
|---|---|---|---|
| **作業時間** | 人間が手を動かしている時間 | 分・時間/回・月 | No.1(報告書作成)、No.6(棚卸し) |
| **ミス件数** | 人為ミスの発生回数 | 件/年 | No.1(転記ミス) |
| **検知までの時間** | 問題発生から気づくまで | 分・時間 | No.4(cron失敗)、No.6(構成のズレ) |
| **MTTR** | 平均復旧時間(検知から復旧完了まで) | 分 | No.5(障害対応) |
| **通知件数** | 人が受け取る通知の量 | 件/日 | No.3(アラート過多) |
| **保守の手間** | 1つの修正で触るファイル数・重複行数 | ファイル数・行 | No.2(共通ライブラリ化) |

### 用語の補足

- **MTTR**(Mean Time To Recovery = 平均復旧時間): 障害を検知してから復旧するまでにかかった時間の平均。運用の現場で最もよく使われる指標のひとつ。
- **検知までの時間**: MTTRの手前にある時間。「壊れてから気づくまで」。ここが長いと、復旧が速くても被害は大きくなる。

## 3. 測り方の実際

### 3.1 作業時間を測る

もっとも単純で、もっとも効く。

```bash
# 手作業の時間を測る最も簡単な方法: 開始と終了の時刻を記録する
date '+%Y-%m-%d %H:%M:%S'   # 作業開始時に実行
# ... 手作業 ...
date '+%Y-%m-%d %H:%M:%S'   # 作業終了時に実行
```

自動化後の時間は、`time` コマンドで測れる。

```bash
time ./generate_report.sh 2026-08
```

```text
real    0m1.812s     ← 実際に経過した時間(これを使う)
user    0m0.402s
sys     0m0.271s
```

**ポイント: 3回測って平均を取る。**1回だけだと、たまたま遅かった/速かったが混ざる。

### 3.2 件数をログから数える

ミス件数・通知件数は、記録から数えるのが最も正確である。

```bash
# 例: 通知ログから1日あたりの通知件数を数える
awk '{print $1}' notify.log | sort | uniq -c
```

```text
    198 2026-08-25
    212 2026-08-26
    203 2026-08-27
```

### 3.3 「気づくまでの時間」を測る

これは**意図的に壊して測る**のが唯一の方法である。改善案件No.4では、次の試験を行っている。

| 試験 | やり方 | 測るもの |
|---|---|---|
| 失敗検知 | わざと失敗するジョブを1本走らせる | 通知が届くまでの時間 |
| 未実行検知 | ジョブをわざと実行しない | 未実行と判定されるまでの時間 |

改善案件No.5(障害対応)も同様に、**障害を意図的に再現して復旧訓練の時間を測る**。実務の防災訓練と同じ発想である。

### 3.4 コードの重複を数える

改善案件No.2では、コード量そのものが指標になる。

```bash
# 重複している関数が何行あるかを数える(例: log 関数の定義行を探す)
grep -rn '^log()' projects/*/src/*.sh
```

数え方(何を1件と数えたか)を必ず書く。数え方が違えば数字も変わるため、**数え方を書かない数字は比較できない**。

## 4. 数字を正直に扱う3つのルール

未経験者のポートフォリオで最も危険なのは、**架空の数字が実務実績のように読めてしまう**ことである。改善案件パックでは次を徹底している。

### ルール1: 出どころを書く

| 書き方 | 意味 |
|---|---|
| 「検証環境で実測」 | 自分の手元で実際に測った値 |
| 「想定シナリオに基づく試算」 | 架空の運用を前提に計算した値 |
| 「リポジトリの実コードを対象に計測」 | このリポジトリのコードを数えた値(改善案件No.2) |

### ルール2: 前提条件を書く

- 対象は何台か / 何本か
- 期間はどれくらいか
- 何回測った平均か

### ルール3: できなかったことを書く

すべての指標が改善した報告は、かえって疑われる。改善案件パックの `05-effect-measurement.md` には必ず「**達成できなかったこと・残課題**」の節がある。

> 💡 「盛らない」のは誠実さのためだけではない。**面接で深掘りされても崩れない**という実利がある。前提条件まで説明できる数字は、そのまま技術力の証明になる。

---

## 5. 面接で語れる数字の作り方

数字は、次の3点セットにすると伝わる。

```text
【問題】 何が、どれくらい悪かったか(数字)
【判断】 なぜその解決策を選んだか(選択肢の比較)
【結果】 どれだけ良くなったか(同じ物差しのBefore/After)+ 前提の注記
```

### 良い例

> 「監視通知が1日約200件出ていて、9割が対応不要でした。全員が通知を見なくなり、重要な通知の見逃しが月2件発生していました。
> 通知そのものを止める案もありましたが、それでは記録まで失われるため、**重要度をP1〜P3に分類して通知先を分け、記録は全件残す**設計にしました。
> 結果、通知は1日約12件まで減り、見逃しはゼロになりました。これは架空の運用を想定した案件で、件数は検証環境のサンプルログで測った値です。」

### 避けたい例

> 「監視を改善して、通知を94%削減しました。」

数字だけが独り歩きしていて、**何を犠牲にしたのか・どう判断したのか**が見えない。面接官は「重要な通知まで消したのでは?」と考える。

## 6. 数字にならない効果の扱い

すべての改善が数字になるわけではない。次のような効果は、**数字にせず言葉で書く**のが正しい。

| 数字にしにくい効果 | 書き方の例 |
|---|---|
| 属人化の解消 | 「担当者1人しかできなかった作業を、コマンド1つで誰でも実行できるようにした」 |
| 心理的負担の軽減 | 「夜間に手順書を見ながら手打ちする不安を、診断の自動化で減らした」 |
| 追跡可能性 | 「作業記録が個人メモ頼りだったものを、監査ログとして残るようにした」 |

無理に数値化すると根拠のない数字になる。**測れないものは測れないと書く**ほうが信頼される。

## 7. 改善案件パック6件の指標一覧

各案件がどの指標で効果を示しているかの一覧である。同じ型の繰り返しであることが分かる。

| No. | 案件 | 主な指標 | Before → After |
|---|---|---|---|
| 1 | 月次報告書の自動生成 | 作業時間 / ミス件数 | 3時間/月 → 5分/月、年6件 → 0件 |
| 2 | 共通ライブラリ化 | 保守の手間 / 潜在バグ | 4ファイル → 1ファイル、バグ2箇所 → 0箇所 |
| 3 | アラート過多の改善 | 通知件数 / 見逃し件数 | 200件/日 → 12件/日、月2件 → 0件 |
| 4 | cron実行の可視化 | 検知までの時間 | 平均18時間 → 5分以内 |
| 5 | 障害対応の半自動化 | MTTR / 情報収集時間 | 40分 → 12分、15分 → 30秒 |
| 6 | 構成ドリフト検知 | 作業時間 / 発見までの時間 | 8時間/四半期 → 0、最大3か月 → 翌日 |

いずれも**架空の運用シナリオに基づく設定**であり、各案件の `05-effect-measurement.md` に測定方法と前提条件を明記している。
