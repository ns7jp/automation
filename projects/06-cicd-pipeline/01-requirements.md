# 01. 要件定義書

案件No.6「GitHub ActionsによるCI/CD自動デプロイパイプライン構築」の要件を定義する。

## 1. 背景・目的

株式会社サンプル商事では、社内向けの簡易コーポレートサイト(Webアプリ)を運用しており、内容の更新は開発担当のエンジニアが手作業で行っていた。具体的には、ローカルで修正したファイルを`scp`コマンドでサーバーへ1つずつ転送する、という運用だった。

この運用には、次のような問題があった。

- 転送するファイルを人間が目視で選んでいるため、**更新したはずのファイルを転送し忘れる**ことがあった
- 転送手順(接続情報・転送先パス・転送後の確認方法)が**担当者の頭の中にしかなく、属人化**していた(担当者不在時に他の人が対応できない)
- 「テストを通してから反映する」という決まったルールが無く、**動作確認が不十分なまま本番に反映してしまう**ことがあった
- 手作業のため、反映作業そのものに毎回時間がかかっていた

この課題を解決するため、以下を目的としてCI/CD(=継続的インテグレーション/継続的デリバリー。詳細は[02-design.md](./02-design.md)で解説)の自動化パイプラインを構築する。

- GitHubリポジトリの`main`ブランチへpushするだけで、**人手を介さず自動でテスト・デプロイ**が行われるようにする
- テストに失敗した場合は**自動的にデプロイを止める**ことで、動作確認が不十分な状態が本番に反映されるのを防ぐ
- SSH接続情報や秘密鍵などの機密情報を、**コードから完全に切り離してGitHub Secretsで安全に管理**する
- デプロイの成功/失敗が、GitHub Actions上・Slack通知の両方から**誰でもすぐに分かる**ようにする

## 2. 機能要件

| 要件ID | 要件名 | 詳細 | 優先度 |
|---|---|---|---|
| FR-01 | pushトリガーによる自動実行 | `main`ブランチへのpushをトリガーに、GitHub Actionsのワークフローが自動的に起動すること | 必須 |
| FR-02 | pull_requestトリガーによるテスト先行実行 | `main`ブランチ向けのpull_requestが作成・更新された際にも、テストジョブだけは自動実行されること(デプロイはされない)。mainへ取り込む前に問題を検知するため | 必須 |
| FR-03 | シェルスクリプトの構文チェック(shellcheck) | リポジトリ内のシェルスクリプト(`.sh`ファイル)に対して、`shellcheck`による静的解析(=プログラムを実行せずにコードを検査すること)を自動実行すること | 必須 |
| FR-04 | サンプルアプリの簡易テスト | デプロイ対象のサンプルWebアプリに対し、必須ファイルの存在確認・HTMLの基本構造チェックなど、簡易的な自動テストを実行すること | 必須 |
| FR-05 | テスト成功時のみデプロイを実行 | FR-03・FR-04のテストがすべて成功した場合のみ、デプロイ処理(FR-06)を実行すること。1つでも失敗した場合はデプロイを行わないこと | 必須 |
| FR-06 | SSH経由の自動ファイル転送・反映 | テスト成功後、`main`ブランチへのpushの場合に限り、SSH経由(`rsync`)で検証用/本番サーバーへ自動的にファイルを転送・反映すること | 必須 |
| FR-07 | 機密情報のSecrets管理 | SSH秘密鍵・接続先ホスト名・ユーザー名など、漏えいすると被害につながる情報は、すべてGitHub Secretsに登録した値を使用し、ワークフローファイルやスクリプトのコード中に直接書かないこと | 必須 |
| FR-08 | GitHub Actions上での成否確認 | ワークフローの各ジョブ・各ステップの成功/失敗が、GitHub ActionsのUI(またはCLI)上で確認できること | 必須 |
| FR-09 | デプロイ結果の通知 | デプロイジョブの成功/失敗を、Slackへの通知メッセージとして送信すること | 必須 |
| FR-10 | 手動実行トリガー(発展要件) | `workflow_dispatch`により、pushを伴わずにGitHubのActions画面から手動でワークフローを実行できること | 推奨 |
| FR-11 | 多重デプロイの防止(発展要件) | 短時間に複数回pushされた場合でも、デプロイ処理が同時に2つ以上実行されないよう排他制御すること | 推奨 |

## 3. 非機能要件

| 要件ID | 分類 | 要件 | 補足 |
|---|---|---|---|
| NFR-01 | セキュリティ | 秘密鍵・接続情報はGitHub Secretsのみで管理し、ログにも平文で出力されないこと | GitHub ActionsはSecretsの値をログ上で自動的に`***`へマスクする。加えてワークフロー自体にも最小権限(`permissions: contents: read`)を設定する |
| NFR-02 | べき等性(=同じ処理を何度実行しても結果が同じになる性質) | 同じ内容を何度デプロイしても、サーバー上のファイルが同じ状態に収束すること | `rsync --delete`により、転送元に無いファイルは転送先からも削除し、常に「今のリポジトリの内容」と一致させる |
| NFR-03 | 可用性・排他制御 | 短時間に複数回pushされても、デプロイ処理同士が競合してファイルが壊れないこと | `concurrency`設定により、同じデプロイの多重実行を防ぐ([02-design.md](./02-design.md) 4.7節) |
| NFR-04 | 保守性 | デプロイ処理の中身(接続方法・転送コマンド)をCI専用の特別な実装にせず、人が手元でも同じ処理を再現できること | `scripts/deploy.sh`をワークフローと手動実行の両方から共通で呼び出す構成にする |
| NFR-05 | 追跡性 | いつ・どのコミットがデプロイされたかを、後から確認できること | デプロイのたびに`deploy-info.txt`へコミットハッシュと日時を記録し、GitHub Actionsの実行履歴からもログを参照できる |
| NFR-06 | 実行速度・コスト | 1回のワークフロー実行(テスト+デプロイ)が数分以内に完了すること | GitHub-hosted runner(`ubuntu-latest`)を利用し、追加のサーバー費用をかけずに構築できること |
| NFR-07 | 移植性 | GitHubが提供するホスト型ランナー(GitHub-hosted runner)だけで完結し、自前のCIサーバー構築が不要なこと | 自己ホストランナー(self-hosted runner)の構築は今回のスコープ外とする(4章参照) |

## 4. スコープ外(今回は対応しない範囲)

- 単体テスト・結合テスト・E2Eテストなど、本格的なテストフレームワーク(pytest、Jest等)を用いた高度な自動テストの実装。今回は「テストが自動実行され、失敗したらデプロイが止まる」というCI/CDパイプラインの骨格を学ぶことを主目的とし、テスト自体はshellcheckと簡易チェックスクリプトにとどめる
- Blue-Greenデプロイ・カナリアリリースなど、無停止・段階的リリースを実現する高度なデプロイ戦略
- GitHub Environments機能を使った「本番デプロイ前に人間が承認する」という承認フロー(発展的な話題として[02-design.md](./02-design.md) 6章で軽く触れるにとどめる)
- 自己ホストランナー(self-hosted runner)の構築・運用
- 検証用サーバーと本番サーバーへの同時デプロイなど、複数環境を切り替える仕組み(今回は単一の対象サーバーへのデプロイを扱う)
- Dockerコンテナ化・コンテナレジストリへのpush等、コンテナベースのデプロイ

## 5. 検証環境

実際の構築・動作確認は、以下の環境を想定して行う。

| 項目 | バージョン等 |
|---|---|
| GitHub Actionsランナー | `ubuntu-latest`(実行時点でUbuntu 24.04 LTS相当。GitHub側で随時更新される点に注意) |
| actions/checkout | v4 |
| shellcheck | 0.9.0(Ubuntu標準パッケージ。バージョンが前後しても本文中のオプションは同様に動作する) |
| rsync | 3.2.7 |
| OpenSSH(client) | 9.x系 |
| Bash | 5.x系(GitHub Actionsランナー標準) |
| デプロイ先サーバーOS | Ubuntu Server 22.04 LTS |
| デプロイ先Webサーバー | nginx(ファイル配信のみ。設定自体は案件外なのでインストール手順のみ示す) |
| GitHub CLI(`gh`) | 2.x系(ワークフローの実行状況をターミナルから確認する際に使用。任意) |
| Git | 2.x系 |
| 通知先 | Slack(Incoming Webhook) |

> 💡 GitHub Actionsは「クラウド上で動くCIサーバー」で、GitHubが用意した仮想マシン(ランナー)がジョブのたびに新しく起動し、終わったら破棄される。そのため、構築するのは「監視対象サーバー」のようなサーバー1台ではなく、「GitHubリポジトリの設定」と「デプロイ先サーバーの受け入れ準備」の2つが中心になる、という点が案件No.1〜No.5とは異なる。

## 6. 想定するデプロイ対象・接続情報(サンプル)

実際に構築・検証する際に前提とする、サンプルの接続情報を以下に示す(実際の値はGitHub Secretsに登録し、コードには書かない。詳細は[03-build-guide.md](./03-build-guide.md)参照)。

| 項目 | Secret名 | サンプル値 | 用途 |
|---|---|---|---|
| 接続先ホスト | `DEPLOY_HOST` | `192.168.1.30` | デプロイ先サーバーのIPアドレス/ホスト名 |
| SSH接続ユーザー | `DEPLOY_USER` | `deploy` | デプロイ専用に作成するSSHユーザー |
| SSHポート | `DEPLOY_PORT` | `22` | SSH接続に使うポート番号 |
| 配置先パス | `DEPLOY_PATH` | `/var/www/sample-app` | サーバー上でWebアプリを配置するディレクトリ |
| SSH秘密鍵 | `DEPLOY_SSH_KEY` | (鍵の中身そのもの) | CI専用に発行するSSH鍵ペアの秘密鍵 |
| Slack通知先 | `SLACK_WEBHOOK_URL` | `https://hooks.slack.com/services/...` | デプロイ結果の通知先Webhook URL |

すべて[03-build-guide.md](./03-build-guide.md)の手順内で、実際にGitHubリポジトリのSecretsとして登録していく。
