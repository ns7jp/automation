# 案件No.4: サーバー死活監視・障害検知ツール

## 難易度

★★★☆☆(中級)

pingとHTTPステータスコードという2種類の監視方式を扱い、さらに「状態ファイルを使った連続失敗回数の管理」「Markdownレポートの自動生成」「稼働率の集計」という複数の技術要素を組み合わせて設計する必要がある。単純に「1つのコマンドを定期実行する」だけの自動化(案件No.1・No.2)よりも、「複数回の実行にまたがる状態を、ファイルを介してどう引き継ぐか」という設計力が問われるため、中級に位置づけている。

## 想定依頼元・背景

| 項目 | 内容 |
|---|---|
| 依頼元 | 株式会社サンプル商事(架空社名。案件No.1・No.2と同一の会社という想定) |
| 部署 | 情報システム部門(担当者1名体制) |
| 課題 | 事業拡大に伴いサーバー台数が3〜5台に増えたが、死活監視は担当者が毎朝手動でアクセスしてExcel台帳に記入する運用のままだった。担当者の確認漏れや休日の対応漏れにより、障害発生から気づくまでに数時間かかることがあった |
| 要望 | 「対象サーバーが生きているかを自動でチェックし、レポートと通知をしてほしい」。ただし、一時的な通信の揺らぎで頻繁に誤通知が来るのも困る、という要望も併せて受けている |

「複数台のサーバーを、限られた人数で運用する」という中小企業でよくある状況において、死活監視の自動化は最初に着手されることが多い定番のテーマ。本案件はその典型例を題材にしている。

## 依頼内容(要求仕様)

- 監視対象サーバーのリスト(IPアドレス/ホスト名、監視方法)を設定ファイルで管理できるようにすること
- pingによる死活監視と、Webサーバーに対してはHTTPステータスコードによる監視(`curl`)の両方に対応すること
- 5分ごとにcron(=Linuxで、決まった時刻・間隔に処理を自動実行するための仕組み)で実行し、結果を記録すること
- 連続して2回以上NGが続いたサーバーがあれば異常とみなして通知すること(1回だけの失敗で誤検知しないようにする)
- 監視結果を一覧できるレポート(Markdown形式)を自動生成すること
- (発展要件)過去の稼働率(直近24時間の成功率など)を集計できるようにすること

詳細は[01-requirements.md](./01-requirements.md)を参照。

## 使用技術・ツール

| 分類 | 技術・コマンド |
|---|---|
| シェル | Bash(`#!/usr/bin/env bash`) |
| 死活監視(ネットワーク層) | `ping -c` / `-W`(ICMPによる生死確認) |
| 死活監視(アプリケーション層) | `curl -o /dev/null -s -w '%{http_code}'`(HTTPステータスコードによる確認) |
| 状態管理 | 連想配列(`declare -A`。「名前」をキーにして値を出し入れできる配列)+ CSV形式の状態ファイル(`state.csv`)による連続失敗回数の管理 |
| 定期実行 | `cron`(`*/5 * * * *`) |
| レポート生成 | ヒアドキュメント(`<<EOF`)によるMarkdown組み立て |
| 稼働率集計 | `awk` + `date -d`(タイムスタンプの文字列比較による期間絞り込み) |
| 通知 | `curl`によるSlack Incoming Webhook(=あらかじめ発行されたURLへHTTPでデータを送るだけでSlackにメッセージを投稿できる仕組み)連携 |
| ログ出力 | `tee -a`(標準出力とログファイルへの同時出力) |
| 検証環境 | Ubuntu Server 22.04 LTS |

## この案件で身につくスキル

- `ping`と`curl`という2種類の死活監視手法を、それぞれの仕組み(ICMP/HTTP)から理解した上で使い分けられる
- HTTPステータスコード(2xx/3xx/4xx/5xx)の基礎を理解し、「応答はあるが異常」というケースまで検知できる監視設計ができる
- cronで繰り返し起動される「独立したプロセス」同士で、状態ファイルを介して情報を引き継ぐ(=前回の結果を次回に持ち越す)実装ができる
- 「誤検知(フラッピング)を防ぐための閾値」という、監視設計における最も基本的かつ重要な考え方を理解し、実装できる
- ヒアドキュメントを使って、シェルスクリプトから構造化されたMarkdownドキュメントを自動生成できる
- `awk`とタイムスタンプの文字列比較を組み合わせた、簡易的な集計処理(稼働率計算)が書ける

## 面接でアピールできるポイント(3つ、実際に話すセリフ例つき)

1. **「なぜ1回の失敗で通知しないのか」を、閾値・フラッピングという概念で説明できる**

   > 「単純に監視結果がNGになった瞬間に通知する作りにすると、一時的な通信の揺らぎだけで管理者に通知が飛んでしまい、いわゆる"オオカミ少年"状態になると考えました。そこで、`state.csv`という状態ファイルに各サーバーの連続失敗回数を記録し、閾値(既定2回)を超えたときにだけ通知する仕組みにしています。cronは5分ごとに毎回独立したプロセスとしてスクリプトを起動するので、"前回の結果"をプログラムの変数ではなくファイルに保存して引き継ぐ、という設計にした点も工夫したところです。」

2. **ping(ネットワーク層)とHTTP(アプリケーション層)、2種類の監視を使い分けて実装した**

   > 「DBサーバーのようにHTTPサービスを持たないサーバーは`ping`で、Webサーバーは`curl -w '%{http_code}'`でHTTPステータスコードそのものを見て監視するようにしました。単に'応答が返ってくるか'だけでなく、'`404`や`500`のようにサーバーは動いているが正常なページを返せていない状態'まで検知できるように、期待するステータスコードをサーバーごとに設定ファイルで指定できる設計にしています。」

3. **通知して終わりにせず、Markdownレポートと稼働率の"見える化"まで実装した**

   > 「障害を通知するだけでなく、`history.csv`に全チェック結果を蓄積し、直近24時間の稼働率をサーバーごとに集計してMarkdownレポートに出力するようにしました。ヒアドキュメントで表の枠組みを組み立て、`awk`でタイムスタンプの文字列比較(ISO形式なら辞書式ソート=時系列ソートになる、という性質を利用)を使って集計する、という実装です。'今は復旧しているが、実は過去に何度も落ちていた'という傾向まで一覧できるようにした点が、単なる通知ツールとの違いだと考えています。」
