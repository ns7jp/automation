# 01. 要件定義書

案件No.4「サーバー死活監視・障害検知ツール」の要件を定義する。

## 1. 背景・目的

株式会社サンプル商事では、案件No.1・No.2などを通じてサーバー台数が徐々に増え、現在はWebサーバー・DBサーバー・アプリケーションサーバーなど3〜5台規模の構成で運用している。

これまで各サーバーが生きているかどうかの確認は、担当者が毎朝ブラウザやSSHで1台ずつアクセスし、その結果をExcel台帳に手入力するという運用だった。しかしこの方法には次のような問題があった。

- 担当者が確認を忘れる、あるいは休みの日は誰もチェックしない
- 障害が発生してから、利用者からの問い合わせで気づくまで数時間かかることがあった
- 「いつから落ちていたのか」「どのくらいの頻度で発生しているか」を後から追跡できない

この課題を解決するため、以下を目的として死活監視・障害検知ツールを構築する。

- サーバーの生死確認を**人の記憶・手作業に頼らず自動化**する
- 一時的な通信の揺らぎで**誤って通知しすぎない**(=誤検知を防ぐ)仕組みにする
- 障害の発生・復旧を**自動で検知して通知**する
- 現在の状況と過去の傾向を**一覧できるレポート**を自動生成する

## 2. 機能要件

| 要件ID | 要件名 | 詳細 | 優先度 |
|---|---|---|---|
| FR-01 | 監視対象リストの外部ファイル管理 | 監視対象サーバーの名前・IPアドレス(またはホスト名)・監視方法(ping/http)を、スクリプト本体とは別の設定ファイル(`targets.conf`)で管理できること | 必須 |
| FR-02 | ping監視 | `ping`コマンドを用いて、対象サーバーがICMPに応答するか(ネットワーク的に生きているか)を確認できること | 必須 |
| FR-03 | HTTP監視 | `curl`コマンドを用いて、対象URLへアクセスし、返ってきたHTTPステータスコードが期待値(既定`200`)と一致するかを確認できること | 必須 |
| FR-04 | 定期自動実行 | `cron`を用いて5分ごとに監視処理を自動実行すること | 必須 |
| FR-05 | 監視結果の記録 | 毎回のチェック結果(成功/失敗)を、後から集計・追跡できる形式でファイルに記録すること | 必須 |
| FR-06 | 連続失敗による異常判定(誤検知対策) | 1回の失敗だけでは異常とみなさず、**連続して2回以上NG**が続いた場合にのみ「異常」と判定し通知すること(閾値は設定で変更可能) | 必須 |
| FR-07 | 障害・復旧の通知 | FR-06で異常と判定した際に管理者へ通知すること。また、異常判定中のサーバーが正常に戻った場合は「復旧」を通知すること | 必須 |
| FR-08 | 通知の重複防止 | 異常判定中に閾値を超え続けても、通知は状態が変化した(異常になった/復旧した)タイミングでのみ送信し、5分ごとに同じ通知を連発しないこと | 必須 |
| FR-09 | Markdownレポートの自動生成 | 全監視対象の現在の状態(OK/NG、連続失敗回数など)を一覧できるレポートを、チェックのたびにMarkdown形式で自動生成すること | 必須 |
| FR-10 | 稼働率の集計(発展要件) | 直近24時間の成功率(稼働率)をサーバーごとに集計し、レポートに含めること | 推奨 |
| FR-11 | 設定の外部化 | 閾値・タイムアウト秒数・通知先など、運用中に調整したい値を設定ファイル(`health_check.conf`)に分離し、スクリプト本体を変更せずに調整可能にすること | 推奨 |

## 3. 非機能要件

| 要件ID | 分類 | 要件 | 補足 |
|---|---|---|---|
| NFR-01 | 可用性 | 1台のサーバーへのチェックが失敗・タイムアウトしても、残りのサーバーのチェックとレポート生成が必ず最後まで実行されること | `ping`/`curl`にタイムアウトを設定し、1台の遅延が全体の処理停止につながらないようにする |
| NFR-02 | べき等性(=同じ処理を何度実行しても結果が同じ・壊れない性質) | 監視処理を同時刻に複数回実行しても、状態ファイルが不整合な内容で壊れないこと | 状態ファイルは一時ファイルに書き出してから`mv`で置き換える(処理途中で中断しても中途半端な内容で上書きされない) |
| NFR-03 | セキュリティ | Slack Webhook URLなどの秘匿情報を含む設定ファイルは、rootまたは実行ユーザーのみ読み取り可能にすること | `chmod 600 health_check.conf`を徹底する |
| NFR-04 | 保守性 | 監視対象の追加・削除、閾値の変更などが、スクリプト本体を編集せずに設定ファイルの変更だけで完結すること | `targets.conf` / `health_check.conf` にすべての可変値を切り出す |
| NFR-05 | 監視性(ログの追跡性) | ログにはタイムスタンプとログレベル(INFO/WARN/ERROR)を付与し、いつ・どのサーバーで何が起きたかを後から追跡できること | 障害発生時の原因調査・報告に使う |
| NFR-06 | 性能 | 1回の監視処理(全対象分)が、次回の実行(5分後)までに確実に完了すること | ping・curlそれぞれにタイムアウトを設け、対象サーバーが多くても処理全体が長時間化しないようにする |
| NFR-07 | 拡張性 | 監視対象サーバーの台数が増減しても、`targets.conf`に行を追加・削除するだけで対応できること | 台数の上限をスクリプト内にハードコードしない |
| NFR-08 | データ保持 | 稼働率集計に必要な履歴データを、少なくとも直近24時間分は保持していること | 履歴ファイル(`history.csv`)自体の自動削除・世代管理は今回のスコープ外とする(4章参照) |

## 4. スコープ外(今回は対応しない範囲)

- CPU使用率・メモリ使用率・ディスク使用率など、死活(生きているかどうか)以外のリソース監視
- 障害検知後の自動復旧アクション(サービスの自動再起動など)。今回は「検知して知らせる」ところまでを対象とする
- 監視サーバー自体の冗長化(監視サーバーがダウンした場合の代替経路確保)
- `history.csv`の肥大化対策(世代管理・ローテーション)。案件No.2で扱った`logrotate`のような仕組みは、運用が長期化した際の追加検討事項として位置づける
- メール(SMTP)による通知。今回は案件No.2と同様、検証環境での再現性を優先しSlack Incoming Webhookのみを実装する

## 5. 検証環境

実際の構築・動作確認は、以下の環境を想定して行う(ローカルVMまたはコンテナでの再現を想定)。

| 項目 | バージョン等 |
|---|---|
| OS | Ubuntu Server 22.04 LTS |
| シェル | bash 5.1.16 |
| ping(iputils-ping) | 3:20211215-1(Ubuntu 22.04標準) |
| curl | 7.81.0 |
| coreutils(date, mktemp等) | 8.32 |
| awk | mawk 1.3.4(Ubuntu標準の`/usr/bin/awk`)。gawkでも同様に動作する |
| cron | cron 3.0pl1(Ubuntu標準) |
| Python(動作確認用の簡易HTTPサーバー) | Python 3.10系(`python3 -m http.server`。動作確認時のみ使用し、本番運用では既存のWebサーバーを対象にする) |
| 実行ユーザー | root、または監視対象への通信と`crontab`登録権限を持つ運用ユーザー |
| 監視対象例 | Webサーバー2〜3台(HTTP監視)、DB/アプリケーションサーバー1〜2台(ping監視)の計3〜5台 |

> 💡 バージョンが多少前後しても、本ドキュメントで使用するオプション(`ping -c/-W`、`curl -o -s -w`、`date -d`など)は標準的なGNU/Linux実装であれば同様に動作する。

## 6. 想定する監視対象サーバー一覧(サンプル)

実際に構築・検証する際に前提とする、サンプルの監視対象一覧を以下に示す(詳細は[src/targets.conf](./src/targets.conf)参照)。

| 名前 | 種別 | 監視方法 | 監視対象 | 正常とみなす条件 |
|---|---|---|---|---|
| web01 | Webサーバー | http | `http://192.168.1.11/` | HTTPステータスコード`200` |
| web02 | Webサーバー | http | `https://192.168.1.12/` | HTTPステータスコード`200` |
| api01 | APIサーバー | http | `http://192.168.1.13:8080/healthz` | HTTPステータスコード`200` |
| db01 | DBサーバー | ping | `192.168.1.21` | ICMP応答あり |
| app01 | アプリケーションサーバー | ping | `192.168.1.22` | ICMP応答あり |

自宅・検証用のVM1台だけで動作確認する場合の代替手順は[03-build-guide.md](./03-build-guide.md)を参照。
