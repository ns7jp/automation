# 04. テスト仕様書

[03-build-guide.md](./03-build-guide.md)の手順で構築した環境に対して実施するテストケース一覧。正常系(想定通りに動くこと)と異常系(想定外の状況でも安全に倒れること)の両方を確認する。

## 1. テスト方針

- 本物の複数サーバーが無くても再現できるよう、`python3 -m http.server`によるダミーのWebサーバーや、あえて閉じたポートを使って擬似的に障害状態を作り出す(詳細は[03-build-guide.md](./03-build-guide.md) Step 5参照)
- 「連続失敗による通知」の検証は、`health_check.sh`を短い間隔で複数回手動実行することで、5分間隔のcron実行を疑似的に再現する
- テスト後は`targets.conf`・`health_check.conf`を必ず元の値(実運用向けの内容)に戻す

## 2. テストケース一覧

| テストID | 分類 | 前提条件 | 操作手順 | 期待結果 |
|---|---|---|---|---|
| TC-01 | 正常系 | `type=ping`の対象(`127.0.0.1`など疎通可能なホスト)が`targets.conf`にある | `sudo /opt/server-health-check/health_check.sh`を実行する | ログに`は正常です`と記録され、`state.csv`の該当行が`OK,0,no`になる |
| TC-02 | 正常系 | `type=http`の対象(疎通可能なURL、期待コード`200`)が`targets.conf`にある | 同上を実行する | ログに`は正常です`と記録され、`state.csv`の該当行が`OK,0,no`になる |
| TC-03 | 正常系 | `FAIL_THRESHOLD=2`。対象サーバーが1回目のチェックでNGになる状態 | `health_check.sh`を1回実行する | ログレベルは`WARN`(`ERROR`ではない)。`state.csv`の連続失敗回数が`1`、`notified`が`no`のまま。Slack通知は送られない |
| TC-04 | 正常系 | TC-03に続けて、対象サーバーが引き続きNGの状態 | `health_check.sh`をもう1回実行する(連続2回目のNG) | ログレベルが`ERROR`になり「閾値を超えたため異常として通知します」と記録される。`state.csv`の`notified`が`yes`になる。Slackに`🔴 [障害検知]`メッセージが届く |
| TC-05 | 正常系 | TC-04実施済み(`notified=yes`)で、対象サーバーが引き続きNGの状態 | `health_check.sh`をさらに1回実行する(連続3回目のNG) | ログレベルは`WARN`に戻り、`ERROR`(異常検知ログ)は出力されない。Slackへの追加通知が送られない(通知の重複防止) |
| TC-06 | 正常系 | TC-05実施済みの対象サーバーを、実際にOKへ復旧させる | `health_check.sh`を実行する | ログに「復旧しました」と記録される。`state.csv`の該当行が`OK,0,no`に戻る。Slackに`✅ [復旧]`メッセージが届く |
| TC-07 | 正常系 | 対象サーバーが1回だけNGになった直後、閾値に達する前にOKへ戻る状態 | 1回目NG→2回目実行前にOKへ復旧させ、`health_check.sh`を2回実行する | 1回目は`WARN`のみで通知なし。2回目はOKになるが、`notified`はもともと`no`のため復旧通知も送られない(「異常と判定していないものは復旧とも言わない」という対称性の確認) |
| TC-08 | 正常系 | 監視対象が3台以上`targets.conf`に定義されている | `health_check.sh`を実行する | `history.csv`に、実行時刻ごとに対象台数分の行が1回の実行で追記される。列は`timestamp,name,type,target,status`の5列 |
| TC-09 | 正常系(発展要件) | 同一サーバーについて、直近の`history.csv`にOK 3件・NG 1件が記録されている | `health_check.sh`を実行し、生成された`report.md`の当該サーバーの稼働率列を確認する | 稼働率が`75.0%`(3÷4×100)と表示される |
| TC-10 | 正常系 | `history.csv`に対象サーバーの記録が1件も無い状態(監視対象を新規追加した直後など) | `health_check.sh`を実行し、`report.md`を確認する | 稼働率列が`N/A`と表示され、`0.0%`のような誤った数値にならない(ゼロ除算を回避できている) |
| TC-11 | 正常系 | 構築直後、`report.md`がまだ存在しない状態 | `health_check.sh`を実行する | `report.md`が新規生成され、Markdownの表形式(ヘッダー行・区切り行・データ行)として正しくパースできる内容になっている |
| TC-12 | 正常系(べき等性) | 同時刻近くに`health_check.sh`を続けて2回実行する | 1回目の実行が完了した直後に、間を空けず2回目を実行する | 2回とも正常終了し(終了コード`0`)、`state.csv`が壊れた内容(行の欠落・文字化け等)にならない |
| TC-13 | 正常系 | `targets.conf`に新しい監視対象を1行追加する | `health_check.sh`本体は変更せず、`targets.conf`に1行追加してから実行する | 追加した対象もチェック対象に含まれ、ログ・`state.csv`・`report.md`すべてに反映される(スクリプト本体の変更が不要であることの確認) |
| TC-14 | 異常系 | `/opt/server-health-check/health_check.conf`を一時的にリネームして存在しない状態にする | `sudo /opt/server-health-check/health_check.sh`を実行する | 「設定ファイルが見つかりません」というメッセージが標準エラー出力に表示され、終了コード`1`で即座に終了する(ログファイルへの書き込みは行われない) |
| TC-15 | 異常系 | `targets.conf`を一時的にリネームして存在しない状態にする | 同上を実行する | 「監視対象リストが見つかりません」というメッセージが表示され、終了コード`1`で終了する |
| TC-16 | 異常系 | `targets.conf`のtype列に`ping`/`http`以外の文字列(例: `dummy`)を指定した行を追加する | `health_check.sh`を実行する | 該当行はログに`未知の監視方法です`という`ERROR`とともにスキップされ、他の正常な対象のチェックとレポート生成は最後まで実行される(1件のエラーが全体を止めない) |
| TC-17 | 異常系 | 監視対象サーバーへの接続自体ができない状態(サーバー停止・ポート未使用など) | `health_check.sh`を実行する | `type=ping`なら`ping`の終了コードが非0、`type=http`なら`curl`の`%{http_code}`が`000`となり、いずれも`NG`と判定される |
| TC-18 | 異常系 | `type=http`の対象が`404`など期待値(`200`)と異なるステータスコードを返す状態 | `health_check.sh`を実行する | `actual_code`(`404`)と`expected_code`(`200`)が不一致のため`NG`と判定される(サーバーは応答しているが異常として扱われることの確認) |
| TC-19 | 異常系 | `health_check.conf`の`SLACK_WEBHOOK_URL`を無効な値(存在しないURL)に一時変更し、TC-04相当の閾値超えを発生させる | `health_check.sh`を実行する | `curl`によるSlack通知自体は失敗するが、その失敗によってスクリプトが異常終了することはない。ログへの`ERROR`記録・`state.csv`の更新は正しく行われる(通知失敗がログ記録を妨げない) |
| TC-20 | 異常系 | `health_check.sh`の実行権限(`x`)を外した状態(`chmod -x`) | `/opt/server-health-check/health_check.sh`を直接実行する | `Permission denied`となり実行できない。`bash /opt/server-health-check/health_check.sh`のように明示的にインタプリタを指定すれば実行できることを確認する |

## 3. テスト結果の記録方法

各テストケースについて、実施日・実施者・結果(OK/NG)・ログの抜粋を記録する。以下は記録テンプレートの例。

```text
テストID: TC-04
実施日: 2026-08-31
実施者: (氏名)
結果: OK
ログ抜粋:
  2026-08-31 10:20:14 [ERROR] down-web(http://127.0.0.1:8081/)が2回連続でNGです。閾値(2回)を超えたため異常として通知します
備考: state.csvのnotified列がyesに変わったことを確認済み。Slackにも通知が届いた。
```

## 4. 完了基準

- TC-01〜TC-20のすべてが期待結果通りであること
- 異常系テスト(TC-14〜TC-19)で変更した設定値・ファイル名が、テスト後にすべて元の状態へ戻っていること
- Slack通知(異常検知・復旧の両方)が実際にチャンネルへ届くことを、目視で最低1回ずつ確認していること
- `targets.conf`が、動作確認用の内容ではなく実運用向けの内容に戻っていること
