# 04. テスト仕様書

[03-build-guide.md](./03-build-guide.md)の手順で構築した環境に対して実施するテストケース一覧。正常系(想定通りに動くこと)と異常系(想定外の状況でも安全に倒れる、または継続動作できること)の両方を確認する。

## 1. テスト方針

- なるべく`THROTTLE_SECONDS`を短い値(例: 5〜10秒)に一時変更し、5分待たずにスロットリングの動作を検証する
- Slackへの実通知を確認するテストと、`journalctl`/標準出力のログだけで確認できるテストを区別する
- 異常系テストで変更した設定値・状態ファイルは、テスト後に必ず元の状態へ戻す

## 2. テストケース一覧

| テストID | 分類 | 前提条件 | 操作手順 | 期待結果 |
|---|---|---|---|---|
| TC-01 | 正常系 | サービスが`active`な状態。`LOG_FILE`に`ERROR`を含まない行のみ存在 | `[INFO]`を含む行を1行追記する | Slackに通知が届かない。`journalctl`にも検知ログが出ない |
| TC-02 | 正常系 | サービスが`active`な状態 | `[ERROR]`を含む行を1行追記する | 数秒以内にSlackへ通知が届く。通知本文に検知したログ行の抜粋が含まれる |
| TC-03 | 正常系 | サービスが`active`な状態 | `[CRITICAL]`を含む行を1行追記する | TC-02と同様に通知が届く(`ERROR`だけでなく`CRITICAL`も検知対象であることの確認) |
| TC-04 | 正常系(スロットリング) | `THROTTLE_SECONDS`を10秒程度に一時変更し、直前の通知から10秒以上経過した状態 | `test-generate-log.sh CRITICAL 5`で0.5秒間隔のログを5件連続追記する | Slackへの通知は1回のみ届く。ログには2件目以降が「スロットリング中のため通知を抑制しました」と記録される |
| TC-05 | 正常系(スロットリング解除) | TC-04実施直後 | スロットリング時間が経過してから、さらに1件`[ERROR]`を追記する | 新たな通知がSlackに届き、本文に「※直近N秒以内に、このほかM件の検知を抑制しました」という一文が含まれる |
| TC-06 | 正常系 | サービス起動直後(状態ファイルが初期値`0\t0`) | `[ERROR]`を1件追記する | `last_notify_epoch=0`のため、スロットリング判定を待たずに即座に通知される |
| TC-07 | 正常系(ログローテート耐性) | サービスが`active`な状態 | 監視対象ファイルを`mv`で退避し、同名の新しいファイルを作成したうえで`[CRITICAL]`を1行追記する | `journalctl`に`tail`が新しいファイルを検知した旨のメッセージ(`has appeared; following new file`)が記録され、新ファイルへの追記も正しく検知・通知される(`tail -F`の効果) |
| TC-08 | 正常系 | サービスが再起動されている、または`systemctl restart`直後 | `systemctl is-enabled log-watch-alert` / `systemctl is-active log-watch-alert` を実行する | それぞれ`enabled` / `active`が返る(自動起動設定の確認) |
| TC-09 | 異常系 | `.env`から`SLACK_WEBHOOK_URL`の行を一時的にコメントアウト(または空)にする | `log-watch-alert.sh`を手動起動する | 起動直後に`[ERROR] SLACK_WEBHOOK_URL が設定されていません...`とログに出力され、終了コード`1`で即座に終了する |
| TC-10 | 異常系 | `LOG_FILE`を存在しないパスに一時変更する | `log-watch-alert.sh`を手動起動する | 起動直後に`[ERROR] 監視対象のログファイルが見つかりません...`とログに出力され、終了コード`1`で即座に終了する |
| TC-11 | 異常系 | `jq`を一時的にアンインストール、またはPATHから除外した状態にする | `log-watch-alert.sh`を手動起動する | 起動直後に`[ERROR] コマンド 'jq' が見つかりません...`とログに出力され、終了コード`1`で即座に終了する |
| TC-12 | 異常系(通知失敗時の継続動作) | `SLACK_WEBHOOK_URL`を到達不能なURL(存在しないポート等)に一時変更する | サービスを起動し、`[ERROR]`を1件追記する | `curl`のエラー(`Failed to connect...`)とともに`[ERROR] Slack通知の送信に失敗しました(HTTP 000)`がログに記録されるが、監視プロセス自体は停止せず動作を継続する |
| TC-13 | 異常系(状態ファイル破損) | `state.tsv`の中身を、タブ区切りでない不正な文字列に書き換えておく | `[ERROR]`を1件追記する | `[WARN] 状態ファイルの内容が不正なため、最終通知時刻を初期値(0)として扱います`とログに記録され、異常終了せずに通知処理が続行される。状態ファイルは正しい形式(`エポック秒\tカウント`)に上書きされる |
| TC-14 | 異常系 | `.env`の権限を`644`など緩い状態にしてしまっている | `stat -c '%a' /opt/log-watch-alert/.env` で権限を確認する | 権限が要件(NFR-04、所有者以外読み取り不可)を満たしていないことを検出できる。検出したら`chmod 600`で是正する |
| TC-15 | 異常系(権限不足) | 監視対象ログファイルの権限を`600`(所有者root以外読み取り不可)に一時変更する | `logwatch`ユーザーでサービスを再起動する | `tail`が`Permission denied`でログを読み取れず、`journalctl`にエラーが記録される。原因調査の観点から、`ls -l`でログファイルの権限を確認する運用手順があることを確認する |

## 3. テスト結果の記録方法

各テストケースについて、実施日・実施者・結果(OK/NG)・ログの抜粋を記録する。以下は記録テンプレートの例。

```text
テストID: TC-04
実施日: 2026-08-31
実施者: (氏名)
結果: OK
ログ抜粋:
  [2026-08-31 09:25:40] [INFO]  Slack通知を送信しました(HTTP 200)
  [2026-08-31 09:25:40] [INFO]  スロットリング中のため通知を抑制しました(直近通知から0秒 / 抑制件数1)
  [2026-08-31 09:25:41] [INFO]  スロットリング中のため通知を抑制しました(直近通知から1秒 / 抑制件数2)
備考: Slackへの通知が1回のみであることを目視確認済み
```

## 4. 完了基準

- TC-01〜TC-15のすべてが期待結果通りであること
- 異常系テスト(TC-09〜TC-15)で一時的に変更した設定値・ファイル内容が、テスト後にすべて元の値へ戻っていること
- Slack通知が実際にチャンネルへ届くことを、目視で最低1回確認していること
- `systemctl is-enabled` / `systemctl is-active` の両方が期待通りであること(常駐化の確認)
