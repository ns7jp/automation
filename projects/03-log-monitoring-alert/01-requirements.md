# 01. 要件定義書

案件No.3「ログ監視・異常検知アラート通知ツール」の要件を定義する。

## 1. 背景・目的

夜間にWebアプリケーションでエラーが多発していたが、監視の仕組みが無かったため誰も気づかず、翌朝クレームが来てから発覚するというインシデントが発生した。

この問題を解決するため、以下を目的として監視・通知ツールを構築する。

- エラーの発生を**人が見に行かなくても**検知できるようにする
- 検知したら**すぐに**担当者へ伝わる経路(Slack)を用意する
- 大量発生時に通知が埋もれないよう、**通知の量そのものを制御**する
- 監視プロセス自体が**止まったままにならない**運用にする(自動起動・自動復旧)

## 2. 機能要件

| 要件ID | 要件名 | 詳細 | 優先度 |
|---|---|---|---|
| FR-01 | ログのリアルタイム監視 | 指定したログファイル(例: `/var/log/app/error.log`)を`tail -F`でリアルタイムに追尾する | 必須 |
| FR-02 | 異常文字列の検知 | `ERROR`または`CRITICAL`を含む行を、正規表現(`grep -E`)のOR条件で検知する | 必須 |
| FR-03 | Slackへの通知 | 検知した内容をSlack Incoming Webhookへ`curl`でPOST送信し、通知する | 必須 |
| FR-04 | 通知本文への抜粋含有 | 通知メッセージに、検知したログ行そのもの(抜粋)を含める | 必須 |
| FR-05 | スロットリング(通知の集約) | 直近5分(既定値、設定変更可)以内に再検知した場合は通知を送らず抑制し、次に通知するタイミングで抑制件数を併記する | 必須 |
| FR-06 | 常駐サービス化 | 監視プロセスをsystemdサービスとして登録し、サーバー再起動後も自動的に起動する | 必須 |
| FR-07 | プロセス異常終了時の自動復旧 | 監視プロセスが予期せず終了した場合、systemdが自動的に再起動する | 必須 |
| FR-08 | 設定の外部化 | 監視対象パス・Webhook URL・検知パターン・スロットリング時間を設定ファイル(`.env`)に分離し、スクリプト本体を変更せずに変更可能にする | 推奨 |
| FR-09 | 動作確認用のログ生成 | 実際の障害を待たずに検知・通知・スロットリングを検証できる、疑似ログ生成スクリプトを用意する | 推奨 |

## 3. 非機能要件

| 要件ID | 分類 | 要件 | 補足 |
|---|---|---|---|
| NFR-01 | 可用性 | 監視プロセスは可能な限り止まらないこと。停止しても自動的に再起動されること | systemdの`Restart=on-failure`で担保する |
| NFR-02 | 耐障害性 | Slack通知が一時的に失敗しても、監視プロセス自体は継続して動作すること | `curl`の失敗を検知しログに残すが、スクリプトは終了させない |
| NFR-03 | べき等性(=同じ処理を何度実行しても結果が同じ、または安全な状態を保てる性質) | スクリプトを複数回起動・再起動しても、状態ファイルが壊れて誤動作しないこと | 状態ファイルが存在しない場合は初期値で自動生成し、内容が数値として不正な場合も検知して初期値へフォールバックする(詳細は[02-design.md](./02-design.md) 4.6節) |
| NFR-04 | セキュリティ | Slack Webhook URLを含む設定ファイル(`.env`)は、所有者以外が読み取れないようにすること | `chmod 600 .env`を徹底する |
| NFR-05 | 最小権限 | 監視プロセスは、root権限ではなく専用の非rootユーザーで実行すること | systemdの`User=`/`Group=`で専用ユーザー(`logwatch`)を指定する |
| NFR-06 | 保守性 | 設定(監視対象・閾値等)とロジック(検知・通知処理)を分離すること | `.env`ファイルと`log-watch-alert.sh`を分離する |
| NFR-07 | 監視性 | 動作ログにはタイムスタンプとログレベル(INFO/ERROR)を付与し、`journalctl`から追跡できること | systemd配下では標準出力がそのままjournaldに記録される |
| NFR-08 | 応答性(検知から通知までの遅延) | エラー発生から通知までの遅延は、スロットリング中でない限り数秒以内であること | `tail -F`によるリアルタイム追尾のため、ポーリング方式より遅延が小さい |

## 4. スコープ外(今回は対応しない範囲)

- 複数のログファイルを同時に監視すること(1インスタンス=1ログファイルを前提とする。複数監視したい場合はサービスを複数登録する運用を想定)
- Slack以外の通知先(メール、PagerDuty等)への対応
- 検知内容の重要度に応じた通知先の出し分け(すべて同一チャンネルへ通知する)
- ログ内容を集計・可視化するダッシュボード機能
- 誤検知(例: `ERROR`という文字列を含むが実際は異常でないログ)を機械学習等で判定する高度なフィルタリング

## 5. 検証環境

実際の構築・動作確認は、以下の環境を想定して行う(ローカルVMまたはコンテナでの再現を想定)。

| 項目 | バージョン等 |
|---|---|
| OS | Ubuntu Server 22.04 LTS |
| シェル | bash 5.1.16 |
| coreutils(tail, date等) | 8.32 |
| grep(GNU grep) | 3.7 |
| curl | 7.81.0 |
| jq | 1.6以上 |
| systemd | 249以上 |
| 実行ユーザー | 専用の非rootユーザー(`logwatch`。`useradd --system`で作成) |
| 監視対象ログ例 | `/var/log/app/error.log`(架空のWebアプリケーションが出力する想定) |
| 通知先 | Slack(Incoming Webhookを利用。ワークスペースの管理者権限が必要) |

> 💡 `jq`は標準ではインストールされていないことが多いため、構築時に`apt-get install -y jq`で追加する([03-build-guide.md](./03-build-guide.md) Step 2参照)。バージョンが多少前後しても、本ドキュメントで使用するオプション(`tail -F`, `grep -E`, `curl -X POST`など)は標準的なGNU実装であれば同様に動作する。
