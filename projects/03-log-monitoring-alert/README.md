# 案件No.3: ログ監視・異常検知アラート通知ツール

## 難易度

★★★☆☆(初級〜中級)

個々の技術要素(正規表現、Webhook、systemd)は単体では難しくないが、それらを組み合わせて「サーバーが再起動しても止まらずに動き続ける常駐プロセス」を設計する点で、案件No.2(cronによる定期実行)よりも一段階上のレベルに設定している。夜間・休日でも人手を介さずに異常を検知できる仕組みを作る、実務に直結したテーマでもある。

## 想定依頼元・背景

架空の自社開発チーム(ECサイト運営)。ある夜間、Webアプリケーションでエラーが多発していたが、監視の仕組みが無かったため誰も気づかなかった。翌朝出社してみると、ユーザーからのクレームが大量に届いており、原因を調べると深夜のうちに数時間エラーが出続けていたことが判明した。

このインシデントを受けて、「エラーログを常時監視し、異常が発生したらすぐにSlackへ通知してほしい。ただし通知が来すぎても見落とすので、短時間に大量発生した場合はまとめて1回にしてほしい」という依頼が来た、という想定でこの案件は設計されている。

## 依頼内容(要求仕様)

- 指定したログファイル(例: `/var/log/app/error.log`)を**リアルタイム**で監視すること
- `ERROR` または `CRITICAL` という文字列を含む行を検知したら、Slackへ**Incoming Webhook**(=あるURLにJSONデータを送るだけでSlackにメッセージを投稿できる仕組み)を使って通知すること
- 同じような検知が短時間(既定5分以内)に連続発生した場合は、通知をまとめて1回にする**スロットリング**(=通知の頻度に上限を設ける仕組み)を実装し、通知の洪水を防ぐこと
- 監視プロセスはサーバー再起動後も自動的に立ち上がるように、**systemd**(=Linuxでプロセスを常駐させ、自動起動・自動再起動を管理する仕組み)でサービス化すること
- 検知したログ内容の抜粋をSlack通知メッセージに含めること

詳細は [01-requirements.md](./01-requirements.md) を参照。

## 使用技術・ツール

- **OS**: Ubuntu Server 22.04 LTS
- **Bash**: 監視・通知本体のロジック実装
- **tail -F**: ログファイルの末尾をリアルタイムに追尾する
- **grep -E**: 拡張正規表現によるキーワード判定(`ERROR|CRITICAL`のOR条件)
- **curl**: Slack Incoming WebhookへのHTTP POST送信
- **jq**: JSON文字列の安全な組み立て(改行やクォートを含む行を壊さずにエスケープする)
- **systemd**: 監視プロセスの常駐化・自動起動・自動復旧
- **状態ファイル(state file)**: 直近の通知時刻・抑制件数を記録し、スロットリングを実現する仕組み

## この案件で身につくスキル

- `tail -f` と `tail -F` の違いを理解し、ログローテートに強い監視スクリプトを書ける
- 正規表現の基本(`|`によるOR条件など)を理解し、`grep -E`で意図した行だけを抽出できる
- Webhookという「HTTP POSTだけでSaaS連携できる」仕組みを理解し、curl + jqで安全に実装できる
- 状態ファイルを使った「時間ベースの制御(スロットリング)」を自作できる
- cronではなくsystemdで常駐プロセスを管理する理由を理解し、unitファイルを自分で書ける
- 「検知して終わり」ではなく、シグナル処理・異常系・再起動時の自動復旧まで含めた運用視点を持てる

## 面接でアピールできるポイント(3つ、実際に話すセリフ例つき)

1. **「検知できない」を「検知して即通知」に変える、監視の自動化力**
   > 「夜間にエラーが多発していても誰も気づけないという課題に対して、`tail -F`でログをリアルタイムに追尾し、`grep -E`で`ERROR|CRITICAL`を検知したら即座にSlackへ通知する仕組みを作りました。`tail -f`ではなく`-F`を使うことで、ログローテートでファイルが入れ替わっても監視が途切れないようにしている点まで説明できます。」

2. **『通知が来すぎて逆に見落とす』を防ぐ、スロットリング設計力**
   > 「同じエラーが短時間に連発すると通知が洪水になり、かえって重要な通知が埋もれてしまいます。そこで、状態ファイルに『最終通知時刻』と『抑制件数』を記録し、直近5分以内の再検知は通知を送らずカウントだけ増やす、というスロットリングを自作しました。次に通知するタイミングで『このほかN件を抑制しました』と一緒に伝えることで、情報を失わずに通知数だけを絞れる設計にしています。」

3. **cronではなくsystemdを選んだ、常駐プロセス設計の理解**
   > 「このツールは常に動き続けて初めて意味があるため、決まった時刻にだけ起動するcronではなく、プロセスとして常駐させ続けられるsystemdを採用しました。`Restart=on-failure`でプロセスが落ちても自動再起動し、`WantedBy=multi-user.target`をenableすることでサーバー再起動後も自動的に立ち上がる。単にコマンドを動かすだけでなく、落ちたときにどう自己復旧させるかまで設計に含めています。」
