# 01. 要件定義書

案件No.5「Ansibleによるサーバー初期構築自動化(IaC)」の要件を定義する。

## 1. 背景・目的

新規サービス立ち上げのたびに、Webサーバー(Nginx)の構築を手作業で行っていた。手順書は存在するものの、以下の問題が繰り返し発生していた。

- 手順書の読み飛ばし・入力ミスによる設定ミス(例: ファイアウォールの許可ポートを間違える)
- 作業者のスキル差による構築時間のばらつき(2時間で終わる人もいれば、半日かかる人もいる)
- 「どのサーバーにどんな手順で構築したか」が作業者の記憶とメモ書きにしか残らない属人化

これらを解消するため、以下を目的としてサーバー構築を自動化・標準化する。

- サーバー構築の手順を**コードとして管理**し、誰が実行しても同じ結果になるようにする(IaC = Infrastructure as Codeの考え方)
- 構築コードをGitなどで**バージョン管理できる形**にし、「いつ・何を変更したか」を追跡可能にする
- **何度実行しても安全**(べき等性)な仕組みにし、構築済みサーバーに再実行しても壊れないようにする

## 2. 機能要件

| 要件ID | 要件名 | 詳細 | 優先度 |
|---|---|---|---|
| FR-01 | Nginxの自動インストール・設定 | Nginxをインストールし、ポート80で静的HTMLページを公開する状態にする | 必須 |
| FR-02 | ファイアウォールの自動設定 | ufw(Debian系)またはfirewalld(RedHat系)を用いて、SSH(22)/HTTP(80)/HTTPS(443)のみを許可し、それ以外の受信は拒否する | 必須 |
| FR-03 | 作業用一般ユーザーの作成 | root以外の一般ユーザーを作成し、sudo(管理者権限への昇格)を許可する | 必須 |
| FR-04 | SSH公開鍵の配置 | 作成した一般ユーザーに、指定したSSH公開鍵を`authorized_keys`として登録する | 必須 |
| FR-05 | パスワード認証の無効化 | SSHのパスワード認証(`PasswordAuthentication`)を無効化し、鍵認証のみ許可する | 必須 |
| FR-06 | rootログインの無効化 | SSHでのrootへの直接ログイン(`PermitRootLogin`)を無効化する | 必須 |
| FR-07 | タイムゾーン設定 | サーバーのタイムゾーンをAsia/Tokyoに設定する | 必須 |
| FR-08 | Inventoryによる対象管理 | 構築対象のサーバーをInventoryファイルに一覧化し、1コマンド(`ansible-playbook`)で複数台へ同時に適用できること | 必須 |
| FR-09 | Role単位のコード分割 | 処理内容を役割ごとにRole(common/users/firewall/nginx)へ分割し、再利用・保守しやすい構成にすること | 必須 |
| FR-10 | dry run(--check)の活用 | 実際に変更を加える前に、`ansible-playbook --check --diff`で「何が変わるか」を事前に確認できること | 必須 |
| FR-11 | べき等性の担保 | 同じPlaybookを複数回実行しても、2回目以降は不要な変更(changed)が発生しないこと | 必須 |

## 3. 非機能要件

| 要件ID | 分類 | 要件 | 補足 |
|---|---|---|---|
| NFR-01 | べき等性(=同じ処理を何度実行しても結果が同じになる性質) | 全タスクが「あるべき状態」を宣言する形で書かれており、既に条件を満たす場合は何もしないこと | Ansibleの標準モジュールは基本的にべき等に作られているため、`shell`/`command`モジュールの多用を避け、専用モジュール(`user`/`package`/`template`等)を優先する |
| NFR-02 | 可用性 | Nginxの設定変更時は`reload`(無停止反映)を優先し、不要な`restart`によるサービス断を避けること | `restart`が必要なケース(ワーカープロセスのユーザー変更等)は今回のスコープでは発生しない |
| NFR-03 | セキュリティ | パスワード認証を無効化する前に、鍵認証でのログインが成立することを人手で確認できる手順になっていること | `--tags`/`--skip-tags`でユーザー作成とSSHロックダウンを分離し、段階的に適用できるようにする |
| NFR-04 | セキュリティ | ファイアウォールで許可するのはSSH/HTTP/HTTPSの3つのみとし、それ以外の受信ポートはデフォルトで拒否すること | ufwは`default deny incoming`、firewalldは許可サービスの明示指定で実現する |
| NFR-05 | 保守性 | 環境固有の値(ユーザー名・ポート番号・パッケージ一覧等)をRoleの`defaults`や`group_vars`に外出しし、タスクの中に直接書かないこと | 設定変更時にコード本体を触らずに済むようにする |
| NFR-06 | 移植性 | Debian系(Ubuntu)とRedHat系(AlmaLinux等)の両方に対応すること | `ansible_facts['os_family']`で判定し、OS固有の処理を分岐する |
| NFR-07 | 再現性 | 対象サーバーがまっさらな状態(初期状態)であれば、Playbook実行だけでFR-01〜FR-07の状態まで到達できること | 手作業の追加設定を前提にしない |
| NFR-08 | 監査性 | 実行結果(どのタスクがchanged/okになったか)がコンソールに一覧表示され、後から確認できること | `stdout_callback = yaml`で可読性を高めている |

## 4. スコープ外(今回は対応しない範囲)

- HTTPS化(SSL/TLS証明書の取得・設定。ファイアウォールで443番ポートは開けるが、証明書発行(Let's Encrypt等)自体は対象外)
- アプリケーションのデプロイ(今回はNginxで静的ページを公開するところまでが対象。動的アプリケーションのデプロイは対象外)
- Ansible Tower/AWX等のGUI・ジョブスケジューリング基盤の導入(CLIでの`ansible-playbook`実行を前提とする)
- Ansible Vault(機密情報の暗号化)を用いた秘匿情報管理の実装(存在は05-troubleshooting.md等で触れるが、本教材のPlaybook自体には組み込まない)
- クラウド上でのVM自体の作成(AWSやGCPのインスタンス作成はAnsibleのスコープ外とし、「既にサーバーが起動している状態」からを対象とする)

## 5. 検証環境

実際の構築・動作確認は、以下の環境を想定して行う(ローカルVM、または対応するクラウドVM上での再現を想定)。

### 5.1 コントロールノード(Ansibleを実行する側の作業PC)

| 項目 | バージョン等 |
|---|---|
| OS | Ubuntu Desktop 22.04 LTS(WSL2上のUbuntu 22.04でも可) |
| Python | 3.10系 |
| Ansible(パッケージ) | ansible 9.x系(内部の`ansible-core`は2.16系) |
| 追加Collection | `ansible.posix` >= 1.5.0 / `community.general` >= 7.0.0(`src/requirements.yml`参照) |
| SSHクライアント | OpenSSH 8.9系 |

### 5.2 管理対象サーバー(構築先。2系統のOSで検証する)

| 項目 | 対象1(Debian系) | 対象2(RedHat系) |
|---|---|---|
| OS | Ubuntu Server 22.04 LTS | AlmaLinux 9.3 |
| Python(管理対象側) | 3.10系(`/usr/bin/python3`) | 3.9系(`/usr/bin/python3`) |
| Nginx | 1.18.0(標準リポジトリ) | 1.20.1(標準リポジトリ) |
| SSHサーバー | OpenSSH 8.9系(サービス名: `ssh`) | OpenSSH 8.7系(サービス名: `sshd`) |
| ファイアウォール | ufw | firewalld |
| 管理者グループ | `sudo` | `wheel` |
| 初期状態 | rootでのSSH鍵ログインが可能なまっさらなサーバー(パッケージ未導入) | 同左 |

> 💡 実務のクラウドVM(AWS EC2、さくらのVPS等)では、初期ユーザーが`root`ではなく`ubuntu`や`ec2-user`になっているケースが多い。その場合は`inventory/hosts.ini`の`ansible_user`を書き換え、`become: true`でrootに昇格する流れになる。本教材では説明を単純化するため、初期状態から`root`で直接SSH接続できる想定としている。

## 6. 用語整理(要件定義段階で押さえておきたいもの)

| 用語 | 意味 |
|---|---|
| IaC(Infrastructure as Code) | サーバーやネットワークなどのインフラ構成を、手順書やGUI操作ではなく「コード」として記述・管理する考え方。コード化することでバージョン管理・レビュー・再現性の確保がしやすくなる |
| べき等性(idempotency) | ある操作を何度実行しても、結果が変わらない(同じ状態に収束する)性質。Ansibleの多くのモジュールはこの性質を持つように設計されている |
| Playbook | Ansibleが実行する処理内容をYAMLで記述したファイル。「どのホストに」「何を」実行するかを定義する |
| Inventory | Ansibleの操作対象となるサーバーの一覧・接続情報を定義するファイル(または動的に取得する仕組み) |
| Role | Playbookのタスクを役割ごとに分割・再利用可能にするためのディレクトリ構成の単位 |
| エージェントレス | 管理対象サーバーに専用の常駐エージェントソフトを事前インストールする必要がなく、標準のSSHとPythonだけで動作する方式。Ansibleの大きな特徴の1つ |
