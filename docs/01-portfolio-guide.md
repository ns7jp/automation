# ポートフォリオ活用ガイド

このドキュメントは、本リポジトリ(`automation`)を転職・就職活動でどう使うかをまとめたものです。「作って終わり」にせず、面接や書類選考で成果として語れる状態にすることを目的としています。

対象読者は次の2者です。

- **本ポートフォリオの作成者本人**: 面接・書類でどう説明すればよいかを知りたい方
- **採用担当者・面接官**: 応募者のスキルをどう読み取ればよいかの参考にしたい方

---

## 1. まず押さえておきたい前提

未経験者のポートフォリオでありがちな失敗は、「技術のお試し実装(Hello World的なもの)」を並べただけで終わってしまうことです。本ポートフォリオは、それを避けるために次の3点を意図的に設計しています。

1. 各案件に「架空の依頼元企業・部署・課題・要望」を設定し、実務のプロジェクトに近い流れ(要件定義 → 設計 → 構築 → テスト → トラブルシューティング)を再現している
2. すべてのスクリプト・設定ファイルは実機相当の環境で動作検証済みである(「動くはず」ではなく「動くことを確認した」)
3. 専門用語には初出時に解説を添え、理解を伴って作成したことが分かるようにしている

面接・書類ではこの3点を軸に説明すると、単なる技術力だけでなく「実務でどう動けるか」を伝えやすくなります。

## 2. 面接でのアピール方法

### 2.1 想定される質問と回答例

#### Q. 「実務経験がないようですが、なぜサーバー構築エンジニアを目指したのですか?」

> A. 実務経験はまだありませんが、実務を想定した6件の「案件」形式でポートフォリオを作成し、要件定義から構築・テスト・トラブルシューティングまでを一通り経験しました。たとえば案件No.4では、複数台のサーバーの死活監視を行うツールを、pingとHTTPステータスコードの2方式で作成し、誤検知(フラッピング)を防ぐための閾値設計まで自分で考えて実装しています。実務経験の代わりに、この一連のプロセスを自分の手で再現することで、「何ができるか」を示せるようにしました。

#### Q. 「この中で一番苦労した案件はどれですか?」

> A. 案件No.5のAnsibleによるサーバー構築自動化です。それまでのBashスクリプトと違い、「べき等性(=何度実行しても安全で、結果が同じになるという性質)」を意識したタスク設計が必要で、最初は`--check`オプションでのdry run(=実際には変更せず、何が変わるかだけ確認する実行方法)がなぜ重要なのか実感できていませんでした。実際に設定を1つ間違えた状態で2回連続実行し、`changed=0`にならないケースを自分で再現・修正したことで、「べき等性が壊れるとはどういうことか」を体感できました。この経験は、YAMLの文法を覚えること以上に大きな学びでした。

#### Q. 「なぜこの技術(cron / systemd / Ansible / GitHub Actions)を選んだのですか?」

> A. 各案件のREADMEにも書いていますが、それぞれ用途に応じて使い分けています。たとえば案件No.2のバックアップは「決まった時刻に1回だけ実行すればよい」処理なのでcronを使い、案件No.3のログ監視は「常に動き続けて即座に検知したい」処理なのでsystemdによる常駐プロセスにしています。「とりあえず動くものを作る」のではなく、要件に対して技術選定の理由を説明できることを意識しました。

#### Q. 「一番自信のある案件はどれですか、その理由も教えてください」

> A. 案件No.6のCI/CDパイプラインです。GitHub Actionsのワークフローで、`shellcheck`による静的解析とサンプルアプリのテストを通過した場合のみ、SSH鍵認証とrsyncを使って本番相当のサーバーへ自動デプロイする仕組みを作りました。`needs`と`if`を使ってCIジョブの成功をCDジョブの実行条件にする設計や、`concurrency`で多重デプロイを防ぐ設計など、単に動くだけでなく「事故を起こさない」ことを意識した点を評価してほしいです。

### 2.2 深掘り質問への備え

面接官は「本当に自分で考えて作ったか」を確認するために、実装の意図を掘り下げてくることがあります。次のような質問には各案件の`02-design.md`(設計書)や`05-troubleshooting.md`(トラブルシューティング集)を読み返しておくと答えやすくなります。

| 想定質問 | 参照すべきドキュメント |
|---|---|
| 「なぜこの設計にしたのか」「他の方法は検討したか」 | 各案件の `02-design.md` |
| 「実際に動かして、うまくいかなかったことはあるか」 | 各案件の `05-troubleshooting.md` |
| 「テストはどう行ったか、異常系はどこまで考えたか」 | 各案件の `04-test-plan.md` |
| 「セキュリティ面で気をつけたことは?」 | 案件No.5・No.6の「SSH鍵認証」「Secrets管理」の記述 |

## 3. 職務経歴書・ポートフォリオサイトでの見せ方

### 3.1 職務経歴書への書き方(例)

未経験者の職務経歴書では、「自己学習・ポートフォリオ」の項目を独立させて書くと伝わりやすくなります。

```text
【自己学習・ポートフォリオ】
実務を想定した「案件」形式で、Linuxサーバーの自動化ツールを6件作成(GitHubで公開)。
要件定義・設計・構築・テスト・トラブルシューティングまでの一連の流れを、
架空の依頼背景を設定した上で実践した。

主な成果:
・Bashシェルスクリプトによるユーザーアカウント一括作成/バックアップ自動化/
  ログ監視・死活監視ツールを合計4件作成、実機環境で動作検証済み
・Ansibleを用いたサーバー初期構築のIaC(Infrastructure as Code)化を実践し、
  べき等性を担保したPlaybook/Roleを設計
・GitHub Actionsを用いたCI/CDパイプライン(shellcheckによる静的解析→
  SSH鍵認証+rsyncによる自動デプロイ→Slack通知)を構築

リポジトリ: https://github.com/<ユーザー名>/automation
```

ポイントは次の3つです。

- 「作った物」の列挙で終わらせず、「実務を想定した流れで取り組んだ」ことを最初の一文で明示する
- 使用技術を羅列するのではなく、成果(動作検証済み・自動化した結果何が改善するか)とセットで書く
- リポジトリURLを必ず添える(採用担当者はコードそのものよりも「READMEの読みやすさ」で第一印象を判断することが多い)

### 3.2 ポートフォリオサイト・GitHub Profile READMEでの見せ方

個人サイトやGitHub Profile README(ユーザー名と同じ名前のリポジトリに置くREADME)を作る場合は、以下の順で情報を出すと読みやすくなります。

1. 一言コンセプト(「実務を想定した案件形式で自動化ツールを6件構築」)
2. 難易度と技術スタックが一覧できる表(本リポジトリのトップREADMEの表をそのまま流用可能)
3. 一番アピールしたい1〜2案件だけ、スクリーンショットや実行結果の抜粋を掲載
4. 「詳しくはリポジトリを参照」という導線

すべての案件を均等に見せようとせず、応募先企業の技術スタックに近い案件(例: クラウド系企業ならAnsible・CI/CDの案件、社内SE系ならユーザー管理・バックアップの案件)を前面に出すと、より刺さりやすくなります。

## 4. GitHubリポジトリの見せ方のコツ

### 4.1 リポジトリ全体

- **README.mdを「入口」として整える**: 採用担当者は全ファイルを読むわけではないため、トップのREADME.mdだけで「何を、なぜ、どう作ったか」が伝わるようにする(本リポジトリのREADME.mdはその実例)
- **コミット履歴を適度に残す**: 1コミットで全部完成、ではなく、要件定義→設計→実装→テストの順で段階的にコミットされていると、「思考の過程」が伝わりやすい
- **READMEバッジは無理に付けない**: 未経験者がCIバッジなどを形だけ付けると逆に不自然に見えることがある。案件No.6のように実際にGitHub Actionsが動く構成であれば、実際のワークフローのステータスバッジを付けるのは効果的

### 4.2 案件ごとのREADME

各案件のREADME.mdには、次の情報がすでに含まれています。面接前に一通り読み返し、口頭で説明できる状態にしておきましょう。

- 難易度とその理由
- 想定依頼元・背景(なぜこの自動化が必要だったか)
- 依頼内容(要求仕様)
- 成果物一覧(各ドキュメント・スクリプトへのリンク)

### 4.3 面接官・採用担当者向けの読み方の提案

初見でリポジトリ全体を読む時間が取りにくい場合は、次の順番での確認をおすすめします。

1. ルートの[README.md](../README.md) で全体像と技術の幅を確認
2. 難易度が中間の案件(No.3またはNo.4)の `README.md` → `02-design.md` を読み、設計力・Mermaid図での説明力を確認
3. 難易度が最も高い案件No.6の `README.md` → `03-build-guide.md` を読み、複雑な仕組みをどこまで手順化・言語化できているかを確認
4. 気になる案件があれば `05-troubleshooting.md` を読み、実際にどんな問題に直面し、どう解決したかを確認

トラブルシューティング集(`05-troubleshooting.md`)には、実際に手を動かした人でなければ書けない具体的なエラーメッセージや対処法が記載されているため、「本当に自分で動かしたか」を見極める材料として特に参考になります。
