# 初心者向け用語集

本ポートフォリオの全6案件に登場する専門用語を、初心者向けに1〜2文で解説した用語集です。各案件のドキュメントを読んでいて分からない単語が出てきたら、このページに戻って確認してください。

英数字の用語は**アルファベット順**、日本語の用語は**50音順**で並べています。

---

## アルファベット順(英数字の用語)

### A

**Ansible(アンシブル)**
複数のサーバーへ、設定変更やソフトウェアのインストールなどを自動で適用するための構成管理ツール。対象サーバーに特別なエージェント(常駐プログラム)を入れる必要がなく、SSHで接続するだけで使える点が特徴。案件No.5で使用。

**Ansible Collection(アンシブル・コレクション)**
Ansible本体(`ansible-core`)には含まれない追加のモジュール集で、`ansible-galaxy collection install`コマンドで別途インストールして使う。案件No.5では、SSH公開鍵管理(`ansible.posix`)やufw・firewalld操作(`community.general`)のために利用しており、必要なCollectionは`requirements.yml`に一覧化しておく。

**ansible_facts(アンシブル・ファクツ)**
Ansibleが対象サーバーに接続した際に自動収集する、そのサーバーのOS種別・IPアドレス・メモリ容量などの情報。この情報を使って「Ubuntuならこの処理、AlmaLinuxなら別の処理」といった条件分岐ができる。

**awk(オーク)**
テキストファイルを行・列(フィールド)単位で処理するためのコマンド。案件No.4では、ログファイルからタイムスタンプ部分だけを取り出して稼働率を集計する用途で使用。

### B

**Bash(バッシュ)**
Linuxで標準的に使われるシェル(コマンドを解釈して実行するプログラム)の1つ。このシェルの命令を並べたファイルが「シェルスクリプト」で、本ポートフォリオの多くの案件はBashスクリプトとして作られている。

### C

**CD(継続的デリバリー/継続的デプロイ)**
CI(後述)でテストに通ったコードを、自動でサーバーに反映(デプロイ)する仕組み。案件No.6では、テスト成功後にrsyncでファイルを転送する工程がCDにあたる。

**chage(チェイジ)**
Linuxユーザーアカウントのパスワード有効期限を管理するコマンド。`chage -d 0 <ユーザー名>` とすると「次回ログイン時に必ずパスワード変更を求める」設定にできる。案件No.1で使用。

**chpasswd(チェンジパスワード)**
複数のユーザーのパスワードを、対話操作なしでまとめて設定できるコマンド。CSVファイルから読み込んだ初期パスワードを一括登録する際などに使う。

**CI(継続的インテグレーション)**
コードの変更をリポジトリに反映するたびに、自動でテストや静的解析を実行する仕組み。「動くコードだけを取り込む」ことを保証するのが目的。案件No.6では`shellcheck`によるチェックがCIにあたる。

**concurrency(コンカレンシー)**
GitHub Actionsのワークフロー設定項目の1つで、「同じワークフローの多重実行を防ぐ」ための排他制御。デプロイ処理などが同時に2つ走ってしまう事故を防ぐために使う。

**cron(クロン)/ crontab(クロンタブ)**
Linuxで「決まった時刻・周期でコマンドを自動実行する」ための仕組み。設定は`crontab -e`で編集し、「分 時 日 月 曜日」の5つの欄でスケジュールを指定する。案件No.2・No.4で使用。

**CRLF(シーアールエルエフ)**
改行コードの種類の1つ。Windowsで作成したファイルは行末が`\r\n`(CRLF)になっていることが多く、Linux標準の`\n`(LF)と混在するとスクリプトが誤動作する原因になる。CSVパース時に注意が必要。

**CSV(シーエスブイ)**
「Comma-Separated Values」の略で、値をカンマ区切りで並べたテキスト形式のファイル。表計算ソフトで作成しやすく、案件No.1では新入社員情報の受け渡しフォーマットとして使用。

**curl(カール)**
コマンドラインからHTTP通信(Webへのアクセス)を行うためのツール。案件ではSlackへの通知送信(Webhook)や、Webサーバーの死活監視(HTTPステータスコード取得)に使用。

### D

**df(ディーエフ)**
ディスクの使用量・空き容量を確認するコマンド。「disk free」の略。案件No.2では、バックアップ保存先の空き容量が閾値を下回っていないかのチェックに使用。

### F

**find(ファインド)**
条件に合うファイルを検索するコマンド。`-mtime`オプションを使うと「最終更新日から何日経過したファイル」を絞り込める。案件No.2では、7世代を超えた古いバックアップファイルの検出に使用。

**firewalld(ファイアウォールディー)**
主にRed Hat系Linux(AlmaLinux、CentOSなど)で使われるファイアウォール(通信の許可・遮断を管理する仕組み)管理ツール。案件No.5で、OSの種類によって`ufw`(後述)と使い分けている。

### G

**getent(ゲットエント)**
ユーザーやグループの情報を、システムに登録された情報源(通常は`/etc/passwd`など)から検索するコマンド。案件No.1では、ユーザーが既に存在するかどうかの判定に使用。

**getopts(ゲットオプツ)**
シェルスクリプト内でコマンドライン引数(`-n`や`--dry-run`など)を解析するための組み込み機能。オプションの過不足チェックや値の取り出しを簡潔に書ける。

**GitHub Actions(ギットハブ・アクションズ)**
GitHubに標準搭載されているCI/CD機能。リポジトリへのpushなどをきっかけに、YAMLファイルで定義した処理(テスト・ビルド・デプロイなど)を自動実行できる。案件No.6の中核技術。

**GitHub CLI(gh)**
GitHubの操作をターミナルから行うための公式コマンドラインツール。プルリクエストの作成や確認などをWebブラウザを開かずに行える。

**GitHub Secrets(ギットハブ・シークレッツ)**
GitHub Actionsのワークフロー内で使う、SSH秘密鍵やパスワードなどの機密情報を安全に保管する仕組み。リポジトリの設定画面から登録し、コードには直接書き込まない。案件No.6で使用。

**grep -E(グレップ・イー)**
文字列中から指定したパターンに一致する行を検索するコマンド`grep`に、拡張正規表現(`-E`)を組み合わせたもの。`ERROR|CRITICAL`のようにOR条件で複数のキーワードを一度に検索できる。

**groupadd(グループアド)**
Linuxに新しいグループ(ユーザーをまとめる単位。部署ごとの権限管理などに使う)を作成するコマンド。

### H

**Handlers(ハンドラーズ)**
Ansibleで、「設定ファイルが変更されたときだけ実行する処理」(例: サービスの再起動)を定義する仕組み。無駄な再起動を避け、変更があった場合のみ動作させられる。

**HTTPステータスコード**
Webサーバーがリクエストに対して返す3桁の数字で、処理結果を表す。`200`は成功、`404`はページが見つからない、`500`はサーバー内部エラーを意味する。案件No.4では、このコードを使ってWebサーバーの生死を判定する。

### I

**IaC(アイエーシー / Infrastructure as Code)**
サーバーやネットワークの構成を、手作業ではなくコード(設定ファイル)として記述・管理する考え方。同じコードを実行すれば誰が実行しても同じ環境が再現できる。案件No.5のテーマ。

**ICMP(アイシーエムピー)**
ネットワーク機器同士が生存確認などを行うための通信プロトコル。`ping`コマンドはこのICMPを使って、相手のサーバーが応答するかどうかを確認する。

**IFS(アイエフエス)**
「Internal Field Separator」の略で、シェルが文字列を単語ごとに区切る際に使う区切り文字を指定する変数。CSVファイルをカンマ区切りで読み込む際、`IFS=,`と設定して使う。

**Inventory(インベントリ)**
Ansibleで、設定を適用する対象サーバーの一覧を定義するファイル。IPアドレスやホスト名、グループ分け(webservers、dbserversなど)を記述する。

### J

**Jinja2(ジンジャツー)**
Ansibleなどで使われるテンプレートエンジン(雛形に変数を埋め込んで文書を生成する仕組み)。`{{ 変数名 }}`のような記法で、設定ファイルの一部を動的に生成できる。

**journald(ジャーナルディー)**
systemdに組み込まれたログ管理の仕組み。サービスの起動・停止・エラーなどのログを一元的に記録し、`journalctl`コマンドで参照できる。

**jq(ジェイキュー)**
JSON形式のデータをコマンドラインで整形・抽出するツール。Slack Webhookへ送信するJSONメッセージを安全に組み立てる際などに使用。

### L

**logrotate(ログローテート)**
ログファイルが際限なく肥大化しないよう、一定の周期・サイズでファイルを切り替え(ローテーション)、古いものを圧縮・削除する仕組み。設定は`/etc/logrotate.d/`配下に置く。案件No.2ではバックアップ処理自体のログ管理に、案件No.3・No.4では監視対象アプリのログがローテートされた場合でも追跡が途切れないようにする文脈で登場する。

### N

**Nginx(エンジンエックス)**
Webサーバーソフトウェアの1つ。軽量で高速な処理が特徴で、静的ファイルの配信やリバースプロキシ(後段のアプリケーションサーバーへの中継)として広く使われる。案件No.5で自動構築する対象。

### P

**PAM(パム / Pluggable Authentication Modules)**
Linuxでユーザー認証やパスワードポリシー(桁数・複雑性などの制約)を柔軟に組み込むための仕組み。案件No.1では、パスワードの複雑性チェック自体はツールの責務とせず、OS側のPAM設定に委ねる方針としている。

**Playbook(プレイブック)**
Ansibleで「どのサーバーに、何をするか」を記述するYAMLファイル。実行したいタスクの一覧を宣言的(手順ではなく「あるべき状態」として)に書く。

### R

**Role(ロール)**
Ansibleで、関連するタスク・変数・テンプレートなどを1つの単位にまとめる仕組み。「common」「nginx」のように機能ごとにRoleを分けることで、再利用しやすく見通しの良い構成にできる。

**root権限**
Linuxシステムの管理者権限のこと。ユーザー作成やシステム設定の変更など、影響範囲の大きい操作にはroot権限が必要になる。案件No.1では、一般ユーザーでスクリプトが実行された場合にエラーで止める安全対策を入れている。

**RPO(アールピーオー / Recovery Point Objective)**
障害やデータ消失が起きたときに、どの時点の状態まで復旧できればよいかを示す目標値。案件No.2では日次(1日1回)バックアップを取得しているため、最大でも「前日のバックアップ取得時点」までは復旧できる計算になり、RPOはおよそ24時間となる。

**rsync(アールシンク)**
ファイル・ディレクトリを別のサーバーへ同期(コピー)するコマンド。変更があった部分だけを転送する差分同期に対応しており、`scp`による全件転送より効率的。案件No.6のデプロイ処理で使用。

### S

**shellcheck(シェルチェック)**
シェルスクリプトの文法ミスや、意図しない挙動につながりやすい書き方を検出する静的解析ツール(=実際にプログラムを実行せず、コードを読むだけで問題を検出するツール)。案件No.6のCIに組み込んでいる。

**Slack Incoming Webhook(スラック・インカミング・ウェブフック)**
外部のプログラムからSlackの特定チャンネルへメッセージを投稿できる仕組み。あらかじめ発行されたURLへHTTPリクエスト(`curl`など)を送るだけでメッセージが届く。

**SSH公開鍵認証**
パスワードの代わりに、公開鍵と秘密鍵のペアを使ってサーバーへ安全にログインする認証方式。秘密鍵は手元(または鍵管理の仕組み)に置き、サーバー側には公開鍵だけを登録する。案件No.5・No.6で使用。

**systemd(システムディー)**
現在の主要なLinuxディストリビューションで標準的に使われる、サービス(常駐プログラム)の起動・停止・自動復旧を管理する仕組み。「unitファイル」と呼ばれる設定ファイルでサービスの挙動を定義する。案件No.3で使用。

### T

**tail -f / -F(テイル)**
ファイルの末尾を表示し続けることで、追記されるログをリアルタイムに確認できるコマンド。`-F`は、ログローテート(ファイルの入れ替え)が起きても追跡を続ける、より堅牢なオプション。

**tar(ター)/ gzip(ジージップ)**
`tar`は複数のファイル・ディレクトリを1つのアーカイブファイルにまとめるコマンド、`gzip`はそれを圧縮するコマンド。`tar czf`のように組み合わせて「圧縮ファイルにまとめる」処理を1コマンドで行うことが多い。

**tee(ティー)**
コマンドの出力を、画面に表示しつつ同時にファイルにも保存するコマンド。案件では、スクリプトの実行結果を画面確認とログ記録の両方に使う目的で利用している。

### U

**ufw(ユーエフダブリュー)**
Ubuntuなどで使われる、比較的シンプルな操作のファイアウォール管理ツール(Uncomplicated Firewall)。案件No.5で、OSに応じて`firewalld`と使い分けている。

**useradd(ユーザーアド)/ usermod(ユーザーモド)**
`useradd`はLinuxに新しいユーザーアカウントを作成するコマンド、`usermod`は既存ユーザーの設定(所属グループなど)を変更するコマンド。

### Y

**YAML(ヤムル)**
インデント(字下げ)によって階層構造を表す、設定ファイル向けのデータ形式。Ansible PlaybookやGitHub Actionsのワークフローなど、多くの自動化ツールの設定記述に使われる。

### その他の記号・略語

**--check / --diff(dry run)**
Ansibleで実際には変更を適用せず、「実行したら何が変わるか」だけを事前確認できるオプション。`--check`が「変更点があるかどうか」、`--diff`が「具体的な差分内容」を表示する。本番適用前の安全確認として重要。

## 50音順(日本語の用語)

### あ行

**アラート通知**
システムに異常が発生した際、担当者へ知らせるための通知のこと。本ポートフォリオでは主にSlackへのメッセージ送信という形で実装している。

**インシデント**
システム障害やセキュリティ事故など、対応が必要になった出来事のこと。各案件の「想定依頼元・背景」では、実際に起きたインシデントを想定した課題設定をしている。

**閾値(しきいち)**
「これを超えたら異常と判断する」という基準となる数値。案件No.4では「連続2回失敗したら異常」という閾値を設定し、1回だけの一時的な失敗による誤通知(フラッピング)を防いでいる。

### か行

**稼働率**
一定期間のうち、システムが正常に動作していた割合。案件No.4では、直近24時間の監視結果から稼働率を自動集計している。

### さ行

**状態ファイル**
プログラムの実行と実行の間で、情報を引き継ぐために使うファイル。案件No.3・No.4では、「直前に何回連続で失敗したか」「最後に通知した時刻はいつか」などをファイルに保存し、次回実行時に読み込んで判断材料にしている。

**常駐プロセス**
起動後、停止させるまで動き続け続けるプログラムのこと。cronのように「決まった時刻だけ動いて終わる」処理とは異なり、常にログを監視し続けるような用途に向く。systemdで管理されることが多い。

**スロットリング**
短時間に大量に発生するイベント(通知など)を、一定間隔にまとめて抑制する仕組み。案件No.3では、5分以内に連続して検知したエラーをまとめて1回の通知にすることで、通知の洪水を防いでいる。

**制御ノード(せいぎょノード)/ 対象ノード**
Ansibleにおいて、Playbookを実行する側のマシンを「制御ノード」、設定を適用される側のサーバーを「対象ノード(管理対象ホスト)」と呼ぶ。制御ノードから対象ノードへSSHで接続して処理を行う。

**静的解析(せいてきかいせき)**
プログラムを実際に実行せず、コードの記述内容だけを検査して問題点を見つける手法。案件No.6の`shellcheck`はシェルスクリプトの静的解析ツールにあたる。

**世代管理(せだいかんり)**
バックアップファイルなどを一定の保存期間・保存件数(世代)だけ残し、それより古いものは自動的に削除していく管理方法。ディスク容量を圧迫しないための工夫。案件No.2で実装。

### た行

**トリガー(trigger)**
処理が開始されるきっかけとなる出来事のこと。GitHub Actionsでは「mainブランチへのpush」などがトリガーにあたり、`on:`という設定項目で指定する。

**トラブルシューティング**
発生した問題の原因を特定し、解決する一連の作業のこと。各案件の`05-troubleshooting.md`では、実際に検証中に遭遇したエラーとその対処法をQ&A形式でまとめている。

### は行

**べき等性(べきとうせい)**
同じ処理を何度実行しても、結果が変わらず安全であるという性質。Ansibleの設計で特に重視される考え方で、「1回目は新規作成、2回目以降は何も変更しない(changed=0)」という挙動がべき等性の一例。

**フラッピング**
死活監視などで、一時的な通信の揺らぎによって「正常↔異常」の判定が短時間に何度も切り替わってしまう現象。誤通知の原因になるため、連続失敗回数などの閾値を設けて対策する。

**プロセス置換**
シェルスクリプトで、コマンドの実行結果をあたかもファイルであるかのように扱える機能(`<(コマンド)`という書き方)。パイプでは書きにくい処理を、`while read`と組み合わせて安全に書くために使うことがある。

**フルバックアップ**
対象データの全体をまるごと複製するバックアップ方式。差分だけを保存する「差分バックアップ」と対比される。案件No.2ではシンプルさを優先し、フルバックアップ方式を採用している。

**ヒアドキュメント**
シェルスクリプト内で、複数行にわたるテキストをそのまま埋め込むための記法(`<<EOF` 〜 `EOF`のように書く)。案件No.4では、Markdown形式のレポートを組み立てる際に使用している。

### ま行

**Markdownレポート**
見出しや箇条書きなどの簡易な記法(Markdown)で書かれた報告書。GitHubなどでそのまま整形されて表示されるため、監視結果のレポート形式として扱いやすい。

### や行

**要件定義**
システムを作る前に、「何を実現する必要があるか」(機能要件)と「どの程度の性能・安全性が必要か」(非機能要件)を整理する工程。各案件の`01-requirements.md`にあたる。

### ら行

**連想配列(れんそうはいれつ)**
数値の連番ではなく、任意の文字列を「キー」として値を出し入れできる配列。Bashでは`declare -A`で宣言する。案件No.4では、監視対象サーバー名をキーにして連続失敗回数や通知済みフラグを管理するために使用している。

### わ行

**ワークフロー(workflow)**
GitHub Actionsにおいて、「どんなきっかけで、どんな処理を実行するか」をまとめたYAML定義ファイル全体のこと。`.github/workflows/`ディレクトリ以下に配置する。

## この用語集の使い方

- 各案件のREADME.mdや設計書を読んでいて分からない単語が出てきたら、このページ内をブラウザの検索機能(Ctrl+F / Cmd+F)で探すと早く見つかります。
- 用語同士のつながりを意識すると理解が深まります。たとえば「cron」→「crontab」→「トリガー」は、いずれも「処理をいつ実行するか」に関わる用語です。
